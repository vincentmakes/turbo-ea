# Frontend request hooks, singleton hooks, field labels, free text, card pickers and search

> Loaded when you touch `frontend/src/hooks/**`, `frontend/src/components/**`, `frontend/src/features/**`, `frontend/src/lib/**`, … (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

- **Filter-driven GETs must go through the request hooks — never a bare `api.get` in a `useEffect`.** Any fetch keyed on user-controlled state (a type picker, a search box, a tab, a metric toggle) races: the request for the *previous* value can land after the one for the current value and overwrite it, leaving the grid or chart showing data the controls say you are not looking at (#882). Use `useApiQuery(path | null)` (`frontend/src/hooks/useApiQuery.ts`) when one payload feeds one state; `useAbortableEffect(fn, deps)` (`frontend/src/hooks/useLatestRequest.ts`) when the effect writes several states or fans out over `Promise.all`; and the `useLatestRequest()` primitive when the fetch must also be callable imperatively — `InventoryPage`'s `loadData`, which 13 mutation handlers refresh through. All three abort the predecessor **and** bump a generation token. The token is not redundant: an already-resolved response cannot be aborted, and test doubles ignore `AbortSignal` entirely. Two rules are routinely missed and are exactly what re-breaks this: **(1)** guard *every* `setState` with `isCurrent()`, and **(2)** clear the loading flag **only** when `isCurrent()` — an unconditional `finally { setLoading(false) }` lets the aborted predecessor clear the spinner while the winner is still in flight, flashing "done" over stale rows. Debounce free-text search with `useDebouncedValue(value, 300)` and OR its `pending` flag into the loading prop, so a grid never looks settled while it is still showing the previous query's rows; keep discrete toggles instant. `api.get(path, { signal })` rejects with an `AbortError` — if you call it outside these hooks you own that rejection, so check `isAbortError(err)` from `src/api/client.ts`. `signal` is deliberately **not** offered on `post`/`patch`/`put`/`delete`: aborting a mutation does not undo it server-side.

- **Boot-time singleton hooks must use the inflight-promise pattern.** Hooks that fetch a process-wide value once (`useMetamodel`, `useDateFormat`, `useCurrency`, `useBpmEnabled`, `usePpmEnabled`, `useTurboLensReady`, …) keep a module-level `_cache` plus an `_inflight: Promise | null`. The fetch helper checks **both** — if `_cache` has the value, return it; if `_inflight` is non-null, return that promise; only otherwise start a new fetch and store it in `_inflight`, clearing it on settle. The naive `if (_cache === null) _fetch()` pattern races: when several components mount in the same tick they each see an empty cache and each fire their own request. Add an inflight guard to any new singleton hook of this shape.
- **For new boot-time settings, prefer adding to `/settings/bootstrap` over creating a new singleton hook.** The frontend's `primeBootstrap()` (in `src/api/bootstrap.ts`) calls `GET /settings/bootstrap` once after login and pushes each value into the corresponding hook's singleton cache via the hook's top-level `invalidate*(value)` export. Every per-hook GET that fires before bootstrap arrives is a wasted round-trip; every value bootstrap doesn't carry is a duplicate fetch. When you add a settings hook, also add a top-level `invalidate*(value)` export, extend `BootstrapResponse` in `bootstrap.ts`, and call your invalidator from `primeBootstrap()`.

- **Field labels are static — the theme owns label placement, never a call site.** `buildTheme` (`frontend/src/theme/index.ts`) sets `MuiInputLabel.defaultProps.shrink` and `MuiOutlinedInput.defaultProps.notched`, so every outlined field's label sits on the border from mount and the notch never re-opens later. That is the fix for the border striking through a floated label on Safari: MUI opens the notch by flipping the `<legend>` from `max-width: 0.01px` to `100%`, and WebKit does not re-lay out a percentage `max-width` on a legend inside a fieldset in some flex layouts (the multiline input root, a `Stack` parent), so any label that floated *after* mount — a value arriving from `GET /roles/{key}` after the panel rendered, the first keystroke into an empty multiline field, a focus — rendered with the line through it ([mui/material-ui#44988](https://github.com/mui/material-ui/issues/44988), [#46891](https://github.com/mui/material-ui/issues/46891), upstream fix PR #48566 unmerged; fixed here in 2.124.1). It had been patched per field three times before (`TagsAdmin`, `cardDetailUtils`), which is exactly why it kept coming back. Rules: never pin `shrink` / `notched` on a field and never derive a label position from field state (`staticLabels.test.tsx` scans `src` and fails on any pin; the only opt-out is a literal `shrink: false` with a reason); a hand-composed `InputLabel` + `Select` / `OutlinedInput` still passes `label`, because that text sizes the notch; `placeholder` is now visible on an empty field, so write it as a hint, not a copy of the label. Extensions inherit the defaults through core's `ThemeProvider`; the vendor-ops tool in the private repo carries its own theme and mirrors the two lines. Full rule: `frontend/UI_GUIDELINES.md` §3.5.

- **Free text is rendered through `LinkifiedText`; stored HTML through `sanitizeRichHtml`.** Anything a person typed and reads back — a card description, a `text` / `multiline_text` attribute, a comment, a todo, a risk or finding note, a PPM status report, a BPM element's documentation, a survey message, a portal or admin description, the Inventory grid's text cells — goes through `frontend/src/components/LinkifiedText.tsx`, which turns every `http://` / `https://` address into a new-tab MUI `Link` (`rel="noopener noreferrer"`) and renders a **fragment**, so the call site keeps its own `Typography` and the swap is `{text}` → `<LinkifiedText text={text} />`. The tokenizer is `splitLinks` (`lib/linkify.ts`) — http(s) **only** in prose (the `url` field's allowlist, zero false positives); `mailto:` is accepted as an href on a `url`-typed value or a stored anchor but never detected. Stored rich text (ADR / SoAW sections, a portal's card description) goes through `sanitizeRichHtml` (`lib/richHtml.ts`), never a bare `DOMPurify.sanitize`: DOMPurify drops `target` by default, so every anchor came out same-tab; the wrapper autolinks bare URLs in text nodes, sanitises last, stamps `target`/`rel` on http(s)/mailto anchors and strips any other href, on a **private** DOMPurify instance so the SVG-thumbnail sanitisers never inherit the hook. TipTap's `RichTextEditor` configures StarterKit's bundled `link` (`autolink`, `linkOnPaste`, `openOnClick: "whenNotEditable"`, new-tab `HTMLAttributes`) so new links are stored right, but the render-time stamp is the safety net for older content. Two traps: AG Grid's `onRowClicked` is a **native** listener that fires before React's `stopPropagation`, so `InventoryPage` guards on `closest("a")` (and cannot `preventDefault`, which would cancel the link); and a truncated or line-clamped preview must **not** be linkified — a cut URL is a broken link. Model-generated text (TurboLens summaries) is not linkified either. Both are on `window.TurboEA.sdk` since UI SDK 1.29. Full rule: `frontend/UI_GUIDELINES.md` §3.14. Guard tests: `lib/linkify.test.ts`, `components/LinkifiedText.test.tsx`, `lib/richHtml.test.ts`, `features/ea-delivery/RichTextEditor.test.tsx`.

- **Picking an existing card — always use `CardPicker`.** Any dropdown/autocomplete that selects a card from the inventory (relations, hierarchy parent/child, predecessors/successors, the Create-card parent, vendor/Provider linking, ADR card links, BPM element linking, compliance findings, …) must reuse `frontend/src/components/CardPicker.tsx`. It is a single-select MUI `Autocomplete` built on the app-wide `frontend/src/hooks/useCardSearch.ts` engine and gives every picker the same behaviour for free: **browse on open** (lists cards alphabetically with an empty input — never require typing first), filter-as-you-type (server-side via `GET /cards?search=`), and **infinite scroll** (`pageSize` first page, `loadMore()` on listbox scroll). Pass `types` (one key or an array), controlled `value`/`onChange` (`CardOption = {id,name,type}`), `excludeIds` for client-side exclusions (self, ancestors/descendants, already-linked), and `enabled` to gate fetching to when the picker is actually open. Do **not** hand-roll an `Autocomplete` + debounced `/cards?search=` effect, and never gate results behind a `search.length` check — that reintroduces the search-only friction #702 removed. **Picking SEVERAL cards is `CardMultiPicker`** (`frontend/src/components/CardMultiPicker.tsx`) — the diagram Insert-Cards dialog is a ~50-line adapter over it, and so is anything else that needs a basket: type rail, hierarchy, chips, and a selection that survives filtering. `CardScopeDialog` remains the compact single-type scope control a report toolbar opens. The only sanctioned direct `useCardSearch` consumers are `VendorField` (needs a freeSolo "create new Provider" affordance) and the diagram editor's left card sidebar (an infinite-scroll drag source, not a picker). `useCardSearch` is the shared engine — reuse it directly only for those cases; otherwise use `CardPicker` or `CardMultiPicker`. **Never hold a bare id `Set` resolved against its `items`** — that array is replaced on every facet or search change, so picks made before the change vanish at apply time. **Showing a hierarchy is opt-in on `CardPicker` (`hierarchy`) and automatic in `AddRelationsDialog`** (`frontend/src/features/cards/sections/AddRelationsDialog.tsx`) — the third and fourth consumers of `@/lib/cardTree`, added for [#1050](https://github.com/vincentmakes/turbo-ea/discussions/1050), where a name alone does not say which level a capability sits at. Opt-in on `CardPicker` because tree mode loads the whole type up front: right for a dialog the user opened on purpose (`RelationCellPopover`), wrong for `ParentCellEditor`, which mounts on every grid cell edit. The invariant that is easy to "clean up" and must not be: **a picker that hides excluded cards must not hide them inside a tree.** `buildChildIndex` files a card whose parent is absent from the loaded set as a **root**, so dropping an already-linked mid-branch card promotes its children to the top level and rewrites the hierarchy the tree exists to show — and since each pick commits immediately, the row just clicked is the one that would vanish. Render exclusions as inert, greyed context rows instead. Pass `impliedRows: false` wherever a pick is its own row rather than a subtree root.
- **Search boxes: debounce what goes to the server, never a filter over a list the client already holds — and rank the results.** Every search input over cards (or a comparable entity list) follows one shape, and the two halves are keyed off *different* values:
  - **Client-side filtering runs on the RAW input**, so the list narrows on the first character. A list already in memory costs nothing to filter, and keying it off the debounced value just leaves the previous query's rows on screen for the whole debounce window.
  - **Only the server query is debounced** (`useDebouncedValue(value, 300)` — `frontend/src/hooks/useDebouncedValue.ts`, or the `search` argument to `useCardSearch`). That is the one thing a debounce exists to protect.
  - **Rank with `searchRank` / `compareByRank`** (`frontend/src/lib/searchRank.ts`): exact → starts-with → starts-a-word → contains, alphabetical within a tier. These mirror `_search_rank` in `backend/app/api/v1/cards.py` **on purpose** — the client re-ranks the loaded options during the debounce window, so the order must not jump when the server response lands. Change one and change the other; `searchRank.test.ts` pins the contract. `compareByRank` sorts a **non-match last**, so it is safe on a list that was not pre-filtered.
  - Canonical implementation: `CardPicker.tsx`'s `filterAndRank()` wired through `filterOptions={(opts, state) => filterAndRank(opts, state.inputValue)}` — `state.inputValue` is MUI's live, un-debounced value. `AddRelationsDialog`, `InsertCardsDialog` and `CardScopeDialog` follow the same split without MUI's help.
  - **In a hierarchy, rank by best *descendant* rank, not the node's own.** A tree search keeps a match's ancestors for context and those score no-match on their own names, so ordering siblings by their own rank buries the branch holding the best hit. Roll the best rank in each subtree up (`bestRank` in `CardScopeDialog.tsx`) and order each level by that. Where a page already exposes an explicit **Sort** control (the Matrix axes), do **not** reorder by relevance — it would silently override the user's choice; filter only.
  - **Paging helpers count the server's view, not the narrowed one.** `useFillVisible` exists to page past client-side *exclusions* eating page slots (#918); feed it the exclusion-filtered count, never the text-filtered one, or every keystroke looks like an exhausted page and pulls pages for a query about to be replaced.
  - Two sanctioned exceptions, both because the client does **not** hold the full set, so there is nothing to filter instantly: server-backed searches over large collections (the Inventory grid, the global search palette, EOL products, Survey Builder, the Diagrams gallery), and `MatrixReport`'s row/column search, whose 200ms debounce deliberately spares an expensive re-derivation of the visible leaves rather than a request.
