# App settings, seeders, card-type categories, migrations of built-in defaults

> Loaded when you touch `backend/app/api/v1/settings.py`, `backend/app/api/v1/metamodel.py`, `backend/app/api/v1/capability_catalogue.py`, `backend/app/services/seed*.py`, … (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

- **A demo seeder must never infer "have I already run?" from the data it created.** Every `seed_demo*` entry point checks a durable one-shot marker first — `demo_seed_completed(db, SEEDER_KEY)` / `mark_demo_seed_completed` (`backend/app/services/seed_markers.py`), stored per-seeder under `app_settings.general_settings.demoSeeded`. The old pattern — "skip if a row I would have created still exists" — silently turns `SEED_DEMO=true` into *re-assert the demo data on every boot* the moment a user deletes that data. `seed_extras_demo_data` guarded on **comments**, which cascade-delete with their cards, so an install that imported a real landscape and removed the NexaTech cards re-created the three demo diagrams, saved reports, surveys and bookmarks on **every restart**, accumulating a copy each time ([#905](https://github.com/vincentmakes/turbo-ea/discussions/905), fixed in 2.38.2). The legacy data-inference guards are kept only to adopt the marker on pre-existing installs, and each card-independent section additionally skips by natural key so a re-run can never double-insert. `RESET_DB=true` drops `app_settings` with everything else, so a genuine reset still re-seeds. Guard tests: `backend/tests/services/test_seed_markers.py`.

- **A card type's category is a registry key, not free text: the route validates, the importers adopt.** `card_types.category` names a row of `card_type_categories` (`models/card_type_category.py`, migration `156`) by its `key` — the label as first typed, immutable, and for the four built-in layers their historical names, so no card-type row changed when the registry arrived. There is deliberately no FK: an importer writes strings and a dangling value must still render. `POST` / `PATCH /metamodel/types` refuse a category that is not a key (`400 unknown_category`; re-sending a type's *current* value is always accepted, so a pre-registry value cannot block an unrelated edit), while every path that writes a card type without the route calls `card_type_categories.ensure_categories` — the workspace applier (after the bespoke `_apply_card_type_categories`, which runs **before** the card types and on a target row that is `built_in` applies `sort_order` alone, so a bundle cannot repaint a locked default but the layer order it carries survives the transfer), content packs (the same applier) and the platform-migration type pass (`category="Imported"`). The four defaults (`CARD_TYPE_CATEGORIES` in `seed.py`, translated in all 9 locales) are seeded insert-only by `seed_default_categories` and are locked: label, colour, translations and delete answer `400 built_in_locked`; their place in `PUT /metamodel/categories/order` (a permutation of every key) is not. A new or renamed category whose case-folded name matches another row's key **or label** is `409 category_exists` (`is_duplicate`), since after renaming `Foo` to `Bar` a second `Bar` would read as the same layer. Order, colour and translated label come from the registry on **every** surface — `lib/cardTypeOrder.ts` (`orderCategoryKeys`, `categoryDisplayName`, the inventory sidebar and the metamodel graph through `groupCardTypesByCategory`), `ldvLayers` in `features/reports/ldvLayoutShared.ts` (the LDV's lanes and layer boxes), `useCardTypeCategories` (primed by `/settings/bootstrap`) and `categoryLabel` / `useCategoryLabel` — with the four built-in names in `CARD_TYPE_CATEGORY_ORDER` only as the fallback when no registry is to hand; never add another hard-coded list. A type with no category is grouped under the sentinel `UNCATEGORIZED_GROUP_KEY` (`lib/cardTypeOrder.ts`) on every surface — the LDV's `typeCategory` included — never under a literal such as `"Other"`, which an admin may create as a real category; that lane comes last, grey, with the caller's translated label. `normalize_key` refuses that sentinel as a category name (`RESERVED_KEYS`), so no registry row can ever share the lane. The logic lives in `services/card_type_categories.py` so it carries a mutation score. Guard tests: `tests/api/test_card_type_categories.py`, `tests/services/test_card_type_categories.py`, `test_alembic_156_card_type_categories.py`, `test_workspace_io_roundtrip.py::test_a_bundle_cannot_repaint_a_built_in_category` / `test_a_custom_layer_between_two_defaults_survives_import`, `test_extension_content_pack.py::test_allowed_sheets_match_the_teax_cli`, `frontend/src/lib/cardTypeOrder.test.ts`, `features/admin/metamodel/CategoryCombobox.test.tsx`, `ManageCategoriesDialog.test.tsx`.

- **Built-in metamodel default changes need a migration too.** `seed.py` only runs when the relevant row is missing on startup, so editing a built-in card type's `color`, `icon`, `label`, etc. has zero effect on existing installs. If you change a built-in default, add a guarded `UPDATE` migration that only rewrites rows still carrying the drifted-from value (so admin customisations and pre-drift defaults are preserved). See `072_restore_business_process_color.py` for the canonical pattern.

- **A migration that creates a `created_at` / `updated_at` column must declare `server_default=sa.func.now()`.** Every model reads the two stamps from `TimestampMixin` (`models/base.py`), whose server default makes the ORM leave them out of the INSERT and rely on the database. A `create_table` that declares them `nullable=False` without the default therefore builds a table the ORM cannot insert into — and nothing in the test suite notices, because `conftest` builds the schema with `create_all` (default included), never with the migrations, so only *upgraded* installs fail. Migration 149 shipped exactly that on `process_message_flows`: its own backfill wrote `now()` explicitly in raw SQL, so the upgrade sailed through and every publish of a process with message flows then 500'd ([#1133](https://github.com/vincentmakes/turbo-ea/issues/1133), fixed in 2.147.2 by migration `151`; `058` had repaired the same omission on the archlens tables before it). Guard test: `backend/tests/services/test_alembic_timestamp_defaults.py` scans every migration off disk and fails on a timestamp `sa.Column` without `server_default`.

- **`app_settings.general_settings` is a settings row, not a cache — and every write to it is key-scoped.** Every core setting and every extension setting (`ext.<key>.*`) shares that one JSONB blob, so whatever *size* it reaches is paid by every save of any setting: a PATCH that read the row into Python, changed one key and wrote the whole dict back moved the entire blob twice. The three reference catalogues fetched from PyPI (capabilities, processes, value streams — megabytes each) were cached inside it, so once one had been fetched every settings save on the instance took hundreds of milliseconds to seconds while the inventory stayed instant; measured at 21 ms → ~500 ms for one extension's `PUT …/settings` and the same slope on core's own `PATCH /settings/*`, reported at 3.5 s with every extension installed (fixed in 2.133.1). Two rules follow: **a cache gets its own table** — `catalogue_cache` (`models/catalogue_cache.py`, `catalogue_common.get_cached_remote` / `set_cached_remote`; migration `146` moves whatever an install already cached and strips it from the blob; deliberately not part of workspace transfer) is the shape for anything refreshed from the network, and nothing else multi-megabyte belongs in `general_settings`; and **the extension settings bridge reads and writes by key in SQL** — `get_settings` selects `general_settings['ext.<key>.<name>']`, `set_settings` is one server-side `||` (`jobs.py`), which also stops two extensions' read-modify-writes clobbering each other's keys. Guard tests: `tests/services/test_extension_settings.py::TestKeyScopedInSql`, the catalogue service tests. Core's own `PATCH /settings/*` handlers still do a Python read-modify-write; that is acceptable only because the blob is now small — do not put anything large back.

- **Static-asset redirects must carry `Cache-Control`.** Any `RedirectResponse` whose target is a static file (the default logo, default favicon, etc.) must include `headers={"Cache-Control": "public, max-age=300"}`. The static target is already cached by nginx, but an un-cached 302 means every page navigation re-does the round-trip.

- **Macro Capabilities are an additive tier above L1** in the Capability Catalogue (consumed from the `turbo-ea-capabilities` wheel ≥ `2026.5.11.505`). Cards land with `type=BusinessCapability`, no subtype, `attributes.capabilityLevel = "Macro"`, and `attributes.catalogueId` prefixed `MC-`. The hierarchy depth limit relaxes from 5 to 6 for macro-rooted chains (`Macro → L1 → L2 → L3 → L4 → L5`); `_sync_capability_level` and `_check_hierarchy_depth` in `cards.py` detect macro roots by walking the parent chain. Macros never match existing cards by name — only by `catalogueId` — to avoid colliding with customer-named cards. Injection of macros into the catalogue payload happens in **one place** (`_resolve_active_catalogue` in `capability_catalogue_service.py`) so the GET endpoint and the import path see the same flat list with rewritten `parent_id`s — otherwise the auto-relink of pre-existing L1s silently no-ops.
