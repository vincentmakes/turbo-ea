# Card health flags and EOL coverage

> Loaded when you touch `backend/app/services/card_flags.py`, `backend/app/services/eol_service.py`, `backend/app/api/v1/eol.py`, the EOL and Data Quality reports, … (full list in the frontmatter). Split from `card-flags-cost-eol.md`; the cost rules are in `cost-fiscal-year.md`.

- **A cross-cutting card health flag has exactly one definition, in `backend/app/services/card_flags.py`.** "Orphaned" and "stale" are each read by three surfaces — an inventory filter (`GET /cards?<flag>=true`), a Data Quality KPI tile with its drill-down panel (`GET /reports/data-quality` + `?scope=`), and a deep link from one to the other (`buildInventoryFlagUrl`) — so if the definitions diverged, clicking a count of 37 would land on a grid showing something else. The same module owns **EOL coverage** (added 2.122.0 for [#1065](https://github.com/vincentmakes/turbo-ea/discussions/1065)): `has_eol_coverage` is an endoflife.date link (`attributes.eol_product` *and* `eol_cycle`) **or** a manual `lifecycle.endOfLife` date — the manual date is the company's own decommission date, which the EOL report has always accepted in its own right, so "not recorded" has to mean neither. Its consumers are the EOL report's `missing` rows and the Data Quality report's coverage chart — which exists in **both forms**, counted in Python for the dashboard totals and queried in SQL by `eol_bucket_condition` for the chart's drill-down panel, so `tests/services/test_eol_coverage.py` runs the two over a matrix of awkward JSONB shapes and pins them equal. Write those SQL negations **positively** (`_jsonb_absent`): `attributes->>'eol_product'` is SQL NULL for an absent key *and* for JSON null, and `NOT NULL` is not TRUE, so `not_(and_(...))` silently drops exactly the cards a "nothing recorded" filter exists to find. **Which types track End of Life is the type's own `eol` section toggle** (Card Layout editor, `section_config.eol.hidden`), decided by `type_tracks_eol` in `card_flags.py` and mirrored by `typeTracksEol` in `frontend/src/lib/eol.ts`: an explicit boolean wins; absent (or a legacy bare boolean / a config with no `hidden`), the shipped default `DEFAULT_EOL_TYPES` (Application, ITComponent) applies — so no migration was needed and every new custom type starts hidden. Before upstream 2.188.0 the list was hard-coded and the card section rendered nothing elsewhere while the layout switch read "visible". The one toggle drives every EOL surface: the card section and create-dialog link, `/reports/eol`, the data-quality coverage chart and drill-down, the dashboards' `eol_*` flags and `eol_coverage` dimension (`ResolvedQuery.eol_types`), the inventory column/filter (`eolColumnApplies(types, keys)`), bulk linking, `/eol/card-status`, `GET /eol/types` and the extension SDK's `get_eol_status`. Callers load `eol_type_keys(db)` once per request and pass it as `eol_types=` to `eol_bucket_condition` / `eol_coverage_key` — never re-add a fixed list. The Card Layout editor shows the **effective** state on the eol row and writes an explicit `hidden` when toggled. Hiding EOL on a type never touches its cards' `eol_*` attributes or lifecycle dates; the EOL report's IT Component → Application impact still names applications when Application itself stops tracking EOL. `frontend/src/lib/eol.ts` also owns the per-status colours the EOL report and the inventory column share. Resolving a *status* (as opposed to coverage) is an outbound call to endoflife.date, so it lives in `backend/app/services/eol_service.py` behind a 30-minute per-product cache, and `GET /eol/card-status` commits its session before calling it. Guard tests: `backend/tests/services/test_eol_coverage.py` (incl. `TestWhichTypesTrackEol`), `tests/api/test_reports_eol.py`, `tests/api/test_reports_extended.py`, `tests/api/test_eol.py::TestEolTypesFollowTheSectionToggle`, `frontend/src/lib/eol.test.ts`, `CardLayoutEditor.test.tsx` ("End of Life follows the type's real state").
- **A custom EOL product is linked through the same two attributes as an endoflife.date one: `eol_product = "custom:<key>"` + `eol_cycle`** (`eol_custom_service.py`). The `custom:` prefix cannot collide with an upstream slug, so `has_eol_link`/coverage and `eol_service.resolve_eol_statuses` treat it with no special case. Deleting a product or cycle that cards still link is 409 `cards_linked`; `switch_to_upstream` fetches upstream cycles before touching the session and moves only cards the caller can read (a hidden card keeps its link, and the product). Service functions never commit — the route owns the transaction. Routes `/eol/custom-products*` (`eol.view` / `eol.manage`). Guard tests: `tests/api/test_eol_custom_products.py`, `tests/services/test_eol_custom_service.py`.
