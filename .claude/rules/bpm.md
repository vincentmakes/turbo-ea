# Business Process Management (BPMN modeler, parser, element links)

> Loaded when you touch `frontend/src/features/bpm/**`, `backend/app/services/bpmn_*.py`, `backend/app/services/process_*.py`, `backend/app/services/element_relation_sync.py`, … (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

## BPM (Business Process Management)

### Architecture
- **BusinessProcess** card type with fields: process type, maturity level, automation level, risk level, frequency
- **BPMN 2.0 Editor**: bpmn-js integration with 7 starter templates (incl. a two-pool `collaboration` one)
- **The modeler's element set is bpmn.io's — extend it with a bpmn-js module, never narrow it with CSS.** `BpmnModeler.tsx` loads, in one lazy chunk: the colour picker, `bpmn-js-create-append-anything` (the searchable **Create element** / **Append element** menus, `N` / `A`, which is how every advanced element — message/timer/signal/error/escalation events, transactions, event sub-processes, call activities, send/receive tasks, data objects — is reached without a wrench detour), and `bpmn-js-properties-panel` with the **plain BPMN provider only** (never the Camunda/Zeebe ones: this is an EA tool, not an execution engine). The panel is what lets a message event name the `bpmn:Message` it refers to, and it is the only UI that can author an element's `documentation` — which the parser has always extracted. The old Simple/Full toggle was CSS that hid six `[data-action]` palette entries; the create menu reaches everything anyway, so hiding entries only ever meant lying about the element set (removed in 2.145.0). Dark mode: the panel is themed entirely by `--bio-*` tokens declared on `.bio-theme-parent` with **light values only and no dark variant**, so `bpmnPropertiesPanelSx(mode)` (`bpmnStyles.ts`) redefines the surface/text/border tokens on the container — the sanctioned override path, not a per-rule patch. The create/append menus render inside `.djs-popup` / `.djs-context-pad`, which `bpmnCanvasSx` already pins for #770, so they need no rule of their own. Guard tests: `bpmnStyles.test.ts`.
- **Element Extraction**: `bpmn_parser.py` extracts tasks, events, gateways, lanes, **data artefacts and message flows** from BPMN XML. Three rules it encodes: an event records its **sub-type** (`event_definition_type`: `message`, `timer`, `signal`, `error`, …, the first `*EventDefinition` child's tag minus the suffix) and resolves `messageRef` / `signalRef` / `errorRef` / `escalationRef` against the root `bpmn:message` / `signal` / `error` / `escalation` elements into `definition_name` (an error with no name falls back to its `errorCode`; send/receive tasks resolve their own `messageRef`) — without it a message start event and a timer start event were the same row. **Data artefacts are extracted but not ordered**: `dataObjectReference` / `dataStoreReference` (`ARTEFACT_TYPES`) take no part in `order_flow_nodes` and are appended after the last flow node, because nothing flows into them and a node with no predecessor ranks as a *source* — a data object would float to the top of every element table. And `parse_bpmn()` returns `ParsedBpmn(elements, message_flows)` while `parse_bpmn_xml()` stays a thin wrapper returning the elements alone, because migration 138 imports it. The frontend mirror is `features/bpm/elementTypes.ts` (icons + `elementTypes.*` / `eventDefinitions.*` i18n keys + `ARTEFACT_TYPES`), rendered by the one `ElementTypeChip` — a raw `element_type` string must never reach the screen again.
- **The two writers of the derived rows share one helper.** `PUT /diagram` (`bpm.py`) and the approve/publish step (`bpm_workflow.py`) both re-parse the XML and upsert; the upsert was duplicated verbatim in both, so a new parser column had to be added in four places. `services/process_element_sync.py` (`sync_process_elements` / `sync_process_message_flows`, flush never commit) is now the single copy: rows are matched on `bpmn_element_id`, EA links on surviving rows are **kept** (an element's Application link, a message flow's `interface_id`), parser-derived columns are **always** rewritten, and rows for elements no longer in the XML are deleted. A message flow's Interface link is informative like a step's Organization links — `element_relation_sync.py` mints no relation from it. Guard tests: `tests/services/test_process_element_sync.py`.
- **Any step can link to the Business Process it hands over to; the reference is the card UUID.** BPMN's one construct for "this step is another process" is `bpmn:CallActivity`, and its `calledElement` is a free string — a BPMN process id (`Process_1`) collides across diagrams and cannot be resolved, so the modeler writes the **BusinessProcess card UUID** there instead. BPMN has no such slot on a plain task, so every other flow node carries the same UUID in the Turbo EA extension attribute **`turboea:processRef`**, declared by a moddle descriptor (`frontend/src/features/bpm/turboeaModdle.ts`, `extends: ["bpmn:FlowNode"]`) registered through the modeler's `moddleExtensions` — that is what makes it typed on `updateProperties`, undoable, emitted with its own `xmlns:turboea` by `saveXML` and read back by `importXML`. **The reference rule lives in one place per side**: `ExtractedElement.process_reference` (`bpmn_parser.py`) and `processRefOf` (`calledProcess.ts`) both mean *a call activity's `calledElement` when set, else `turboea:processRef`* — the fallback is what keeps a link alive when a linked task is morphed into a call activity, since bpmn-js's replace copies FlowNode properties across. Writing is the mirror image (`processRefProperties`): a call activity gets `calledElement` and loses `processRef` (two references on one shape would be two truths), every other step gets `processRef`, and a clear drops both. The namespace string is pinned on both sides by `test_bpmn_parser.py::TestProcessRef::test_namespace_matches_the_modeler_extension`, which reads the descriptor off disk: get it wrong and the attribute the modeler writes is simply invisible to the parser, with no error anywhere. `sync_process_elements` resolves the effective reference into the fifth EA link, `business_process_id`, with a fixed precedence: **the XML wins** when the value is the UUID of an ACTIVE BusinessProcess other than the process itself (`resolve_process_references`, one query per diagram); a value that does not resolve — a foreign reference from another tool, or nothing — **keeps a link the user made** in the element table, like every other link; and a **data artefact** (`ARTEFACT_TYPES`) is not a step, so it holds no link at all and loses one it had. Inside a **draft** that order is inverted — `_apply_draft_link` lets what the user set there win, the XML being only the fallback; see the next bullet, which owns the rule for all five links. `validate_process_link` (ACTIVE BusinessProcess → 404, self → 400) is the one validator behind both write paths (`update_element` and `update_draft_element_link`), and both refuse an artefact. The relation it mints is the built-in `relProcessCalls` (*calls* / *is called by*, seeded and upserted by key on boot like every relation type, so it needed no migration; migration `150` adds the two columns and backfills from the stored XML), through `ELEMENT_LINK_RELATION_MAP` in `element_relation_sync.py` — the first **self-pair** in that map, which is why `sync_element_relations` now skips `target_id == process_id`. `element_link_ids()` / `ELEMENT_LINK_KEYS` are the one place the write paths collect link ids from, and the legacy `PUT /diagram` save also mints the relation for XML-resolved links, since there the XML *is* the link. Nobody types an id: the frontend has **three doors to one picker** (`features/bpm/calledProcessModule.ts`, a didi module built around a `bridge` object the React side owns) — the **Linked cards** panel group's Business Process row and the context pad's **Link cards** menu, both shared with the four card links and described in the next bullet, plus a `commandStack.shape.create.postExecuted` listener that opens the picker the moment an unlinked **call activity** is placed — deliberately that shape alone, and deliberately the process kind alone, since it is the one BPMN shape whose meaning *is* another process and a prompt on every task drop would be noise. That listener asks the **bridge** as well as the shape (`bridge.links[elementIdOf(shape)]?.business_process`), because a link made in a table leaves nothing in the diagram to check and re-placing such a shape would otherwise prompt over a link that exists. (The panel provider sits at priority 500, i.e. after the built-in 1000; the entry is a Preact component in `CalledProcessEntry.ts`, authored with `h()` from `@bpmn-io/properties-panel/preact` and never a `.tsx` file, because `@vitejs/plugin-react` would wrap it in React's Fast Refresh runtime.) The pick is a **dual write** — `modeling.updateProperties` (undoable, trips autosave) *and* the draft link through the API, because this one link has two stores and both are read by something; names are resolved after import with `fetchCardsByIds` and pushed into the panel with `eventBus.fire("propertiesPanel.providersChanged")`, the one public hook that re-runs every provider. Every rendering of the link — the **Business Process** column chip (`ProcessFlowTab`, a dash on an artefact row like the other step links), the viewer badge and popover chip, the navigator step chip — drills down to `/cards/{id}?tab=1` (`calledProcessPath`); the portal publishes `called_process_name` only. The process map's House has **no process↔process bucket**, so `relProcessCalls` shows in the generic Dependencies view, not there. Guard tests: `tests/api/test_bpm_called_process.py`, `test_bpmn_parser.py::TestProcessRef`, `test_process_element_sync.py::TestCalledProcess`, `test_element_relation_sync.py`, `frontend/src/features/bpm/calledProcess*.test.ts`, `CalledProcessEntry.test.ts`.
- **A step's five card links are one set, wherever they are edited — and inside a draft, what the user set there wins.** A step carries the same five links in the modeler and in the tables: Business Process, Application, Data Object, IT Component and Organizations. They have two stores, and that is what made them drift: the **process** link lives in the diagram XML (`calledElement` / `turboea:processRef`, above) *and* in the draft, because BPMN has a construct for it that other tools read; the **four card links** live only in `ProcessFlowVersion.draft_element_links` (a draft) or the `ProcessElement` rows and the `ProcessElementOrganization` junction (published). The modeler used to read the XML alone, so a process linked in the steps table was simply invisible on the canvas. One precedence rule now answers "what is this step linked to?" and **three places apply it identically**: `get_draft_elements` (what the pre-link table and the modeler read), `_apply_draft_link` (what publishing writes into the rows) and the modeler, which reads the server's answer rather than re-deriving one. The rule: **inside a draft, an explicit draft link wins — key present, including a deliberate clear — and the XML reference is the fallback** for a key that is absent. The inversion matters: an XML-wins rule made a user's own unlink un-doable, since the attribute the modeler had written kept putting the link back.
  - **An explicit clear is stored, never deleted.** `update_draft_element_link` writes `None` for an emptied FK and `[]` for emptied `organization_ids`; deleting the key instead means "I said nothing", which falls through to the XML or to the seeded value. That was a live bug on Organizations: clearing them in a draft never took at publish, because `approve_version` skips an element whose link lacks the key.
  - **A draft is a snapshot, and creating one is the sync point.** `create_draft` seeds `draft_element_links` from the base version's, or — when the base is published, whose links were consumed into rows — from the live rows via `_links_from_live_elements`. So a published flow stays approved while its links are edited in its own elements table ("metadata on top", no re-approval), and the next draft made from it starts from those links. An **existing** draft keeps its own snapshot and does not follow later published-table edits; that is the point of a snapshot, not a gap to close. `approve_version` therefore sets `draft_element_links = None` once it has applied them, or a later draft would clone consumed pre-links over the fresher rows.
  - **`linkKindsFor` (`calledProcess.ts`) is the one gate** on which links a shape offers, and every surface asks it: the panel group, the context-pad entry and the popup menu. A flow node that is not a label offers all five; a **data artefact** (`DataObjectReference` / `DataStoreReference`) offers Data Object alone, matching the table; with no draft open (`versionId` absent) only the process link is offered, because the other four would have nowhere to go. A pool, a sequence flow and an external label offer none, and a surface given none contributes nothing at all rather than an empty group.
  - **The modeler reads the server, and writes both stores for the process kind.** `loadDraftLinks` fetches `…/draft-elements` into `bridge.links` and fires `propertiesPanel.providersChanged` (the one public hook that re-runs every provider); the rows render that map, falling back to the diagram's own reference only for a shape the server has not seen yet, i.e. one placed since the last autosave. `writeLink` updates the map optimistically, PUTs, and reverts on failure. A **cleared** link therefore reads as cleared even while the diagram still carries the attribute — which is why the "References X" hint is gated on the reference being *foreign* (`!isCardUuid`) rather than merely present.
  - **The canvas shows a step's links as one dot per card type, from one renderer — never as names.** `linkDots.ts` is shared by the read-only viewer and the editor (`linkDotsFor` → `linkDotsHtml`, `LINK_DOTS_OVERLAY_TYPE`), so a draft looks on the canvas the way it will once published; the two name badges the viewer used to draw made a linked diagram unreadable, so names live in the click popover, the Linked cards panel and each dot's hover `title` only. Colours come from the metamodel through `useLinkTypeColors` (memoised on `types`, never on the per-render `getType` closure — a host keys its diagram-import effect on the object) with the seeded `LINK_TYPE_COLORS` as the fallback, the `CALLED_PROCESS_COLOR` rule generalised: the viewer also renders inside account-less portals, which cannot read the metamodel, so `BpmnViewer` takes `typeColors` as a prop that the app supplies (`ProcessFlowTab`, the navigator's in-app `source.typeColors`) and a portal leaves unset. "Under the name" is `linkDotPlacement`: on the **external label** when the shape has one (events, gateways, artefacts — attached to the label element, so it moves with it), else at the bottom of the shape; diagram-js reads `position.bottom` as the overlay's *top* edge measured from the element's bottom, hence `14` for an 8px row inside a shape and `-2` under a label — and `-3`, i.e. hanging just under the box, on a shape whose bottom centre already carries a BPMN marker (`hasBottomMarker`: call activity `⊞`, collapsed sub-process `+`, ad-hoc `~`, loop / multi-instance): the marker owns the bottom and a two-line name the middle, so there is no free row inside. The editor redraws its overlays (`overlays.remove({ type })` then add) from `bridge.links` in `refreshLinkDots` on load, on every write and revert, and on `commandStack.changed` — a label appearing when a step is first named is a new element the dots must move onto — with the diagram's card-uuid reference as the fallback for a shape the server has not seen. Guard tests: `linkDots.test.ts`, `useLinkTypeColors.test.ts`.
  - **Context-pad wiring.** One pad entry opens diagram-js's own popup menu (`LINK_MENU_ID`), so it inherits the replace menu's look; five pad entries would not be readable. Two traps: position the menu from `canvas.getContainer().querySelector(".djs-context-pad").getBoundingClientRect()` — `contextPad.getPad()` is deprecated in diagram-js 15 and `console.warn`s on every call — and **call `popupMenu.close()` in the action**, because `PopupMenu.trigger` only runs the action; the replace menu gets away with it only because a command closes the menu for it, and ours opens a dialog under an open menu.
  
  Guard tests: `backend/tests/api/test_bpm_called_process.py`, `test_bpm_element_organizations.py`, `test_bpm_workflow.py`, `frontend/src/features/bpm/calledProcess.test.ts`, `calledProcessModule.test.ts`, `CalledProcessEntry.test.ts`, `CardLinkEntry.test.ts`.
- **`sequence_order` is causal, not an iteration artefact.** The element tables (Pre-link Elements, published Elements, the Process × Organization matrix) render the parser's order positionally, so it *is* the reading order of the process. `bpmn_flow_order.order_flow_nodes` computes it: build a graph from `sequenceFlow` + `messageFlow` + `boundaryEvent[@attachedToRef]`, condense strongly connected components (so a rework loop is one causal level and never strands what follows it), rank by **longest** path over the condensation, and break every tie on document order. Four things look simplifiable and are not: (1) a greedy topological walk is *not* equivalent — it emits a short branch's tail before a long branch's head, which gets a two-pool conversation wrong; (2) sub-processes are solved as their own containers and spliced in after their parent — a flat "container → child" edge lets a sibling interleave into the sub-process body; (3) the weakly-connected-component key is what keeps two unrelated processes in one file as separate blocks instead of interleaving them rank by rank; (4) containers are sub-processes only, never `<process>` — grouping by process would order the pools of a collaboration one after another and lose the message-flow interleaving. Tarjan is iterative on purpose (a 2000-node chain is a real model), and it already emits components in reverse topological order, which is why no separate topological sort is needed. Ordering is derived entirely from the stored XML, so a change here warrants a backfill migration for already-published processes — see `138_backfill_process_element_order.py` ([#978](https://github.com/vincentmakes/turbo-ea/issues/978)).
