# Extension Store: signing, licensing, content packs, field contributions, the store tab

> Loaded when you touch `backend/app/services/extensions/**`, `backend/app/core/extension_signing.py`, `backend/app/api/v1/extensions.py`, `backend/app/api/v1/adr.py`, … (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

### Extension Store Conventions

The **Extension Store** (Admin → Extensions) installs vendor-signed, licensed extensions — content packs, backend plugins, and UI plugins — without changing core ("clean core"). Delivery is file-based (signed `.teax` bundle + signed license text), fully offline/air-gapped capable. The `teax` CLI (build/sign/verify bundles + licenses) lives in `scripts/extension-tools/`; the **extension authoring guide, signing/key custody, release pipeline, and license-issuance runbook live in the vendor's private extensions repo** (not in this public repo). The customer-facing page is `docs/admin/extensions.md`.

**Module layout**: `backend/app/core/extension_signing.py` (Ed25519 verify + baked-in `DEFAULT_VENDOR_PUBLIC_KEY`), `backend/app/services/extensions/` (`license.py`, `registry.py` in-memory singleton, `gate.py` `require_extension()`, `bundle.py` `.teax` verifier, `installer.py`, `content_pack.py`, `sdk.py`, `loader.py`, `migrations.py`, `jobs.py`, `startup.py`), routes in `backend/app/api/v1/extensions.py`, admin UI `frontend/src/features/admin/ExtensionsAdmin.tsx`, UI host `frontend/src/lib/extensionHost.tsx` + `ExtensionRoutesOutlet.tsx`. Tables: `extensions`, `extension_licenses`, `extension_schema_versions`, `extension_installs` (migration 121). Uploads land in `data/extension_installs/`, installed extensions in `data/extensions/{key}/` — both persisted by the `backend_data` docker volume.

**Invariants — do not weaken:**

- **Provenance is anchored to the baked-in vendor keys.** Bundles and licenses verify against the vendor keys baked into `extension_signing.DEFAULT_VENDOR_PUBLIC_KEYS` (`trusted_public_keys()`), and nothing else. Shipping your own extensions means forking — replace the keys in that map and rebuild. Tests inject a throwaway key with `tests/teax_helpers.trust_test_key()`, which replaces the baked map in-process (the same seam a fork edits). The loader re-verifies every installed bundle's `manifest.sig` at each boot, so files dropped on the volume are never trusted. Signatures cover exact bytes (raw `manifest.json`; base64-decoded license payload) — never introduce a JSON-canonicalization step.
- **Two independent gates**: signature = may it be installed/loaded; license entitlement (per-extension, expiry + grace, default 30 days) = may it run. Lapse ⇒ soft-disable via `require_extension` (404 not installed / 403 disabled-or-unlicensed) and per-tick job checks; **data is never deleted** on lapse or uninstall. One **active license per instance** — `persist_license` supersedes the previous row, so `PUT /license` refuses with 409 `entitlement_downgrade` (confirmable via `confirm: true`) any license that omits entitlement keys the current license still covers as active/grace (`_apply_license_text` in `api/v1/extensions.py`); the auto-renew path never shrinks coverage on its own (`_should_apply` in `license_refresh.py`).

- **Content packs go through `workspace_io.apply_selected`** (the public facade) and reuse the workspace-transfer engine + guarantees; allowed sheets exclude `Users`/`Roles`/`Settings`. `ext_*` tables are excluded from workspace transfer. A pack may also ship the `Surveys` sheet (but never `SurveyResponses`): `build_content_bundle` clamps every pack survey to `status="draft"` with cleared `sent_at`/`closed_at` (`_enforce_survey_draft`), so an install can never send a survey / email subscribers — the survey lands as a reviewable draft with its fields pre-selected in the builder. Keep `CONTENT_ALLOWED_SHEETS` (`content_pack.py`) in sync with `CONTENT_SHEETS` in `scripts/extension-tools/teax.py`.
- **Manifest field-section contributions (`metamodel` capability) are the ONLY way an extension adds fields to an EXISTING card type.** A content-pack `CardTypes` row whole-column-overwrites `fields_schema` (fine for pack-owned new types, destructive for existing ones), so a manifest may instead declare `"capabilities": [..., "metamodel"]` + `"metamodel": {"field_sections": [{card_type, section, columns?, translations?, fields: [...]}]}` and `apply_field_contributions` (`backend/app/services/extensions/field_contributions.py`) MERGES the section into the target type — stamped `"ext": "<key>"` on section + fields, idempotent, never touching admin/core fields (a conflicting field key is skipped, never hijacked). Contributed field types must be built-in or `ext.{key}.*` (validated in `bundle.py` + `teax lint`). The same manifest block may also carry `"subtypes": [{card_type, subtypes: [{key, label, translations?, color?}]}]` — **additive subtype contributions to existing card types** (`apply_subtype_contributions` / `remove_subtype_contributions` in the same module, same stamp/merge/strip lifecycle and never-hijack rule; card `subtype` values survive removal and rendering degrades to the raw key). A contributed section is also given a place in `section_config["__order"]` (`_place_section`, run on **every** apply), at the position the contribution's optional **`"placement"`** asks for — `start` / `end` / `before:<anchor>` / `after:<anchor>`, anchors being the built-in section keys (`SECTION_ANCHORS` in `bundle.py`, mirrored in `teax.py`, pinned by `test_teax_grants_lint.py`; `custom:N` is deliberately not addressable, being a positional index that names a different section on every install). **Core supplies the default `before:relations` and no opinion beyond it** — where a contributed section belongs is a property of what the extension is, not of the platform, and "just above Relations" is right for a regulatory attribute block and wrong for a post-decision summary meant to read last. An anchor the target type does not carry (`eol`, `successors`) degrades to the default rather than to the bottom, since that is the outcome the author was avoiding. Omitting the key keeps the pre-`placement` behaviour, so bundles built before it exist are unaffected, and an older core ignores it (the manifest check is required-keys-only, not reject-unknown): `custom:N` is the *positional* index into `fields_schema` minus `__description`, and both order builders append any `custom:N` missing from a stored order to the very END — below Relations, unlike `tags`/`successors`, which card detail splices in before it. **The stored order is the only truth** — the fix belongs here and NOT in the renderer, because the Card Layout editor has its own builder (`getSectionOrder`, `CardLayoutEditor.tsx`) that appends where card detail would splice, so compensating in one of them makes the editor and the card disagree about a position neither has stored. Writing the key instead leaves both simply reading it. Two guards, not a creation check, are what make an every-apply write safe: it **no-ops when no `__order` is stored** (that path already renders custom sections high, and writing one would freeze a layout the admin never chose) and it **no-ops when the key is already present**, so a re-apply never moves a section anyone has positioned — including one deliberately dragged below Relations. Running it only on first creation instead left every pre-existing install stuck at the bottom forever, since a re-apply finds the section and skips the creation path. Removal re-indexes the surviving `custom:N` keys (`_reindex_section_order`) from a `kept_flags` list the removal loop builds — **not** by comparing the two schemas, because that loop rebuilds every edited section as a NEW dict, which makes identity comparison read them all as removed. Lifecycle mirrors content-pack soft-hide: install/enable/update re-merge (updates re-sync ext-owned fields and clean retargeted types via the stamp scan, preserving admin-added fields inside the section); disable/uninstall strip the stamped fields **but never the values in `cards.attributes`** — re-enabling restores the section and every value reappears. License lapse does NOT remove contributions (lapse ≠ deactivation; rendering is never gated). Data-quality is recomputed for affected types on apply/remove. Tests: `tests/services/test_extension_field_contributions.py`.

- **ADR extension attributes bag** (`architecture_decisions.attributes`, migration 122). ADRs are **not cards**, so extensions cannot extend them via the `metamodel` field-contribution capability; instead they stash data under `ext.<key>.*` top-level keys in this JSONB bag. `update_adr` shallow-merges the bag, **rejects non-`ext.*` keys** (core owns no native ADR attributes), and a key set to `null` is deleted. It is **frozen automatically once the ADR is signed** (`update_adr` 403s on signed decisions) and **carried into revisions + duplicates**, so figures the signatories approved stay accurate. Surfaced in both `_adr_to_dict` and `_adr_to_summary` (so the list endpoint can power a dashboard without N+1). The column transfers via workspace-transfer introspection (ADR is an `ENTITY_SECTION`); user ids stored *inside* the bag are **not** email-remapped on cross-instance transfer (same caveat as card `attributes`) — a portable extension stores emails or its own `ext_*` tables. Paired with the `adrPanels` (authoring) + `adrExportSections` (DOCX) UI points.
- A broken extension must never block core boot or blank the SPA — quarantine + surface on the admin page.
- **Instance-bound licensing.** Every install mints a checksummed **instance ID** once (`TEA-XXXX-XXXX-XXXX`, Crockford base32 + weighted mod-32 check char — `app/services/extensions/instance_id.py`, persisted in `app_settings.general_settings.instanceId` by `ensure_instance_id()` at startup, surfaced by `GET /admin/extensions/instance` and a copy-chip on ExtensionsAdmin). Licenses carry `payload.instance_id` and core **binds** on it: `_apply_license_text` 400s on mismatch (paste, claim, and auto-renew alike), the registry soft-disables a stored mismatched license at load (`license_problem` → error banner; data untouched), and an **unbound** license is accepted only when `ENVIRONMENT=development` (`teax sign-license` requires `--instance-id`, so production files always carry one). The in-app Buy button appends the ID to Stripe's `client_reference_id` (`<claimToken>-<TEA-…>`, parsed off the end by the store webhook); the renew request sends `instance` alongside the renewal key. **Two invariants:** (1) the ID *identifies*, claim tokens / `renewal_key` *authenticate* — knowing an ID must never allow fetching a license; (2) the ID **travels with workspace transfer** (never add `instanceId` to the secret-strip lists) so host migrations keep licenses valid — binding is to the ID, not hardware. Full design + vendor re-key/self-issue tooling: the private extensions repo's `docs/plans/instance-id-licensing.md`.
- **Multi-key trust**: `DEFAULT_VENDOR_PUBLIC_KEYS` (key_id → base64 key) in `extension_signing.py` is the set of trusted vendor keys; `verify_with_trusted()` selects by the envelope/manifest `key_id` and falls back to trying every trusted key (so pre-`key_id` envelopes still verify). This lets a vendor sign licenses with a key separate from the one used to sign bundles, and lets keys rotate without a format change. `teax pack --key-id` stamps the id into the manifest.
- **In-product Store tab = read-only proxy over public static files — never a store connection, and never configuration.** The catalogue URL (`EXTENSION_STORE_URL` in `config.py`) is a **hard code constant, deliberately NOT an env var** — the store is part of the product on every install, with no opt-in/opt-out knob (repointing it means forking, same posture as the trusted vendor keys; a source-level test in `test_startup.py` guards against reintroducing an env lookup). `GET /admin/extensions/store/catalog` proxies + annotates it (installed version, entitlement state, update available) and `POST /admin/extensions/store/install` downloads the bundle server-side into the SAME verify → dry-run preview → apply pipeline as a manual upload (`_persist_upload` + `_verify_and_preview_job`). Bundle downloads are restricted to the store origin (SSRF guard). Every catalogue item carries a `category` slug from a small fixed vocabulary that lives on the **frontend** (`STORE_CATEGORIES`, `storeCategories.ts`) with an i18n label per slug; the backend only shape-checks it (`_sanitize_category`, the tag slug regex), and the Store tab renders the items as ordered sections with an **Other** section for any slug it does not know — so a newer catalogue can never hide an item from an older core, and a catalogue with no categories at all still renders the flat grid. There are NO accounts, tokens, redeem codes, or online activation — bundles are inert without a signed license, payment happens in a new browser tab via the catalogue's `payment_link`, and the license is still pasted as a file on the Installed tab. Air-gapped instances need nothing: an unreachable store degrades to a friendly hint and the file-based flow is always fully functional. Anything about how licenses are sold/distributed commercially lives outside this repo, in the vendor's private extensions repo.
