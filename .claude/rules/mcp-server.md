# The MCP server and the mutation-batch ledger

> Loaded when you touch `mcp-server/**`, `backend/app/api/v1/mutation_batches.py`, `backend/app/services/mutation_batch_service.py` (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

### MCP Server Conventions
- The MCP server lives in `mcp-server/` — a separate Python package (`turbo-ea-mcp`) with its own `pyproject.toml` and Dockerfile.
- It provides AI tool access to EA data via the [Model Context Protocol](https://modelcontextprotocol.io/) (FastMCP library).
- **Two transport modes**: HTTP/SSE (production, via Docker `--profile mcp`) and stdio (local testing with Claude Desktop).
- **Authentication**: In HTTP mode, users authenticate via OAuth 2.1 delegated to the Turbo EA SSO provider. The MCP server resolves OAuth tokens to Turbo EA JWTs. In stdio mode, `TURBO_EA_EMAIL`/`TURBO_EA_PASSWORD` env vars are used for direct login. **Redirect-URI validation is enforced**: clients register their `redirect_uris` via RFC 7591 dynamic registration (`POST /oauth/register`), the URIs are persisted in `OAuthStore.clients`, and `authorize()` refuses — with a direct 400, never a redirect — any request whose `redirect_uri` is not an exact match of a registered URI for that `client_id`; the token exchange re-checks `redirect_uri` against the one the code was issued for. **Never redirect an unvalidated `redirect_uri`** — doing so was the auth-code-exfiltration flaw fixed in 1.64.4 (CWE-601/346). Operators fronting the server with a fixed, non-registering integration can whitelist static redirect URIs via `MCP_OAUTH_ALLOWED_REDIRECT_URIS`.
- **Read tools** (32, across eight clusters). **Cards & metamodel**: `search_cards`, `get_card`, `get_card_relations`, `get_card_hierarchy`, `list_card_types`, `get_relation_types`, `resolve_card_refs` (name-to-UUID pre-check), `analyze_impact` (dependency blast-radius for a proposed change). **Dashboards**: `get_dashboard`, `get_landscape`. **GRC (Risk Register)**: `list_risks`, `get_risk`, `get_risk_metrics`, `get_card_risks`. **GRC (Compliance)**: `list_compliance_findings`, `get_compliance_overview`. **Governance & Delivery**: `list_principles`, `list_adrs`, `get_adr`, `list_soaws`. **Reports**: `get_portfolio_report`, `get_cost_treemap`, `get_capability_heatmap`, `get_data_quality_report`. **Card context**: `get_card_stakeholders`, `get_card_comments`, `get_card_documents`, `get_card_logo`, `list_available_icons`. **Diagrams**: `list_diagrams`, `get_diagram`. (`resolve_card_refs` carries a read annotation — it resolves only, it never writes.)
- **Audit & change history** (1, read). `get_change_history(batch_id?, actor_user_id?, tool_name?, origin?, limit?)` surfaces the mutation-batch ledger so agents and admins can reconstruct exactly what a previous MCP commit changed from a single id. Wraps `GET /mutation-batches` and `GET /mutation-batches/{id}/events`.
- **Write tools** (19, annotated additive or destructive). **Additive** (14, `_WRITE_ADDITIVE_ANNOT`): `transition_card_lifecycle`, `create_risks`, `update_risks`, `add_card_comment`, `create_soaw`, `assign_stakeholders`, `update_cards_bulk`, `create_adr`, `update_adr`, `sign_adr`, `create_cards_bulk`, `create_diagram`, `import_bpmn`, `set_card_logos` (a bundled brand-icon slug, an `image_url` the MCP server fetches, or raw bytes; `mime` optional and sniffed). **Destructive** (5, `_WRITE_DESTRUCTIVE_ANNOT`): `rollback_batch`, `update_diagram`, `archive_cards`, `upsert_relations_bulk`, `clear_card_logos`. The artifact-import subset (`create_cards_bulk` → `POST /cards/bulk-create`; `upsert_relations_bulk` → `POST /relations/bulk`; `create_diagram` → `POST /diagrams`; `import_bpmn` → find-or-create `BusinessProcess` then `PUT /bpm/processes/{id}/diagram`) lands structured rows the agent has read from its own context (spreadsheets, BPMN XML, DrawIO XML, PDFs, images). **Dry-run by default**: every mutating tool defaults to `dry_run=True`, which runs every validator and resolver server-side then rolls the transaction back so the agent can show the user a preview before committing. The backend's mutating endpoints carry the matching `dry_run: bool = False` request flag; `event_bus.publish` calls and side-effect emitters are gated on `not dry_run` so a preview never leaks events. Adding more mutating tools warrants careful security review.
- **All data access respects RBAC**: The user's JWT is passed through to the backend API, so permission checks are enforced server-side. Write tools require the same permissions as the underlying REST routes — e.g. `inventory.create` / `inventory.edit` / `inventory.archive`, `relations.manage`, `diagrams.manage`, `bpm.edit`, `risks.manage`, `comments.create`, `stakeholders.manage`, `soaw.create`, `adr.create` / `adr.sign`.
- **Write-tool guardrails.** Defense in depth so an LLM mishap can't cause mass damage. (a) Per-call size caps on the MCP path — defaults `MCP_MAX_CARDS_PER_CALL=200`, `MCP_MAX_RELATIONS_PER_CALL=500`, `MCP_MAX_LOGOS_PER_CALL=50`. The underlying backend bulk endpoints still accept up to 2000/5000 for the legitimate Excel-importer UI, but the MCP tool wrappers reject larger payloads before forwarding. (b) `upsert_relations_bulk` refuses `action: "delete"` ops by default — relations should be removed from the web UI for an auditable trail; flip `MCP_ALLOW_RELATION_DELETE=true` only when an operator explicitly opts in. `clear_card_logos` is the deliberate exception to the removal-is-UI-only stance: a deleted relation loses an edge nothing else records, whereas a cleared logo is trivially restored by setting it again, and without the tool an agent that wrote a wrong logo has no remedy at all. (c) Kill switch — `MCP_WRITES_ENABLED=false` disables all 19 write tools without a code redeploy; read tools keep working. (d) Audit origin — the MCP server sends `X-Turbo-EA-Origin: mcp` on every backend call; the `capture_request_origin` middleware in `app.main` mirrors it into the `request_origin` contextvar that `event_bus.publish` stamps into the event data payload (`{"origin": "mcp"}`) so admins can filter MCP-driven writes out of the timeline. Header values are whitelisted to `{mcp, web, api}` — any other value is dropped. (e) `set_card_logos` may fetch an `image_url`, and that fetch lives in the **MCP server**, never the backend (`mcp-server/turbo_ea_mcp/logo_fetch.py`): the bytes go up the ordinary upload route, so an LLM-chosen URL never reaches the process holding the database and every backend gate (permission, per-type `allow_card_logo`, 1 MB cap, magic-byte sniff, SVG refusal) still runs unchanged. Guards: `MCP_LOGO_FETCH_ENABLED` (kill switch), an **exact-match** host allowlist `MCP_LOGO_FETCH_HOSTS` (default: public icon CDNs only — a domain→logo service is deliberately not shipped on, since the request would *be* the customer's vendor list), https-only, no credentials in the URL, port 443, a private/loopback/link-local address refusal after DNS resolution, at most 2 redirects each re-validated from the top, a streamed 1 MB cap and a signature check. The dry run fetches too, cached in-process, so a dead or disallowed link is a preview row rather than a commit-time surprise — the same reason the preview resolves `icon_slug`s against the packs and reports `unknown_icon_slugs`. This is a deliberate narrowing of the older "the server never makes an outbound request on your behalf" rule: it held right up until agents turned out to be sandboxed away from the web, at which point "fetch the mark yourself" was advice they could not take. (f) The toolset deliberately omits **hard card delete** (permanent deletion). Bulk-update and archive *are* exposed (`update_cards_bulk`, `archive_cards`) but archive is recoverable (soft-delete with a 30-day restore window) and both are annotated/dry-run-gated; any future MCP tool that performs an *irreversible* mutation (hard delete, force-purge) needs an RFC discussion first.
- **Mutation batches.** Every MCP write call opens a `mutation_batches` row (`POST /mutation-batches`) before any writes, threads the resulting `batch_id` through every subsequent backend call via the `X-Turbo-EA-Batch` header, and closes the batch on success (`POST /mutation-batches/{id}/commit`). The same middleware that captures `X-Turbo-EA-Origin` mirrors the batch id into the `request_batch_id` contextvar so `event_bus.publish` stamps every event emitted during the request with that id — admins (or the `get_change_history` MCP tool) can then reconstruct the full per-event diff of a single batch from one id. Commits above `MCP_BATCH_CONFIRMATION_THRESHOLD` (default 20 rows) must present the one-shot `confirm_token` their dry-run was issued. A dry-run batch is opened and **closed** like any other — closing never checks a token (it did until 2.175.1, which refused every preview above 20 rows, [#1302](https://github.com/vincentmakes/turbo-ea/issues/1302)). The token is checked when the **real** batch opens (`POST /mutation-batches`, `confirm_token` in the body), before any write: `resolve_confirm_token` (`services/mutation_batch_service.py`) is the one rule — a dry-run of the same `tool_name`, by the same actor, under 15 minutes old, not yet used. Single use is a stamp on the issuing dry-run's `summary` (`confirmed_batch_id`), taken under `with_for_update()` so two concurrent commits cannot both spend it, and the real batch keeps the token in its own `confirm_token` column as the audit cross-reference. The MCP wrapper's gate (`_confirmation_required_message`) is only the friendly early error; the backend floor of 20 applies whatever `MCP_BATCH_CONFIRMATION_THRESHOLD` / `MCP_REQUIRE_DRYRUN_FIRST` say, so those can only tighten it. Every bulk write tool therefore opens a dry-run batch on its preview (that is how it gets a token) and returns `batch_id` + `confirm_token` from it — a new bulk tool must too, or its commits above 20 rows can never succeed. The wrapper helper lives in `mcp-server/turbo_ea_mcp/batches.py`; the standardised mutation pattern is documented on its `mutation_batch` async-context-manager. **All 51 MCP tools carry `ToolAnnotations`** (`readOnlyHint` / `destructiveHint` / `idempotentHint`) so connectors can surface destructiveness in their UI.
- **Config** is in `mcp-server/turbo_ea_mcp/config.py` — reads from env vars (`TURBO_EA_URL`, `TURBO_EA_PUBLIC_URL`, `MCP_PUBLIC_URL`, `MCP_PORT`, the nine write-guardrail vars `MCP_WRITES_ENABLED`, `MCP_MAX_CARDS_PER_CALL`, `MCP_MAX_RELATIONS_PER_CALL`, `MCP_MAX_LOGOS_PER_CALL`, `MCP_ALLOW_RELATION_DELETE`, `MCP_BATCH_CONFIRMATION_THRESHOLD`, `MCP_REQUIRE_DRYRUN_FIRST`, `MCP_LOGO_FETCH_ENABLED`, `MCP_LOGO_FETCH_HOSTS`, plus the OAuth redirect-URI allowlist `MCP_OAUTH_ALLOWED_REDIRECT_URIS` and the DNS-rebinding allowlists `MCP_ALLOWED_HOSTS` / `MCP_ALLOWED_ORIGINS`). `_build_transport_security()` in `server.py` admits localhost plus the hosts and origins of the two public URLs; the two allowlists only add to that — keep the guard on, never disable it or trust `X-Forwarded-Host` (a rebound page can set any header). An extra host is never turned into an origin. Every MCP env var is passed through `docker-compose.yml` explicitly — a var missing there is silently unset on compose installs.
- **Tests** live in `mcp-server/tests/` and use `pytest` + `pytest-asyncio`. Run with `cd mcp-server && pip install -e ".[dev]" && pytest`.
- The MCP server shares the `/VERSION` file with backend/frontend for version consistency.
