# The MCP server and the mutation-batch ledger

> Loaded when you touch `mcp-server/**`, `backend/app/api/v1/mutation_batches.py`, `backend/app/services/mutation_batch_service.py` (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

### MCP Server Conventions
- The MCP server lives in `mcp-server/` — a separate Python package (`turbo-ea-mcp`) with its own `pyproject.toml` and Dockerfile.
- It provides AI tool access to EA data via the [Model Context Protocol](https://modelcontextprotocol.io/) (FastMCP library).
- **Two transport modes**: HTTP/SSE (production, via Docker `--profile mcp`) and stdio (local testing with Claude Desktop).
- **Authentication**: In HTTP mode, users authenticate via OAuth 2.1 delegated to the Turbo EA SSO provider. The MCP server resolves OAuth tokens to Turbo EA JWTs. In stdio mode, `TURBO_EA_EMAIL`/`TURBO_EA_PASSWORD` env vars are used for direct login. **Redirect-URI validation is enforced**: clients register their `redirect_uris` via RFC 7591 dynamic registration (`POST /oauth/register`), the URIs are persisted in `OAuthStore.clients`, and `authorize()` refuses — with a direct 400, never a redirect — any request whose `redirect_uri` is not an exact match of a registered URI for that `client_id`; the token exchange re-checks `redirect_uri` against the one the code was issued for. **Never redirect an unvalidated `redirect_uri`** — doing so was the auth-code-exfiltration flaw fixed in 1.64.4 (CWE-601/346). Operators fronting the server with a fixed, non-registering integration can whitelist static redirect URIs via `MCP_OAUTH_ALLOWED_REDIRECT_URIS`.
- **Read tools** (42, across eleven clusters). **Cards & metamodel**: `search_cards`, `query_cards` (multi-hop relation query, keys-only grammar evaluated by `GET /cards?query=`), `list_inventory_views`, `get_card`, `get_card_relations`, `get_card_hierarchy`, `list_card_types`, `get_relation_types`, `list_tag_groups` (tag groups with description, mode, `mandatory`, `restrict_to_types`, and their tag ids — for `where.tags` and `set_card_tags`), `resolve_card_refs` (name-to-UUID pre-check), `analyze_impact` (dependency blast-radius for a proposed change). **Dashboards**: `get_dashboard`, `get_landscape`. **GRC (Risk Register)**: `list_risks`, `get_risk`, `get_risk_metrics`, `get_card_risks`. **GRC (Compliance)**: `list_compliance_findings`, `get_compliance_overview`. **Governance & Delivery**: `list_principles`, `list_adrs`, `get_adr`, `list_soaws`, `get_document_discussion` (`GET /{adr|soaw}/{id}/comments?scope=document|chain`; each comment's HTML `body` is also returned as plain `text` by the pure `turbo_ea_mcp/text_render.py::html_to_text`, stdlib only, mentions as `@Label` / `[restricted]` / `[deleted]`), `get_document_history` (`GET /{adr|soaw}/{id}/history`, the timeline only: version content and restore stay web-only). **Reports**: `get_portfolio_report`, `get_cost_treemap`, `get_capability_heatmap`, `get_data_quality_report`. **Card context**: `get_card_stakeholders`, `get_card_comments`, `get_card_documents`, `get_card_logo`, `list_available_icons`. **Diagrams**: `list_diagrams`, `get_diagram`. **Process flows**: `list_process_flow_versions` (`GET …/flow/published` + `…/flow/drafts`, summaries without XML; a 403 on drafts reads as `drafts_visible: false`), `get_process_flow_version` (`GET …/flow/versions/{vid}`, XML included, thumbnail dropped), `get_process_flow_elements` (`GET …/versions/{vid}` then `…/versions/{vid}/draft-elements`: each step's id, type, name and current links, `links_editable` for a draft or pending version). **Audit**: `get_change_history` (next bullet). **Extensions**: `list_extension_tools`, `call_extension_read` (see *Extension operations* below). (`resolve_card_refs` carries a read annotation — it resolves only, it never writes.)
- **Audit & change history** (1, read). `get_change_history(batch_id?, actor_user_id?, tool_name?, origin?, limit?)` surfaces the mutation-batch ledger so agents and admins can reconstruct exactly what a previous MCP commit changed from a single id. Wraps `GET /mutation-batches` and `GET /mutation-batches/{id}/events`.
- **Write tools** (28, annotated additive or destructive). **Additive** (21, `_WRITE_ADDITIVE_ANNOT`): `transition_card_lifecycle`, `create_risks`, `update_risks`, `add_card_comment`, `add_document_comment` (plain text only: the wrapper escapes every `<` into `<p>` paragraphs, so no mention markup reaches the backend from MCP; its preview reads the discussion before the batch opens and reports `can.comment` and whether `parent_id` is a top-level thread of that document; the backend declines rolling a posted comment back), `create_soaw`, `assign_stakeholders`, `update_cards_bulk`, `create_adr`, `update_adr` (both take `linked_diagram_ids` beside `linked_card_ids`, passed through to the backend, which checks `diagrams.view` and the decision's lock; every tool returning a decision's detail drops each linked diagram's `thumbnail` through `_without_diagram_thumbnails` — guards `TestLinkedDiagramIds` and `TestDiagramThumbnailsAreLeftOut` in `tests/test_adr_register_tools.py`), `sign_adr`, `revise_adr` (the next revision of a signed decision, same reference; its preview reads the decision and reports the revision number or the backend's refusal), `create_cards_bulk`, `create_diagram`, `save_inventory_view` (stores a `query_cards` query on a bookmark; the preview runs the query, the commit POSTs / PATCHes `/bookmarks`; bookmarks publish no event, so `rollback_batch` cannot undo it), `import_bpmn` (saves a draft only — see the artifact-import subset below), `submit_process_flow` / `approve_process_flow` (one workflow step each: `POST …/versions/{vid}/submit` / `…/approve`; the preview reads the version before the batch opens and reports the transition or a `wrong_status` refusal; a 400 / 403 / 404 on commit comes back as `submit_refused` / `approve_refused` carrying the backend's `detail` via `_detail(exc)`), `link_process_flow_elements` (step links on a draft or pending version: one `PUT …/versions/{vid}/draft-elements/{bpmn_element_id}` per entry, the element id encoded as ONE path segment by `_element_segment` — dots too, so `..` is never a dot-segment — and checked against the version's own steps before the batch opens; entry keys are a closed set, card ids UUID-validated, `""`/`null` clears a card link and `organization_ids: null` is sent as `[]` because the backend reads `null` there as "say nothing"; a step named twice is refused; a 400/403/404 stops the run and reports `applied` / `not_applied`; bulk confirm-token cycle, `row_count` = entries; draft links publish no event, so `rollback_batch` cannot undo them), `set_card_logos` (a bundled brand-icon slug, an `image_url` the MCP server fetches, or raw bytes; `mime` optional and sniffed), `create_tag_groups` (new groups with nested tags, or `{group_id, tags}` for an existing group; deduplicated by name, case-insensitive, against `GET /tag-groups` **before** the batch opens, so an existing group or tag is reported `exists` and never created twice and an unknown `group_id` refuses the call; entries resolving to the same existing group (a repeated `group_id`, or a name plus that group's id) are merged into one plan item carrying `merged_entries`, a tag named again across them is `duplicate` and sent once, and two new groups of one name are refused by the shape check (`duplicate_group`); `row_count` = groups + tags named; the preview sends each `POST /tag-groups` / `POST /tag-groups/{gid}/tags` with `dry_run: true` — the backend runs `tags.manage`, the `single`/`multi` Literal, the `restrict_to_types` card-type check and the group's existence, stores nothing and writes no audit row; tag groups are admin records with no card event, so `rollback_batch` cannot undo them). **Destructive** (7, `_WRITE_DESTRUCTIVE_ANNOT`): `rollback_batch`, `update_diagram`, `archive_cards`, `upsert_relations_bulk`, `clear_card_logos`, `call_extension_write` (see *Extension operations* below), `set_card_tags` (add / remove / replace through `POST /cards/tags/bulk`, cap `MCP_MAX_CARDS_PER_CALL`, confirm-token cycle; the backend route reads each card through `CardReadScope(mode="inventory")` — hidden or unknown is a per-row `not_found` —, refuses the whole call with 403 when a readable card is not taggable (`tags.manage` or `inventory.edit` / `card.edit`, the bulk-archive convention), fails an archived card per row, and runs `tag_service.set_card_tags` in a per-row savepoint so the single-choice and type-restriction rules apply to the resulting set; `dry_run` rolls back and publishes nothing — `set_card_tags(..., dry_run=True)` skips `publish_tag_event`, because a savepoint does not stop live SSE fan-out; reversible, `tag.added` / `tag.removed` are in `rollback_service`). The single-card `POST /cards/{id}/tags` is deliberately left without the rules: the UI swaps a single-choice tag by adding before it removes. The artifact-import subset (`create_cards_bulk` → `POST /cards/bulk-create`; `upsert_relations_bulk` → `POST /relations/bulk`; `create_diagram` → `POST /diagrams`; `import_bpmn` → find an existing `BusinessProcess` card (it never creates one) then save a **draft** and nothing more: `PATCH …/flow/versions/{draft_version_id}` to update a draft in place (same revision; a version not in `draft` status is refused before the batch opens), else `POST …/flow/drafts` with `based_on_id` = `based_on_version_id` or, by default, the published version when there is one. **It never submits or approves** — an LLM's first diagram needs review, so publishing is the separate, explicit `submit_process_flow` → `approve_process_flow` (discussion 1390). Draft saves publish no event, so `rollback_batch` cannot undo one; a PATCH of a draft's XML leaves `draft_element_links` alone, so the links of every element whose id survives carry over; `import_bpmn` takes no links — that is `link_process_flow_elements`; every link it returns is absolute, built by `_app_url` on `TURBO_EA_PUBLIC_URL`) lands structured rows the agent has read from its own context (spreadsheets, BPMN XML, DrawIO XML, PDFs, images). **Dry-run by default**: every mutating tool defaults to `dry_run=True`. Where the backend endpoint has a `dry_run: bool = False` request flag (cards bulk create/update, relations bulk, card tags bulk, `POST /tag-groups` and `POST /tag-groups/{gid}/tags`, `POST`/`PATCH /diagrams`, BPM `PUT /diagram`) the preview runs every validator and resolver server-side then rolls the transaction back (`begin_nested()` savepoint, `event_bus.publish` gated on `not dry_run`, `rollback()` instead of `commit()` — `bpm.save_diagram` / `diagrams.create_diagram` are the pattern); where it has none (`import_bpmn`'s flow workflow, ADR, SoAW, comments, lifecycle, sign, saved views) the MCP tool builds the preview itself and says so. Diagram events (`diagram.created` / `updated` / `deleted`) never carry the XML, and card-id changes sit in top-level `added_card_ids` / `removed_card_ids` — never nested under `changes`, which `scrub_event_payloads` does not reach and the dashboard feed shows to every reader. Adding more mutating tools warrants careful security review.
- **All data access respects RBAC**: The user's JWT is passed through to the backend API, so permission checks are enforced server-side. Write tools require the same permissions as the underlying REST routes — e.g. `inventory.create` / `inventory.edit` / `inventory.archive`, `relations.manage`, `diagrams.manage`, `bpm.edit` (drafts, submit) / `bpm.approve_flows` (approve), `risks.manage`, `comments.create`, `stakeholders.manage`, `tags.manage` (tag groups and tags; tagging also admits edit rights on the card), `soaw.create`, `adr.manage` (create, update, revise) / `adr.sign`, `adr.comment` / `soaw.comment` (or being a signatory) for `add_document_comment`.
- **Write-tool guardrails.** Defense in depth so an LLM mishap can't cause mass damage. (a) Per-call size caps on the MCP path — defaults `MCP_MAX_CARDS_PER_CALL=200`, `MCP_MAX_RELATIONS_PER_CALL=500`, `MCP_MAX_LOGOS_PER_CALL=50`. The underlying backend bulk endpoints still accept up to 2000/5000 for the legitimate Excel-importer UI, but the MCP tool wrappers reject larger payloads before forwarding. (b) `upsert_relations_bulk` refuses `action: "delete"` ops by default — relations should be removed from the web UI for an auditable trail; flip `MCP_ALLOW_RELATION_DELETE=true` only when an operator explicitly opts in. `clear_card_logos` is the deliberate exception to the removal-is-UI-only stance: a deleted relation loses an edge nothing else records, whereas a cleared logo is trivially restored by setting it again, and without the tool an agent that wrote a wrong logo has no remedy at all. (c) Kill switch — `MCP_WRITES_ENABLED=false` disables all 28 write tools without a code redeploy; read tools keep working. (d) Audit origin — the MCP server sends `X-Turbo-EA-Origin: mcp` on every backend call; the `capture_request_origin` middleware in `app.main` mirrors it into the `request_origin` contextvar that `event_bus.publish` stamps into the event data payload (`{"origin": "mcp"}`) so admins can filter MCP-driven writes out of the timeline. Header values are whitelisted to `{mcp, web, api}` — any other value is dropped. (e) `set_card_logos` may fetch an `image_url`, and that fetch lives in the **MCP server**, never the backend (`mcp-server/turbo_ea_mcp/logo_fetch.py`): the bytes go up the ordinary upload route, so an LLM-chosen URL never reaches the process holding the database and every backend gate (permission, per-type `allow_card_logo`, 1 MB cap, magic-byte sniff, SVG refusal) still runs unchanged. Guards: `MCP_LOGO_FETCH_ENABLED` (kill switch), an **exact-match** host allowlist `MCP_LOGO_FETCH_HOSTS` (default: public icon CDNs only — a domain→logo service is deliberately not shipped on, since the request would *be* the customer's vendor list), https-only, no credentials in the URL, port 443, a private/loopback/link-local address refusal after DNS resolution, at most 2 redirects each re-validated from the top, a streamed 1 MB cap and a signature check. The dry run fetches too, cached in-process, so a dead or disallowed link is a preview row rather than a commit-time surprise — the same reason the preview resolves `icon_slug`s against the packs and reports `unknown_icon_slugs`. This is a deliberate narrowing of the older "the server never makes an outbound request on your behalf" rule: it held right up until agents turned out to be sandboxed away from the web, at which point "fetch the mark yourself" was advice they could not take. (f) The toolset deliberately omits **hard card delete** (permanent deletion). Bulk-update and archive *are* exposed (`update_cards_bulk`, `archive_cards`) but archive is recoverable (soft-delete with a 30-day restore window) and both are annotated/dry-run-gated; any future MCP tool that performs an *irreversible* mutation (hard delete, force-purge) needs an RFC discussion first.
- **Mutation batches.** Every MCP write call opens a `mutation_batches` row (`POST /mutation-batches`) before any writes, threads the resulting `batch_id` through every subsequent backend call via the `X-Turbo-EA-Batch` header, and closes the batch on success (`POST /mutation-batches/{id}/commit`). The same middleware that captures `X-Turbo-EA-Origin` mirrors the batch id into the `request_batch_id` contextvar so `event_bus.publish` stamps every event emitted during the request with that id — admins (or the `get_change_history` MCP tool) can then reconstruct the full per-event diff of a single batch from one id. Commits above `MCP_BATCH_CONFIRMATION_THRESHOLD` (default 20 rows) must present the one-shot `confirm_token` their dry-run was issued. A dry-run batch is opened and **closed** like any other — closing never checks a token (it did until 2.175.1, which refused every preview above 20 rows, [#1302](https://github.com/vincentmakes/turbo-ea/issues/1302)). The token is checked when the **real** batch opens (`POST /mutation-batches`, `confirm_token` in the body), before any write: `resolve_confirm_token` (`services/mutation_batch_service.py`) is the one rule — a dry-run of the same `tool_name`, by the same actor, under 15 minutes old, not yet used. Single use is a stamp on the issuing dry-run's `summary` (`confirmed_batch_id`), taken under `with_for_update()` so two concurrent commits cannot both spend it, and the real batch keeps the token in its own `confirm_token` column as the audit cross-reference. The MCP wrapper's gate (`_confirmation_required_message`) is only the friendly early error; the backend floor of 20 applies whatever `MCP_BATCH_CONFIRMATION_THRESHOLD` / `MCP_REQUIRE_DRYRUN_FIRST` say, so those can only tighten it. Every bulk write tool therefore opens a dry-run batch on its preview (that is how it gets a token) and returns `batch_id` + `confirm_token` from it — a new bulk tool must too, or its commits above 20 rows can never succeed. The wrapper helper lives in `mcp-server/turbo_ea_mcp/batches.py`; the standardised mutation pattern is documented on its `mutation_batch` async-context-manager. **The batch rule covers every write tool, single-record ones included**: each call — preview and commit — opens `mutation_batch(..., dry_run=dry_run)` before its first backend write (read-only lookups that can refuse the call, like `import_bpmn`'s card search, may come first), sends every write through `batch.client()`, returns `**_preview_fields(batch)` on a preview and `batch_id` on a commit. `rollback_batch` is the one exception — the backend records a rollback as its own batch. Guard: `mcp-server/tests/test_safeguards.py::TestEveryWriteToolIsABatch`, parametrised over every tool annotated `_WRITE_ADDITIVE_ANNOT` / `_WRITE_DESTRUCTIVE_ANNOT` in the registry; a new write tool fails it until it is given an argument set there and follows the rule. Rolling back `diagram.created` deletes the diagram (skipped once published); `diagram.updated` / `diagram.deleted` are declined. **All 70 MCP tools carry `ToolAnnotations`** (`readOnlyHint` / `destructiveHint` / `idempotentHint`) so connectors can surface destructiveness in their UI.
- **Extension operations (backend SDK 1.18).** An extension declaring the manifest grant `core.agent.tools` may offer routes of its own router as `AgentTool` rows (`get_agent_tools()` hook); `backend/app/services/extensions/agent_tools.py` checks each against the mounted router at startup and drops what it cannot vouch for (configuration segments, file downloads, `ext.<key>.admin` / `admin.*` permissions, unknown routes, mismatched path params, a bare-`dict` body without `input_schema`), and `GET /extensions/agent-tools` lists only live extensions (enabled, licensed, granted — `grants_for` per call) with only the tools whose permission the caller holds. The MCP side is three static tools, never one tool per extension operation: `list_extension_tools` (read), `call_extension_read` (read; refuses a non-`read` kind) and `call_extension_write` (`_WRITE_DESTRUCTIVE_ANNOT`; kill switch first; `destructive` kinds refused unless `MCP_ALLOW_EXTENSION_DESTRUCTIVE=true`; one mutation batch with `row_count=1` on preview and commit; the preview forwards `dry_run: true` when the tool declares `supports_dry_run`, else is built by the MCP server and sends nothing). The plain helpers `_find_extension_tool` / `_check_extension_arguments` / `_build_extension_request` read the catalogue per call (no cache), refuse unknown extensions, tools and argument keys and missing required ones (`input_schema.required` + path params), encode each path parameter as one segment (no `/`, dots as `%2E`), send `query_params` (every argument on GET / DELETE) in the query string and the rest as the JSON body, and call `/ext/<key><path>` with the user's JWT through the batch client — `require_extension` and the route's own RBAC stay the authority. A non-JSON success answer is reported, never a crash. The extension's bridge writes made while serving the call record the MCP batch as `summary.via_batch_id` on their `ext:<key>` batch (`data_service.open_batch`, and `data_service.single_op_summary` for a write made outside a batch scope). **Not reversible by `rollback_batch`** — extension tables are the extension's. Guards: `tests/test_extension_tools.py`, `backend/tests/api/test_extension_agent_tools.py`, `backend/tests/services/test_extension_agent_tools.py`.
- **Every tool refuses an argument it does not declare.** The SDK's argument models ignore unknown keys, so Claude Desktop passing step links to `import_bpmn` (which has no such parameter) got a success while the links vanished (discussion 1390 follow-up). `mcp` is a `_StrictFastMCP`, whose `add_tool` — reached by `@mcp.tool` in every SDK release the package allows (`mcp>=1.22.0,<2`; the floor is the first release that runs on pydantic 2.14, see the comment in `pyproject.toml`) — rebuilds each tool's `fn_metadata.arg_model` with the `_NoUnknownArguments` mixin (`extra="forbid"`, so the published schema says `additionalProperties: false`, plus a before-validator that raises `UnknownArgumentsError`, deliberately not a `ValueError`, naming the unknown and the valid arguments) and republishes `parameters`. Never add a per-tool `**kwargs` catch-all or switch this off. Guard: `tests/test_safeguards.py::TestUnknownArgumentsAreRefused`, parametrised over the registry.
- **Config** is in `mcp-server/turbo_ea_mcp/config.py` — reads from env vars (`TURBO_EA_URL`, `TURBO_EA_PUBLIC_URL`, `MCP_PUBLIC_URL`, `MCP_PORT`, the ten write-guardrail vars `MCP_WRITES_ENABLED`, `MCP_MAX_CARDS_PER_CALL`, `MCP_MAX_RELATIONS_PER_CALL`, `MCP_MAX_LOGOS_PER_CALL`, `MCP_ALLOW_RELATION_DELETE`, `MCP_ALLOW_EXTENSION_DESTRUCTIVE`, `MCP_BATCH_CONFIRMATION_THRESHOLD`, `MCP_REQUIRE_DRYRUN_FIRST`, `MCP_LOGO_FETCH_ENABLED`, `MCP_LOGO_FETCH_HOSTS`, plus the OAuth redirect-URI allowlist `MCP_OAUTH_ALLOWED_REDIRECT_URIS` and the DNS-rebinding allowlists `MCP_ALLOWED_HOSTS` / `MCP_ALLOWED_ORIGINS`). **`TURBO_EA_PUBLIC_URL` is resolved by `config.public_app_url`**: the variable when set to a real host; when it is unset, empty or a loopback host (`localhost` / `127.0.0.1` / `[::1]`, any port — `.env.example` ships `http://localhost`, which nginx also reads), the origin (scheme + host) of the raw `MCP_PUBLIC_URL` variable when that names a real host (never its code default, which is this server's own port); a loopback value stands when `MCP_PUBLIC_URL` gives nothing better; else `http://localhost:8920` — `docker-compose.yml` therefore passes it to the MCP container as `${TURBO_EA_PUBLIC_URL:-}`, not with a localhost default, or every link `_app_url` builds on an OAuth install that set only `MCP_PUBLIC_URL` pointed at localhost. `_build_transport_security()` in `server.py` admits localhost plus the hosts and origins of the two public URLs; the two allowlists only add to that — keep the guard on, never disable it or trust `X-Forwarded-Host` (a rebound page can set any header). An extra host is never turned into an origin. Every MCP env var is passed through `docker-compose.yml` explicitly — a var missing there is silently unset on compose installs.
- **Tests** live in `mcp-server/tests/` and use `pytest` + `pytest-asyncio`. Run with `cd mcp-server && pip install -e ".[dev]" && pytest`.
- The MCP server shares the `/VERSION` file with backend/frontend for version consistency.
