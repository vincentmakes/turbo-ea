# The MCP server and the mutation-batch ledger

> Loaded when you touch `mcp-server/**`, `backend/app/api/v1/mutation_batches.py`, `backend/app/services/mutation_batch_service.py` (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

### MCP Server Conventions
- The MCP server lives in `mcp-server/` — a separate Python package (`turbo-ea-mcp`) with its own `pyproject.toml` and Dockerfile.
- It provides AI tool access to EA data via the [Model Context Protocol](https://modelcontextprotocol.io/) (FastMCP library).
- **Two transport modes**: HTTP/SSE (production, via Docker `--profile mcp`) and stdio (local testing with Claude Desktop).
- **Authentication**: In HTTP mode, users authenticate via OAuth 2.1 delegated to the Turbo EA SSO provider. **A connection is a durable backend session, never MCP-process memory** (#1449): at the token exchange `oauth._handle_code_exchange` (after the redirect-URI, client-id and PKCE checks) calls `api_client.create_mcp_session` → `POST /auth/mcp/sessions` with the SSO JWT and the registered `client_name`, and the refresh grant relays to `POST /auth/mcp/sessions/refresh` (`backend/app/api/v1/mcp_sessions.py`, `services/mcp_session_service.py`). The **access token** handed to the AI tool is the session's 1 h Turbo EA JWT (bound to the session by its `msid` claim, so revoking the session refuses it at once) Fernet-sealed under `config.oauth_token_key` with its own expiry, prefix `tea1a.`; `resolve_token` opens it with no backend call, so it survives a restart. The **refresh token** is the backend's `tea1r.<session>.<generation>.<HMAC>`, **verified here before it is relayed** (unchanged): `oauth._refresh_token_signed` mirrors the backend's `parse_refresh_token` with `config.refresh_token_key` (`HMAC-SHA256(SECRET_KEY, "turbo-ea/mcp-refresh-token/v1")`, the backend's `REFRESH_KEY_CONTEXT`, known-answer vector pinned in `tests/test_config.py`) — a string of at most 200 characters (`MAX_REFRESH_TOKEN_LENGTH`), ASCII, the prefix, a constant-time compare of the unpadded base64url signature — and anything else gets 400 `invalid_grant` "Unknown refresh token" with **no backend call**, so an anonymous flood of junk `tea1r.` tokens on `/oauth/token` cannot fill the backend's per-peer rate-limit bucket for the MCP container and starve every real renewal; without SECRET_KEY every refresh token is refused here (none was issued). Tests relay tokens signed by `tests/refresh_tokens.py::signed_refresh`, whose key `tests/conftest.py` sets on `oauth._refresh_token_key` for every test. The backend rotates it on every use, re-issues the same successor for the previous one within 60 s, ends the session (and logs it) on any older replay, and expires it after 30 days idle / 180 days in all. Both backend calls carry `X-Turbo-EA-Service`, a 60 s HS256 proof signed with `config.service_proof_key` (`HMAC-SHA256(SECRET_KEY, "turbo-ea-mcp/service-auth/v1")`, mirrored in `backend/app/core/security.py` and pinned by the same known-answer vector in both suites), so a refresh token is useless anywhere but through this instance's MCP server. **Only a real refusal ends a connection**: on refresh, 400 / 403 / 422 (`_REFRESH_REFUSED_STATUSES`) are `invalid_grant`; 401 (proof refused — clock drift, SECRET_KEY mismatch), 404 / 405 (a backend older than this server, e.g. mid rolling upgrade), 429, 5xx, network errors and any other non-2xx raise `RefreshUnavailableError` → 503 `temporarily_unavailable` + `Retry-After`, and the client keeps its refresh token. At the create call, network errors, 5xx, 429 and any non-2xx outside 401/404/405 raise the same (the authorization code stays usable for the retry). **Degraded mode**: no `SECRET_KEY` on the MCP container, or a backend answering 401/404/405 to the create call (another key, or older than this server) — sign-in still works with the SSO JWT sealed as the access token and **no `refresh_token`** in the response, for **at most an hour** (`DEGRADED_ACCESS_TOKEN_SECONDS` = 3600: `expires_in` and the sealed expiry are min(the JWT's remaining life, 3600), since nothing can revoke that JWT), and a warning names the cause. Every MCP key derives from `SECRET_KEY`, so the MCP container needs the backend's exact value; without it client ids and access tokens die with the process (`CLIENT_KEY_IS_EPHEMERAL`, startup warning). A client id (`mint_client_id`) signs its redirect URIs and the first 100 characters of the registered `client_name` (claim `c`, JSON with `ensure_ascii=False`, under `MAX_CLIENT_ID_LENGTH`), so after a restart `client_from_id` still names the tool in the admin table and the audit log; an id minted before (no `c`) or with a blank or non-text name reads `DEFAULT_CLIENT_NAME`. Only a sign-in in flight (`OAuthStore.pending` / `codes`) lives in memory. In stdio mode, `TURBO_EA_EMAIL`/`TURBO_EA_PASSWORD` env vars are used for direct login. **Redirect-URI validation is enforced**: clients register their `redirect_uris` via RFC 7591 dynamic registration (`POST /oauth/register`), the URIs are persisted in `OAuthStore.clients`, and `authorize()` refuses — with a direct 400, never a redirect — any request whose `redirect_uri` is not an exact match of a registered URI for that `client_id`; the token exchange re-checks `redirect_uri` against the one the code was issued for. **Never redirect an unvalidated `redirect_uri`** — doing so was the auth-code-exfiltration flaw fixed in 1.64.4 (CWE-601/346). Operators fronting the server with a fixed, non-registering integration can whitelist static redirect URIs via `MCP_OAUTH_ALLOWED_REDIRECT_URIS`.

Adding more mutating tools warrants careful security review.
- **All data access respects RBAC**: The user's JWT is passed through to the backend API, so permission checks are enforced server-side. Write tools require the same permissions as the underlying REST routes — e.g. `inventory.create` / `inventory.edit` / `inventory.archive`, `relations.manage`, `diagrams.manage`, `bpm.edit` (drafts, submit) / `bpm.approve_flows` (approve), `risks.manage`, `comments.create`, `stakeholders.manage`, `tags.manage` (tag groups and tags; tagging also admits edit rights on the card), `soaw.create`, `adr.manage` (create, update, revise) / `adr.sign`, `adr.comment` / `soaw.comment` (or being a signatory) for `add_document_comment`, `admin.settings` for the custom-language tools, `ppm.view` / `ppm.manage` for the PPM tools.
- **Write-tool guardrails.** Defense in depth so an LLM mishap can't cause mass damage. (a) Per-call size caps on the MCP path — defaults `MCP_MAX_CARDS_PER_CALL=200`, `MCP_MAX_RELATIONS_PER_CALL=500`, `MCP_MAX_LOGOS_PER_CALL=50`, `MCP_MAX_TRANSLATIONS_PER_CALL=2000`, `MCP_MAX_PPM_ROWS_PER_CALL=200` (items per PPM save call; dependency adds + removes). The underlying backend bulk endpoints still accept up to 2000/5000 for the legitimate Excel-importer UI, but the MCP tool wrappers reject larger payloads before forwarding. (b) `upsert_relations_bulk` refuses `action: "delete"` ops by default — relations should be removed from the web UI for an auditable trail; flip `MCP_ALLOW_RELATION_DELETE=true` only when an operator explicitly opts in. `clear_card_logos` is the deliberate exception to the removal-is-UI-only stance: a deleted relation loses an edge nothing else records, whereas a cleared logo is trivially restored by setting it again, and without the tool an agent that wrote a wrong logo has no remedy at all. (c) Kill switch — `MCP_WRITES_ENABLED=false` disables all 37 write tools without a code redeploy; read tools keep working. (d) Audit origin — the MCP server sends `X-Turbo-EA-Origin: mcp` on every backend call; the `capture_request_origin` middleware in `app.main` mirrors it into the `request_origin` contextvar that `event_bus.publish` stamps into the event data payload (`{"origin": "mcp"}`) so admins can filter MCP-driven writes out of the timeline. Header values are whitelisted to `{mcp, web, api}` — any other value is dropped. (e) `set_card_logos` may fetch an `image_url`, and that fetch lives in the **MCP server**, never the backend (`mcp-server/turbo_ea_mcp/logo_fetch.py`): the bytes go up the ordinary upload route, so an LLM-chosen URL never reaches the process holding the database and every backend gate (permission, per-type `allow_card_logo`, 1 MB cap, magic-byte sniff, SVG refusal) still runs unchanged. Guards: `MCP_LOGO_FETCH_ENABLED` (kill switch), an **exact-match** host allowlist `MCP_LOGO_FETCH_HOSTS` (default: public icon CDNs only — a domain→logo service is deliberately not shipped on, since the request would *be* the customer's vendor list), https-only, no credentials in the URL, port 443, a private/loopback/link-local address refusal after DNS resolution, at most 2 redirects each re-validated from the top, a streamed 1 MB cap and a signature check. The dry run fetches too, cached in-process, so a dead or disallowed link is a preview row rather than a commit-time surprise — the same reason the preview resolves `icon_slug`s against the packs and reports `unknown_icon_slugs`. This is a deliberate narrowing of the older "the server never makes an outbound request on your behalf" rule: it held right up until agents turned out to be sandboxed away from the web, at which point "fetch the mark yourself" was advice they could not take. (f) The toolset deliberately omits **hard card delete** (permanent deletion). Bulk-update and archive *are* exposed (`update_cards_bulk`, `archive_cards`) but archive is recoverable (soft-delete with a 30-day restore window) and both are annotated/dry-run-gated; any future MCP tool that performs an *irreversible* mutation (hard delete, force-purge) needs an RFC discussion first.
- **Mutation batches.** Every MCP write call opens a `mutation_batches` row (`POST /mutation-batches`) before any writes, threads the resulting `batch_id` through every subsequent backend call via the `X-Turbo-EA-Batch` header, and closes the batch on success (`POST /mutation-batches/{id}/commit`). The same middleware that captures `X-Turbo-EA-Origin` mirrors the batch id into the `request_batch_id` contextvar so `event_bus.publish` stamps every event emitted during the request with that id — admins (or the `get_change_history` MCP tool) can then reconstruct the full per-event diff of a single batch from one id. Commits above `MCP_BATCH_CONFIRMATION_THRESHOLD` (default 20 rows) must present the one-shot `confirm_token` their dry-run was issued — except a tool in `CONFIRMATION_EXEMPT_TOOLS` (only `submit_translations`, see above; pinned by `test_only_submit_translations_is_exempt` in the backend and `test_only_submit_translations_skips_the_confirm_cycle` in the MCP suite, so no second tool joins silently). A dry-run batch is opened and **closed** like any other — closing never checks a token (it did until 2.175.1, which refused every preview above 20 rows, [#1302](https://github.com/vincentmakes/turbo-ea/issues/1302)). The token is checked when the **real** batch opens (`POST /mutation-batches`, `confirm_token` in the body), before any write: `resolve_confirm_token` (`services/mutation_batch_service.py`) is the one rule — a dry-run of the same `tool_name`, by the same actor, **with the same `scope`**, under 15 minutes old, not yet used. `scope` (≤ 200 chars, optional) is a tool's own summary of its arguments, sent by `mutation_batch(scope=…)` on the preview and the commit alike: the preview keeps it as `summary["confirm_scope"]` (`SCOPE_KEY`), which `close_summary` keeps and never takes from a caller — like the single-use stamp — and a token whose preview had another scope (or none, against one) is refused `wrong_scope`. Only `start_ai_translation` binds today (`_ai_translation_scope`: `locale|mode|manual-or-keep`; pinned by `_BATCH_SCOPES` in `test_safeguards.py`); a tool whose commit could act on other arguments than its preview showed should bind too. Single use is a stamp on the issuing dry-run's `summary` (`confirmed_batch_id`), taken under `with_for_update()` so two concurrent commits cannot both spend it, and the real batch keeps the token in its own `confirm_token` column as the audit cross-reference. The MCP wrapper's gate (`_confirmation_required_message`) is only the friendly early error; the backend floor of 20 applies whatever `MCP_BATCH_CONFIRMATION_THRESHOLD` / `MCP_REQUIRE_DRYRUN_FIRST` say, so those can only tighten it. Every bulk write tool therefore opens a dry-run batch on its preview (that is how it gets a token) and returns `batch_id` + `confirm_token` from it — a new bulk tool must too, or its commits above 20 rows can never succeed. The wrapper helper lives in `mcp-server/turbo_ea_mcp/batches.py`; the standardised mutation pattern is documented on its `mutation_batch` async-context-manager. **The batch rule covers every write tool, single-record ones included**: each call — preview and commit — opens `mutation_batch(..., dry_run=dry_run)` before its first backend write (read-only lookups that can refuse the call, like `import_bpmn`'s card search, may come first), sends every write through `batch.client()`, returns `**_preview_fields(batch)` on a preview and `batch_id` on a commit. `rollback_batch` is the one exception — the backend records a rollback as its own batch. Guard: `mcp-server/tests/test_safeguards.py::TestEveryWriteToolIsABatch`, parametrised over every tool annotated `_WRITE_ADDITIVE_ANNOT` / `_WRITE_DESTRUCTIVE_ANNOT` in the registry; a new write tool fails it until it is given an argument set there and follows the rule. Rolling back `diagram.created` deletes the diagram (skipped once published); `diagram.updated` / `diagram.deleted` are declined. **All 85 MCP tools carry `ToolAnnotations`** (`readOnlyHint` / `destructiveHint` / `idempotentHint`) so connectors can surface destructiveness in their UI.
- **Extension operations (backend SDK 1.18).** An extension declaring the manifest grant `core.agent.tools` may offer routes of its own router as `AgentTool` rows (`get_agent_tools()` hook); `backend/app/services/extensions/agent_tools.py` checks each against the mounted router at startup and drops what it cannot vouch for (configuration segments, file downloads, `ext.<key>.admin` / `admin.*` permissions, unknown routes, mismatched path params, a bare-`dict` body without `input_schema`), and `GET /extensions/agent-tools` lists only live extensions (enabled, licensed, granted — `grants_for` per call) with only the tools whose permission the caller holds. The MCP side is three static tools, never one tool per extension operation: `list_extension_tools` (read), `call_extension_read` (read; refuses a non-`read` kind) and `call_extension_write` (`_WRITE_DESTRUCTIVE_ANNOT`; kill switch first; `destructive` kinds refused unless `MCP_ALLOW_EXTENSION_DESTRUCTIVE=true`; one mutation batch with `row_count=1` on preview and commit; the preview forwards `dry_run: true` when the tool declares `supports_dry_run`, else is built by the MCP server and sends nothing). The plain helpers `_find_extension_tool` / `_check_extension_arguments` / `_build_extension_request` read the catalogue per call (no cache), refuse unknown extensions, tools and argument keys and missing required ones (`input_schema.required` + path params), encode each path parameter as one segment (no `/`, dots as `%2E`), send `query_params` (every argument on GET / DELETE) in the query string and the rest as the JSON body, and call `/ext/<key><path>` with the user's JWT through the batch client — `require_extension` and the route's own RBAC stay the authority. A non-JSON success answer is reported, never a crash. The extension's bridge writes made while serving the call record the MCP batch as `summary.via_batch_id` on their `ext:<key>` batch (`data_service.open_batch`, and `data_service.single_op_summary` for a write made outside a batch scope). **Not reversible by `rollback_batch`** — extension tables are the extension's. Guards: `tests/test_extension_tools.py`, `backend/tests/api/test_extension_agent_tools.py`, `backend/tests/services/test_extension_agent_tools.py`.
- **Every tool refuses an argument it does not declare.** The SDK's argument models ignore unknown keys, so Claude Desktop passing step links to `import_bpmn` (which has no such parameter) got a success while the links vanished (discussion 1390 follow-up). `mcp` is a `_StrictFastMCP`, whose `add_tool` — reached by `@mcp.tool` in every SDK release the package allows (`mcp>=1.22.0,<2`; the floor is the first release that runs on pydantic 2.14, see the comment in `pyproject.toml`) — rebuilds each tool's `fn_metadata.arg_model` with the `_NoUnknownArguments` mixin (`extra="forbid"`, so the published schema says `additionalProperties: false`, plus a before-validator that raises `UnknownArgumentsError`, deliberately not a `ValueError`, naming the unknown and the valid arguments) and republishes `parameters`. Never add a per-tool `**kwargs` catch-all or switch this off. Guard: `tests/test_safeguards.py::TestUnknownArgumentsAreRefused`, parametrised over the registry.
- **Config** is in `mcp-server/turbo_ea_mcp/config.py` — reads from env vars (`TURBO_EA_URL`, `TURBO_EA_PUBLIC_URL`, `MCP_PUBLIC_URL`, `MCP_PORT`, the twelve write-guardrail vars `MCP_WRITES_ENABLED`, `MCP_MAX_CARDS_PER_CALL`, `MCP_MAX_RELATIONS_PER_CALL`, `MCP_MAX_LOGOS_PER_CALL`, `MCP_MAX_TRANSLATIONS_PER_CALL`, `MCP_MAX_PPM_ROWS_PER_CALL`, `MCP_ALLOW_RELATION_DELETE`, `MCP_ALLOW_EXTENSION_DESTRUCTIVE`, `MCP_BATCH_CONFIRMATION_THRESHOLD`, `MCP_REQUIRE_DRYRUN_FIRST`, `MCP_LOGO_FETCH_ENABLED`, `MCP_LOGO_FETCH_HOSTS`, plus the OAuth redirect-URI allowlist `MCP_OAUTH_ALLOWED_REDIRECT_URIS` and the DNS-rebinding allowlists `MCP_ALLOWED_HOSTS` / `MCP_ALLOWED_ORIGINS`). **`TURBO_EA_PUBLIC_URL` is resolved by `config.public_app_url`**: the variable when set to a real host; when it is unset, empty or a loopback host (`localhost` / `127.0.0.1` / `[::1]`, any port — `.env.example` ships `http://localhost`, which nginx also reads), the origin (scheme + host) of the raw `MCP_PUBLIC_URL` variable when that names a real host (never its code default, which is this server's own port); a loopback value stands when `MCP_PUBLIC_URL` gives nothing better; else `http://localhost:8920` — `docker-compose.yml` therefore passes it to the MCP container as `${TURBO_EA_PUBLIC_URL:-}`, not with a localhost default, or every link `_app_url` builds on an OAuth install that set only `MCP_PUBLIC_URL` pointed at localhost. `_build_transport_security()` in `server.py` admits localhost plus the hosts and origins of the two public URLs; the two allowlists only add to that — keep the guard on, never disable it or trust `X-Forwarded-Host` (a rebound page can set any header). An extra host is never turned into an origin. Every MCP env var is passed through `docker-compose.yml` explicitly — a var missing there is silently unset on compose installs.
- **The HTTP server takes a request head of up to 64 KB.** `main()` passes `h11_max_incomplete_event_size=MAX_REQUEST_HEAD_BYTES` (64 * 1024) to `uvicorn.run`, because the edge nginx forwards up to four 16 KB header buffers (`large_client_header_buffers 4 16k`) so a sign-in proxy's token headers and cookies fit, and uvicorn's h11 default of 16 KB answered such a request "400 Invalid HTTP request received." ([#1445](https://github.com/vincentmakes/turbo-ea/issues/1445), 2.217.1). Keep it at least the edge's total. Guard: `tests/test_server_entrypoints.py::TestMain` pins the exact `uvicorn.run` kwargs with the literal 65536.
- **Tests** live in `mcp-server/tests/` and use `pytest` + `pytest-asyncio`. Run with `cd mcp-server && pip install -e ".[dev]" && pytest`.
- The MCP server shares the `/VERSION` file with backend/frontend for version consistency.
