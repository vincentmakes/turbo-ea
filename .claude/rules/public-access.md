# Auth cookie, sign-in landing, route permissions, portals, published diagrams, framing

> Loaded when you touch `backend/app/services/public_access.py`, `backend/app/services/diagram_legend.py`, `backend/app/api/v1/auth.py`, `backend/app/api/v1/diagrams.py`, … (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

- **Published, account-less resources share one access layer.** Two things are reachable without an app session — web portals and published diagrams — and both go through `app/services/public_access.py` (SSO gate config, the visitor-email resolver that enforces `email_verified`, Google's hosted domain and the per-resource domain allowlist, and the httpOnly cookie helpers). Never re-implement those checks per resource: they are exactly where a divergence becomes a security bug, and every check must derive from the **signature-verified** id_token, never from client input. The session cookie is minted by `create_portal_token(..., resource=...)` and validated with `portal_token_matches(claims, resource, id)` — the `res` claim is what stops a grant for one resource unlocking another (a token with no `res` is legacy and means `portal`, so cookies issued before the discriminator existed keep working). One cookie *name* for all of them; isolation comes from the per-resource cookie **path**. **The diagram's cookie is the cross-site one.** The embed page runs inside another site's iframe, and a `SameSite=Lax` cookie is never sent from there, so `set_access_cookie(..., cross_site=True)` emits `SameSite=None; Secure; Partitioned` (CHIPS) — the `Partitioned` attribute appended by hand in `_mark_partitioned`, because Starlette hands it to the stdlib Morsel, which only learned it in Python 3.14 and the image runs 3.12; over plain HTTP it degrades to Lax with a warning, which is why SSO-gated embeds need HTTPS. Portals stay Lax (never framed). Three consequences the frontend is built around, all in `frontend/src/lib/publicSso.ts` and `PublicDiagramPage.tsx` ([#1126](https://github.com/vincentmakes/turbo-ea/issues/1126), fixed in 2.146.1): **a framed page never navigates itself to the IdP** — every provider serves its authorize endpoint with `X-Frame-Options: DENY`, `prompt=none` included, so the sign-in is a popup opened from the click and `/auth/callback` (`SsoCallback.tsx`) *relays* `{code, nonce}` to `window.opener` with `postMessage` when the state carries `popup: true`; **the iframe issues the code exchange**, never the popup, because a partitioned cookie is keyed by the top-level site and one set in the popup lands in the wrong partition; and **the nonce lives in a ref in the page**, not `sessionStorage` (the popup opens on the IdP and inherits none, and two diagrams on one wiki page would share a key). The top-level page keeps the portal-style redirect and writes its `portal_silent_diagram_<slug>` flag *before* leaving, so an attempt that never returns cannot loop. `location /` must never gain `Cross-Origin-Opener-Policy` — it would sever `window.opener` when the popup returns. Guard tests: `tests/api/test_diagrams_publish.py::TestSsoGate` (cookie shape), `frontend/src/features/diagrams/PublicDiagramPage.test.tsx`, `SsoCallback.test.tsx`, `lib/publicSso.test.ts`.

- **A public read endpoint returns the artefact, not the model behind it.** `GET /diagrams/public/{slug}` returns `{name, xml, legend}` and runs the XML through `sanitise_public_xml` first, stripping `cardId` / `cardType` / `relationId` / `relationType` / `parentGroupCell` (`backend/app/api/v1/diagrams.py`). A published diagram is a picture; without the strip, "no drill-through" would be a UI convention while the raw payload still handed every anonymous visitor the card UUIDs and the relation graph. Its third key, `legend`, is the key to the colours the picture already shows and holds to the same line: `build_public_legend` (`services/diagram_legend.py`) sends rule titles, option labels + translations and colours, a per-rule `has_missing` flag and a coloured count — aggregates only, never a card's id, name or value (`test_public_legend_is_aggregate_only`); the page renders it through the same `legendSections` builder as the editor. Any future public surface owes the same treatment. Publishing is gated on its own `diagrams.publish` permission — exposing data outside the instance is a different authority from editing it, and no default role but admin holds it. Publication state is excluded from workspace transfer (`sections.py`) so cloning an instance can never re-expose a link on the target.

- **Only the published-diagram paths may be framed by another site.** `X-Frame-Options` has no allowlist form, so the three embed locations (`/embed/`, `/api/v1/diagrams/public/`, `/drawio-embed/`) drop it and send CSP `frame-ancestors` built from `TURBO_EA_EMBED_ALLOWED_ORIGINS` instead (generated in the nginx entrypoint in `/Dockerfile`, **default empty ⇒ `'self'`**, i.e. embedding off until an operator opts in). The DrawIO viewer is served twice on purpose: `/drawio-embed/` carries the relaxed header while the app's own `/drawio/` stays `'self'`, because CSP `frame-ancestors` is checked against **every** ancestor — a nested same-origin frame inside a third-party page is still blocked, and splitting the path is what keeps the authenticated editor un-framable. `add_header` in an nginx `location` replaces the inherited set, so each of those blocks re-declares the full header block; add new locations the same way or they silently lose every security header. `location ^~ /drawio/` (the DrawIO scripts, styles and images) predated that rule and carried only its two caching headers, so every asset left the edge with no security headers at all until the 2026-09-30 DAST crawl reached the editor; `tests/services/test_nginx_headers.py::TestEveryLocationKeepsTheSecurityHeaders` now fails any location that adds a header without re-declaring the response-level set. ZAP's content rules that fire on DrawIO's own vendored files are `OUTOFSCOPE` for `/drawio/` in `.github/zap-rules.tsv`, never IGNOREd globally.

- **A route's permission is declared once, in `ROUTE_PERMISSIONS` — never on the `<Route>` and never a second time in the nav.** `frontend/src/lib/routePermissions.ts` is the single source of truth for "which permission does this URL need?", and three things read it: `RouteGuard` (`components/RouteGuard.tsx`), which wraps the whole authenticated table in `App.tsx` so a **typed URL is gated exactly like the nav item that leads to it**; `AppLayout`'s nav definitions (`layouts/navItems.ts`), which derive each entry's permission from the path it points at rather than carrying their own; and `SsoCallback`, which asks `canAccessPath()` before honouring a deep link. Wrapping the table **once** is what stops the gating drifting — do not hand-wrap route elements in `<RequirePermission>`, and do not re-add a `permission` field to a nav entry that has a `path`. A route absent from the table is ungated, so every new route must be added either there or to `INTENTIONALLY_UNGATED` (with a reason); the parity tests in `routePermissions.test.ts` read `App.tsx` from disk and fail on anything unreviewed, on a stale entry, on a nav item the table does not cover, and on a permission key the backend does not define. Two ordering rules: `ModuleGate` stays **inside** the route elements, so permission is checked first and the module flag second ("you may not see this at all" outranks "this is switched off"); and `canAccessPath` consults permissions **only, never module flags** — those are async singletons that read `false` until loaded, so folding them in would bounce users off a page purely because a flag had not arrived yet. `/` must stay ungated: it is the fallback target for the catch-all, for both gates' Back buttons, and for the post-sign-in denial redirect, so gating it would leave some roles with no reachable page (`Dashboard` therefore also drops its Overview tab and opens on My Workspace when the role lacks `reports.ea_dashboard`).

- **Where a user lands after signing in is a security decision, not a convenience.** The login form renders *in place* at the requested URL (`App.tsx`'s unauthenticated catch-all `path="*"` — deliberately not a redirect, pinned by `App.test.tsx`), so email/password sign-in preserves a deep link for free. SSO does not: it navigates the document away to the identity provider and returns at `/auth/callback`. `frontend/src/lib/returnPath.ts` carries the path across that round trip in **sessionStorage**, never in the OAuth `state` — `state` comes back attacker-influenceable and would be an open-redirect vector, quite apart from landing in IdP logs and browser history. Every stored path goes through `sanitizeReturnPath` on **both** write and read (same-origin rooted path only; `//host`, `\`, control characters, absolute URLs and non-http schemes rejected; `/`, `/auth/*`, `/portal/*` and `/embed/*` map to the "no deep link" sentinel `null`). The value is single-use and shares the CSRF nonce's lifecycle exactly: written on every SSO click (which **clears** it when the path is not usable, so an abandoned attempt cannot hijack a later sign-in), consumed in `SsoCallback` before any early return so every failure path clears it too, and dropped on logout. Landing is fail-closed — an unreachable deep link goes to the dashboard with `state: { deniedPath }`, which `AppLayout` renders as a brief Snackbar.

- **The browser never holds the JWT — auth is an httpOnly cookie, and the frontend only tracks *whether* it is signed in.** Every endpoint that mints a session (`/auth/login`, `/register`, `/refresh`, `/sso/callback`, `/proxy/session`, `/impersonate`, `/stop-impersonating`) sets an `access_token` cookie via `_set_auth_cookie` (`backend/app/api/v1/auth.py`): `httponly`, `samesite="lax"`, `path="/api"`, `secure` auto-detected from `X-Forwarded-Proto`, expiring with `ACCESS_TOKEN_EXPIRE_MINUTES`. The browser then sends it on its own. So `api.*` attaches **no** `Authorization` header and passes `credentials: "same-origin"`; there is nothing in `sessionStorage` to read, and `setAuthenticated(value)` / `isAuthenticated()` in `client.ts` are an in-memory UI flag, not a token store. `setToken()` / `clearToken()` / `hasToken()` survive as legacy aliases over that flag — `setToken` ignores its argument entirely — so do not reach for them expecting a token to land anywhere. Two things depend on this and are why it is a cookie rather than a header: `httponly` keeps the token out of reach of any XSS, and the SSE stream is an `EventSource` (`useEventStream.ts`), which **cannot** set request headers and authenticates purely by the cookie riding along. `samesite="lax"` is the app's CSRF control, so a future cross-site POST surface needs its own token rather than a relaxed cookie. A caller outside the browser — the MCP server, a script, `curl` — still sends `Authorization: Bearer <token>`; `get_current_user` (`backend/app/api/deps.py`) reads the header first and falls back to the cookie.
