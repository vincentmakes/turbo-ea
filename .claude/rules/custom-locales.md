# Custom languages (admin-added UI locales)

> Loaded when you touch the custom-language service, routes, models, the frontend registry or its admin section (full list in the frontmatter).

- **A custom language is data; the ten built-in languages are code and stay exactly as they are.** `custom_locales` (code, native `name`, `english_name`, `rtl`, `enabled`, transient `translate_job`) and `custom_locale_strings` (one row per locale + namespace: `strings` `{flat_key: text}` and `meta` `{flat_key: {"h": source hash, "o": manual|ai|import|mcp}}`). A code must match `^[a-z]{2,3}(-[A-Z][a-z]{3})?(-[A-Z]{2})?$` with fullmatch semantics (`he`, `pt-BR`, `zh-Hant`; no trailing newline) — backend, frontend and MCP use the same pattern — and is never a built-in code. Any script, either direction: `rtl` is an explicit switch, off by default (the dialog only hints for `he, ar, fa, ur, yi, ps, sd, ug, dv`). Built-in locales keep their bundled files, `SUPPORTED_LOCALES` and `useEnabledLocales`; never route a built-in through the custom path, and never add a custom code to those lists. Adding a *bundled* language is the recipe in `i18n-locales.md`, not this. Scope is the 14 UI namespaces plus a 15th, `metamodel` (next bullet); the docs site is not covered.
- **The English catalogue is the source of truth on the backend too.** `app/services/language_pack.py` is pure (no DB, no FastAPI — a future community-pack CI reuses it) and reads `frontend/src/i18n/locales/en` (copied into the backend image at `/app/i18n/en`; `I18N_EN_DIR` overrides). A flat key is the English JSON path joined with `"."`. Missing catalogue at runtime: export, `GET`/`POST …/strings` and translate answer 503 `catalog_unavailable`; list, detail, create, patch and delete answer 200 with `stats: null` (the UI must cope); the bundle still serves what is stored.
- **One validator is the single gate for every untrusted value** — file import, AI output, MCP `submit_translations`, manual edits. Per key, with a reason code (`empty|too_long|placeholder_mismatch|nesting_mismatch|markup_not_in_source|url_not_in_source|control_chars|not_a_string`, plus `source_changed` / `source_hash_missing` for `metamodel`). A key English lacks is never a rejection on the wire: it is counted in `unknown` and named in `unknown_keys` (`[{namespace, key}]`, capped at 200; the count stays exact). The rules: the `{{placeholder}}` multiset and `$t(...)` references equal English's, no tag or URL that English lacks, no Unicode `Cc` character but `\n`/`\t` and no bidi override U+202D/U+202E — combining marks, ZWJ/ZWNJ, LRM/RLM and bidi isolates are accepted (Hindi, Persian, Hebrew, Thai need them) — and length ≤ `4 × English + 200` in code points. A rejected key never blocks the others. Never add a second, looser path that writes strings without it.
- **Staleness is a source-hash diff, never a timestamp.** `source_hash` = first 12 hex of sha256 of the English text, stored per key in `meta`. Status: `missing` (no value), `stale` (hash ≠ current English hash — still served, an old translation beats English), `translated`, `obsolete` (key gone from English: never served, pruned on write). An import that carries `source_hashes` stores those, so a pack made on an older version shows as stale where English moved. Plural keys beyond `_one`/`_other` are accepted as `<base>_<zero|one|two|few|many|other>` when `<base>_other` exists, validated against it; the bundle fills every category a pack does not carry (and an untranslated `_one`) from the pack's `<base>_other`, so a count never falls through to English.
- **Database labels are the `metamodel` namespace (`app/services/metamodel_strings.py`).** Same validator, statuses, routes and MCP tools; keys come from stable keys, never ids (`type.<k>.label`, `type.<k>.field.<f>.option.<o>`, `relation.<k>.reverse_label`, `category.<escaped>` …), free-text segments escaped so a key parses back. **The text lives where it already lives** — each record's own `translations` map under the custom code — so the existing resolvers render it unchanged; the `metamodel` row of `custom_locale_strings` holds only `meta`, except lifecycle phase help. **Writes go through the service, never the admin routes**, and change nothing but the custom code's entry of the addressed map (other locales, labels, order and every other JSON key stay byte-identical; reassign JSONB so it is flagged dirty; `cards.updated_at` does not move) — that is why locked built-ins (relation attributes, `_LOCKED_OPTION_FIELDS`, built-in categories, dashboards with no translation route) accept it. **Lifecycle phase help** for a custom code is kept in that row's `strings` (`lifecycle.<phase>`) and overlaid onto the bootstrap payload for enabled custom locales — only for phases that still have English text; `normalize_phase_help` and the stored setting are untouched. **Import rule for this namespace only**: a `source_hashes` entry that differs from the current English hash is skipped as `source_changed` (a translation of "Application" never lands on a renamed type). Who must give a hash: origin `import` — every `metamodel` entry, else `source_hash_missing` (every export mode writes hashes); origin `mcp` — honoured when given (`GET …/strings` items carry `source_hash` so the MCP tools forward it), applied without; origin `manual` — applied; the AI job always passes the hash of the English it translated. A value equal to the stored one is `unchanged`, decided before `source_changed`. A stored value with no `meta` entry (written by the field editor, a manifest or a workspace import) reads as `{h: current hash, o: manual}`, never stale, and that meta is persisted on the next write. **`mode=share`** export = UI namespaces as `current` plus only the `metamodel` entries whose key and English equal the built-in seed's (derived from `seed.py` with the same key builder) **and** whose stored hash equals the current one (rename → translate → rename back must not leak) — nothing installation-specific. **Extension manifests keep custom-language codes only**: on enable/update `extensions/field_contributions.py` lets the manifest win for the locales it carries and keeps a stored locale it lacks only when that locale is a `custom_locales` code — a built-in locale or group the manifest drops is dropped. Deleting a custom language clears its code from every metamodel record through `metamodel_strings.apply(…, None)` before the row goes. The AI job translates `metamodel` first and feeds the translated card-type names into the UI chunks' terminology. The public bundle leaves `metamodel` out.
- **The bundle has the shape of a built-in file.** `GET /custom-locales/{code}/bundle` rebuilds each namespace by walking the English tree, so i18next resolves it exactly like a bundled locale; it is public for an enabled locale (ETag = content hash, `If-None-Match` → 304) and `admin.settings`-only for a disabled one (else 404).
- **Never hold a DB session across an LLM call.** `custom_locale_translate.py` runs one in-process task per locale: read what to translate → commit/close → call the LLM → a fresh short session to merge the chunk and update `translate_job`. Chunks are ≤ 40 strings / ~6000 chars with numeric ids, not keys; every answer goes through the validator; `mode: "all"` skips `manual` strings unless `include_manual`. A job still `running` at startup is marked `interrupted`.
- **Every route is `admin.settings`**, every mutation goes through `audit_log.record`, `translate` is rate-limited, `users.locale` accepts only an *enabled* custom code, and deleting a locale resets its users to `en`. The AI suggestion language for a custom locale is its stored `english_name`, never client text.
- **MCP** (`list_custom_languages`, `get_untranslated_strings`, `submit_translations`, `start_ai_translation`, `stop_ai_translation`) lives in `mcp-server/turbo_ea_mcp/server.py` under the rules of `mcp-server.md`: `submit_translations` saves on its first call (`dry_run` defaults to `False`; the only tool in the backend's `CONFIRMATION_EXEMPT_TOOLS`, so no confirm token at any size), forwards `origin: "mcp"` to `POST …/strings`, caps at `MCP_MAX_TRANSLATIONS_PER_CALL` (2000), refuses `null` (clearing stays in the web app), attaches the source hashes `get_untranslated_strings` handed out (remembered per token digest + language in `hash_memory.py`; explicit `source_hashes` win; `get_untranslated_strings` returns them only with `include_source_hashes=True`), counts `accepted` per namespace without the backend's `unknown_keys` and returns those (the integer `unknown` passes through), refuses codes over 10 characters and is not reversible by `rollback_batch`; the language code is checked with the same pattern before any call. **Identical English is translated once**: `GET …/strings?collapse=true` lists each (source hash, plural category) once with `same_text`, and `POST …/strings` with `fill_identical: true` (default off on the route, on in the MCP tool) gives each accepted value to every other key with the same English and plural category that has **no value at all** — never overwriting a translation, whatever its origin — through `apply_strings` with the call's origin and `expected={key: None}` (conditional: a value written meanwhile, e.g. a metamodel label from the field editor, stays) (`store.collapse_identical` / `identical_text_fills` / `fill_identical`). A source whose given `source_hashes` entry is not the current hash fills nothing (its twins would read as current), and two different values for one text in one call fill nothing. Reported as `filled` / `fill_rejected`; the audit row carries both and its `namespaces` include the ones the fill reached. `start_ai_translation` (destructive: `all` + `include_manual` replaces hand corrections) / `stop_ai_translation` drive the server-side AI job (`POST …/translate`, `…/translate/cancel`) with the standard preview, since the job spends the provider's budget — the start's batch counts the strings, so it takes the confirm-token cycle above the threshold, with the token bound to the preview's language, mode and `include_manual` (`scope`); progress is `list_custom_languages`' `job`. Its translation instructions (which tell the translator to do `metamodel` first and reuse those names) mirror the export file's — change both together.
- **The community library is untrusted network input (`app/services/language_catalogue.py`, `GET /custom-locales/catalogue`, `POST …/catalogue/{code}/install`, both `admin.settings`, install rate-limited and audited as `admin.custom_locale.community_installed` — the constant lives in the route module, where the Security-log label guard reads actions).** `LANGUAGE_CATALOGUE_URL` (default the `index.json` of `vincentmakes/turbo-ea-translations`; empty = off) is fetched **only when an admin asks** — first read and `?refresh=true`, never on a timer or at startup — and cached in its own `catalogue_cache` row (`language_catalogue`), keyed by URL and re-validated on read. Every download: https only, no redirect to another host (≤ 3 same-host), `TIMEOUT`, size capped while streaming (index 1 MiB, pack 3 MB = the library's cap). **Nothing in `index.json` steers a download**: `pack_url` / `path` are ignored, the pack URL is derived from the configured URL and the `code_error`-checked code (`…/packs/<code>/pack.json`), with the ref replaced by the entry's commit on raw.githubusercontent.com. The index is validated per field (`parse_entry`; a bad entry dropped, a bad file `catalogue_invalid`); a pack must match the entry's `sha256`, parse without duplicate keys, be `mode: share` for the requested code and pass `validate_pack`'s file checks, and is merged by `apply_strings` with origin **`community`** (`store.ORIGIN_COMMUNITY`, in `FILE_ORIGINS` with `import`, so a `metamodel` entry needs its source hash); a `null` value is refused, never a clear; `instructions` is never read. First install creates the language **disabled** from the pack's header; an update keeps every `manual` string (`keep_manual`) unless `overwrite_manual`, and keeps the admin's name / switch / direction. `custom_locales.source` / `source_sha256` / `source_commit` (migration 178) record it — `update_available` is the recorded digest ≠ the index's — and travel in a workspace bundle, validated by `transfer_problem`. No session is open across a download: the service's orchestrators (`catalogue`, `install`) open their own short `async_session()`s and the route commits its auth read first; the install's writes are one transaction. Built-in codes are `language_pack.BUILT_IN_CODES` (`code_error`'s default), so the `validate` CLI the library runs refuses a pack for one; `settings.SUPPORTED_LOCALES` must equal it (test). Frontend: `CommunityLanguages` / `CommunityInstallDialog` (report = the shared `ImportReport`), `UnreviewedChip` on community rows, origin labels in the review table (`originLabel`).
- **Workspace transfer**: both tables transfer (the two JSONB blobs as JSON assets, `translate_job` excluded) and are matched by natural key — a language by `code` (an existing code is kept, its id remapped), a strings row by `(locale, namespace)` — never by preserved id; the importer validates the code and `english_name` like the route, so a bundle cannot create a built-in code. `metamodel_strings.apply` refuses a built-in code as defence in depth — follow `workspace-transfer.md`.
- **A regional or script variant does not inherit from a built-in language**: i18next runs with `load: "currentOnly"`, so `pt-BR` falls back to English, not to `pt` — the same as the database labels and what the admin UI reports as missing.
