# Relation types, relation rows and how every surface renders them

> Loaded when you touch `backend/app/services/relation_orientation.py`, `backend/app/api/v1/relations.py`, `backend/app/api/v1/reports.py`, `backend/app/api/v1/turbolens.py`, … (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

- **Several relation types may share an ordered card-type pair — so key by relation type, never by card-type pair.** The metamodel places no limit on how many relation types connect a given ordered `(source_type_key, target_type_key)` pair: an Organization that *owns* an Application and one that *uses* it are different relationships, each with its own verbs, `attributes_schema`, cardinality and filters. Relation *rows* stay keyed on `(type, source_id, target_id)` (see the idempotency rule below), which is what lets two types coexist between the same two cards. Attributes remain the right tool for **variants of one relationship** — a `single_select` on the relation type, set per relation (`usageType` on `relOrgToApp`, `flowDirection` on `relAppToInterface`, edited via `RelationAttributesEditor`) — and the admin create dialog says so with a non-blocking warning when a pair is already connected; a second relation type is for relationships that are genuinely distinct. The uniqueness check this replaced was lifted in 2.114.0 together with every consumer that assumed it, and those consumers are the pattern to copy:
  - **Anything grouping cards dedups by card id, not by relation.** `GET /reports/landscape` appended one item per *relation*, so a card reachable through two types was listed twice (`reports.py`).
  - **Anything enumerating relation types for a card type must not dedup by the other end.** `GET /reports/app-portfolio` kept a `seen_other_types` set and dropped the second type outright — the inventory grid's whole relation payload comes from there.
  - **Graph edges are keyed by `(card pair, relation type)`.** `GET /reports/dependencies` and the two TurboLens architect graphs (`turbolens.py`) dedupe on `min:max:type`, so each type contributes its own edge with its own verb; two rows of the *same* type still collapse. **Every renderer that draws lines draws one per relation type**: `layeredDependencyLayout.ts` (each line keeps its own verb, `flowDirection` and description; `routeLdvEdges` already allocates handles per edge, and the same-lane horizontal shortcut has a single fixed handle pair so only the first edge of a pair may take it) and the diagram canvas (`insertRelationEdges` in `drawio-shapes.ts` — one vertex per child, one edge per relation, fanned onto the orthogonal router because the default ER router ignores anchors and would superimpose them). A fan is **two** waypoints per line, not one (`fanWaypoints`): a single mid-run point pinches the lines back together at both cards, so a pair separated only at the very middle and still read as one line. Two give each relation a parallel corridor over the middle half of the run, carrying its verb out there with it. The offset is **perpendicular to the dominant axis** — offsetting a vertically-stacked pair in `y` moves both lines along the same corridor and separates nothing — with the single-point pinch kept only as the fallback for cards too close to route between. The **dependency tree is the deliberate exception**: `buildAdjacency` (`dependencyAdjacency.ts`) merges per neighbouring card and joins verbs with `" / "`, because a tree renders one child per *card* — that is structural, not a style choice, so do not "fix" the two into agreement.
  - **The inventory grid keeps one column per *related card type*** (its persisted column state, bookmarks and `rel_<CardType>` deep links depend on that key), and handles the fan-out beneath it: the cell shows the union across the group (`relatedRefsOf`), the editor opens one section per relation type with per-section `excludeIds` (`RelationCellPopover`), and the sidebar builds **facets per relation type** from the non-deduped list, disambiguating same-target rows by verb.
  - **Card detail keeps one section per relation type, ordered so same-target sections are contiguous.** The per-type group is load-bearing (mandatory warning, cardinality chip, descendant roll-up, subtype toggle, its own Add button), so `RelationsSection` does not merge — it sorts. `orderRelationTypesByOtherEnd` (`lib/relationSort.ts`) is a stable group-by anchored on each other-type's **first** appearance, applied once to `relevantRTs` so the displayed groups, the hidden-but-populated block and the Add menu all inherit it; `sort_order` alone is flat and knows nothing about pairs, so `owns Application` and `uses Application` could otherwise land at opposite ends. Adjacency is only half of it: a card reached through several types still renders one row per group, so `multiLinked` marks each of those rows with the other verbs (`relations.alsoLinked`). Read the direction **per row** (`r.source_id === fsId`), never off the type's static side flag — that is what `otherEnd` exists for. **A self-referencing type is two sides, everywhere.** "Am I the source" derived from the *type* (`rt.source_type_key === cardTypeKey`) is true at both ends of such a type, which is how *has site* / *is site of* rendered as one group under the forward verb on both cards, the target-side visibility/mandatory flags became unreachable, and the Add dialog could only ever create the outgoing row (reported by a user against 2.117.0, fixed in 2.117.1). The side helpers in `lib/relationSort.ts` are the one vocabulary: `expandSides(rts, cardTypeKey)` (one side for a cross-type rt, two adjacent sides for a self-pair), `onSide(r, key, myId, isSource)` (the per-row predicate), `sideKey(rt, isSource)` / `parseSideKey` (a cross-type rt keeps its bare key so persisted filters and deep links keep resolving; a self-pair takes `<key>__out` / `<key>__in`, the suffix the inventory's mass edit already used). Every surface consumes them the same way — card detail (`RelationsSection` groups per side, `sideFlags` and `AddRelationsDialog` take `isSource` as a **required** input and never derive it), the inventory (`buildRelationIndex` indexes every end whose card is the selected type; the sidebar facets, the cell popover's sections and `relationsMap` entries are per side), the reports (`app_relations[*].direction` and the heatmap's `related_by_rel_type` side keys; `relationOnSide` is the matcher), and the descendant roll-up (`(type, direction)` buckets, `direction` on `DescendantRelationSummaryEntry`, the `already_linked` suppression keyed per side so a direct outgoing link cannot hide an incoming roll-up). Where a surface unions both directions on purpose (a portal's relation filter), it says so by carrying both verbs.
  - **Where "first match wins" is unavoidable, make the order explicit** — `build_group_map` (`ppm_portfolio_service.py`) sorts candidate relation types by `(sort_order, key)` rather than relying on row order.
  
  Still true after the lift: relation type **keys** are unique, the workspace-transfer applier and the platform-migration importer both accept duplicate pairs (they agree by deletion of the old check), and `deriveRelationKey` (`features/admin/metamodel/helpers.ts`) keeps a pair's keys as one family — the first relation on a free pair is `<Source>To<Target>`, a second anchors on the pair's existing key plus the verb (`relOrgToApp` + "owns" → `relOrgToAppOwns`), with a numeric suffix only as the fallback. The key is never made read-only: it is absent from `update_relation_type`'s `updatable` list and has no field in the edit dialog, so creation is the *only* chance to choose what becomes an Excel column, a calculation variable and a survey field key. Guard tests: `backend/tests/api/test_reports_multi_relation_types.py`, `test_metamodel.py::test_multiple_relation_types_per_pair_allowed`, `frontend/src/features/inventory/RelationCellPopover.test.tsx`, `features/reports/dependencyAdjacency.test.ts`, `features/admin/metamodel/relationAutoKey.test.ts`, `lib/relationSort.test.ts`, `features/cards/sections/RelationsSection.test.tsx`.

- **Creating a relation is idempotent on `(type, source_id, target_id)`.** `POST /relations` reuses an existing row and merges any supplied `attributes` / `description` onto it rather than inserting a second identical relation — matching what `POST /relations/bulk` has always done. The single-relation path lacked this, so drawing an edge on a diagram between two cards that were *already* related silently forked the inventory into duplicates (#905). There is deliberately **no** DB unique constraint: the invariant is owned at the application layer on every write path, and a hard constraint would turn a future edge case into a 500 rather than a merge. Migration `131_dedupe_relations.py` merged the duplicates existing installs already carried (oldest row wins, attributes/description folded in).

- **Every relation is stored in its relation type's direction.** A relation type runs one way (`relAppToInterface`: Application → Interface) and every surface reads a row that way round: card detail and the inventory list it under the side the card sits on (`onSide`, `relationIndex`), and its attributes mean something on that axis — `flowDirection` `forward` is offered as the Application being *Provider*. The UI always sends the ends right, but the API accepted card ids without checking them against the type, so rows stored the other way round (an Interface as the source) reached installs through `/relations/bulk` id refs, the MCP server, the extension bridge, workspace import, the Excel Relations sheet and the pre-2.39.1 diagram editor. Such a row was listed on neither card — users re-added the link, forking a duplicate — and its arrow drew a provider as a consumer ([#1140](https://github.com/vincentmakes/turbo-ea/discussions/1140), fixed in 2.149.3). `app/services/relation_orientation.py` is the one rule: `runs_against_type` (pure, the mirror of the frontend `runsAgainstType`; never true for a self-referencing type, false when anything is unknown), `oriented` for a caller that already knows both card types, `orient_endpoints` (one query) for one that does not, and `direction_for` for a caller that looks rows up **per side** before writing — the survey apply path takes the side from the relation type, not the field, so its lookup and its insert agree. **Every write path turns a swapped pair before any lookup**, silently and with the attributes kept exactly as sent: `card_write_service.upsert_relation` (so `POST /relations` and the extension bridge merge a swapped request into the existing row — the idempotency above), `apply_relation_operations` (the upsert, the **delete** and the cardinality guards all key on the oriented pair), survey apply, the TurboLens commit, the workspace applier and the platform-migration apply (which reuses a row the turn lands on instead of inserting). Correcting rather than rejecting is deliberate: an import or an integration that got the order wrong still lands what it meant. Migration `153_orient_relations_to_their_type.py` repaired existing rows with migration 131's merge rule, keeping `flowDirection` unchanged. `test_relation_orientation.py::test_every_relation_writer_orients` scans `backend/app` for `Relation(` and fails on any module that neither imports `relation_orientation` nor sits in its allowlist with the reason its direction is fixed — add a new writer there or it will not build. Guard tests: `tests/services/test_relation_orientation.py`, `test_alembic_153_orient_relations.py`, `tests/api/test_relations.py::TestCreateRelationOrientation`, `test_relations_bulk.py`, `test_workspace_io_roundtrip.py::test_import_stores_a_backwards_relation_in_its_type_direction`.

- **A relation type is named by its VERB wherever it sits among other relation types; the Predecessors / Successors nouns belong to ONE section.** The verb comes from `useRelationLabel()` / `relationLabel(rt, locale, reverse)`, read from the side under view (`reverse=true` when the card is at the target end) — in the inventory's filter facets and mass-edit picker, `RelationCellPopover`, card detail's Relations groups, the Survey Builder's relation list and the survey forms downstream of it, portals, the calculation token catalogue, the Portfolio / Capability Map / Matrix facets and legends, the diagram relation picker, and the Layered Dependency View's edges. The reason is **parallel structure**: those lists are heterogeneous and a verb is the only part of speech every relation type has, so one noun among them reads as a different kind of thing — and you cannot turn `uses` into a noun to match it. This is Jira's inward/outward link model, which `label` / `reverse_label` mirrors exactly. The **one exception** is card detail's dedicated Lineage section (`SuccessorsSection.tsx`, `cards:successors.*`), which heads its two sub-lists **Predecessors** / **Successors**: it holds a single relation type, so there is nothing to be non-parallel with, its headings name two collections of cards rather than enumerate types, and the nouns are the vocabulary EA practitioners bring from LeanIX. **Lineage is UI-isolated in only six lists** — card-detail Relations, `AddRelationsDialog`, `DescendantRelationsDrawer`, the Metamodel admin Relations tab, `MetamodelGraph`, `TypeDetailDrawer` (all via `successorRelationKeys`, `frontend/src/lib/successorRelation.ts`) — and nowhere else, which is exactly why its verb has to work in a mixed list. Relabelling the Survey Builder's lineage rows to the nouns was #1091's second-guess fix and was reverted for this reason. If a verb reads badly, fix it in the metamodel — it is admin-editable and there is one definition. Full rule: `frontend/UI_GUIDELINES.md` §3.13.

- **Every relation edge on a diagram is built by `relationEdgeStyle` — there is exactly one renderer.** `frontend/src/features/diagrams/drawio-shapes.ts` owns the style of a relation edge and every path that draws one goes through it: the relation picker (`stampEdgeAsRelation`), the pending→synced switch (`markEdgeSynced`), expansion from the inventory (`expandCardGroup` / `insertChildVertex`), the delete-undo path (`restoreRemovedEdge`) and the LDV "Create diagram" serialiser (`buildLdvDiagramXml`). They each used to hand-roll a near-identical style string and they drifted, so the *same* relation rendered two ways depending on how it reached the canvas — grey with a verb when drawn by hand, card-coloured with no label at all when retrieved with `+` (#905, fixed in 2.39.1). Three invariants the builder encodes: an edge is drawn in the one neutral `RELATION_EDGE_COLOR`, **never** the related card's colour (an edge *is* a relation; tinting it by card type restates the node and hurts a dense landscape); direction is shown by moving the **arrowhead** (`startArrow` vs `endArrow`), never by flipping the mxGraph endpoints — expansion always inserts parent→child and expand/collapse plus the sync side-table key off that; and the verb is **always the forward label** — `relationLabel(rt, locale)`, never the reverse form. An edge on a canvas has no "card you started from": a reader sees a line with an arrowhead and reads it in the arrow's direction, and since the arrowhead always marks the relation's *target*, the sentence along the arrow is always source-verb-target. Resolving it from the expanded card instead made one relation read two ways depending on which end you expanded from — "uses" from the Organization, "is used by" from the Application — which is the #905 complaint one level deeper. `layeredDependencyLayout.ts` is forward-only for the same reason (both of its label branches collapse to `e.label`), so this is what keeps the diagram and the LDV agreeing; `humanRelationLabel` (the delete-confirm dialog and the side-table) was always forward-only too. When the relation type declares a `flowDirection` attribute *and* the relation has a value, `flow` decides the arrowhead instead of `incoming` (`forward` → target end, `reverse` → source end, `bidirectional` → both), matching what `layeredDependencyLayout.ts` already draws — this is what distinguishes an Application that *provides* an Interface from one that *consumes* it, since `relAppToInterface`'s label carries both verbs. `flow` means something on the **relation type's** source→target axis while the edge may be drawn the other way, so `relationArrowParts` XORs it with `incoming` rather than reading either alone. **The type's axis, not the stored row's.** Card detail offers `forward` as the Application being *Provider*, but several write paths accept ids without checking them against the type (the Excel Relations sheet, `/relations/bulk` id refs, the MCP server, the extension bridge, workspace import, the pre-2.39.1 diagram editor), so a `relAppToInterface` row can be stored Interface → Application — and read on the row, its provider drew as a consumer in the LDV, its "Create diagram" export and expansion ([#1140](https://github.com/vincentmakes/turbo-ea/discussions/1140), fixed in 2.149.3). `runsAgainstType(rt, sourceType, targetType)` (`lib/relationSort.ts`) is the one test for such a row (never true for a self-referencing type), and every arrow renderer reads it as if stored the type's way: the LDV turns its edges once on entry (`orientEdgesToRelationTypes`, `ldvLayoutShared.ts`, applied in `LayeredDependencyView` so both layouts and the export inherit it), expansion derives `incoming` through `edgeIncoming` (`expandChildren.ts`), and the stale check's flow restyle XORs `runsAgainst`. Since the same release no such row can be written or survive (see *Every relation is stored in its relation type's direction* under Backend Conventions), so on current data these are no-ops — they stay as the safety net for a row that arrives by a path nobody has thought of yet, and for a diagram edge synced to one before the repair. Guard tests: `features/reports/ldvOrientation.test.ts`, `lib/relationSort.test.ts`, `features/diagrams/expandChildren.test.ts`, `staleCheck.test.ts`. Gate on `flowDirectionBadge(rt, attrs)` (the same helper Card Detail buckets Provider/Consumer with) so the canvas and the card can't disagree, and stamp the value onto the edge user-object — `markEdgeSynced` reads it back rather than taking it as an argument, so the pending→synced restyle cannot drop it. A reversed pick is stamped `reversed="1"` on the edge user-object and `scanDiagramItems` surfaces it, because sync must swap `source_id`/`target_id` before POSTing — without it the relation is created backwards.
