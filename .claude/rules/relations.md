# Relation types, relation rows and how every surface renders them

> Loaded when you touch `backend/app/services/relation_orientation.py`, `backend/app/api/v1/relations.py`, `backend/app/api/v1/reports.py`, `backend/app/api/v1/turbolens.py`, … (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

- **Several relation types may share an ordered card-type pair — so key by relation type, never by card-type pair.** The metamodel places no limit on how many relation types connect a given ordered `(source_type_key, target_type_key)` pair: an Organization that *owns* an Application and one that *uses* it are different relationships, each with its own verbs, `attributes_schema`, cardinality and filters. Relation *rows* stay keyed on `(type, source_id, target_id)` (see the idempotency rule below), which is what lets two types coexist between the same two cards. Attributes remain the right tool for **variants of one relationship** — a `single_select` on the relation type, set per relation (`usageType` on `relOrgToApp`, `flowDirection` on `relAppToInterface`, edited via `RelationAttributesEditor`) — and the admin create dialog says so with a non-blocking warning when a pair is already connected; a second relation type is for relationships that are genuinely distinct. The uniqueness check this replaced was lifted in 2.114.0 together with every consumer that assumed it, and those consumers are the pattern to copy:
  - **Anything grouping cards dedups by card id, not by relation.** `GET /reports/landscape` appended one item per *relation*, so a card reachable through two types was listed twice (`reports.py`).
  - **Anything enumerating relation types for a card type must not dedup by the other end.** `GET /reports/app-portfolio` kept a `seen_other_types` set and dropped the second type outright — the inventory grid's whole relation payload comes from there.
  - **Graph edges are keyed by `(card pair, relation type)`.** `GET /reports/dependencies` and the two TurboLens architect graphs (`turbolens.py`) dedupe on `min:max:type`, so each type contributes its own edge with its own verb; two rows of the *same* type still collapse. **Every renderer that draws lines draws one per relation type**: `layeredDependencyLayout.ts` (each line keeps its own verb, `flowDirection` and description; `routeLdvEdges` already allocates handles per edge, and the same-lane horizontal shortcut has a single fixed handle pair so only the first edge of a pair may take it) and the diagram canvas (`insertRelationEdges` in `drawio-shapes.ts` — one vertex per child, one edge per relation, fanned onto the orthogonal router because the default ER router ignores anchors and would superimpose them). A fan is **two** waypoints per line, not one (`fanWaypoints`): a single mid-run point pinches the lines back together at both cards, so a pair separated only at the very middle and still read as one line. Two give each relation a parallel corridor over the middle half of the run, carrying its verb out there with it. The offset is **perpendicular to the dominant axis** — offsetting a vertically-stacked pair in `y` moves both lines along the same corridor and separates nothing — with the single-point pinch kept only as the fallback for cards too close to route between. The **dependency tree is the deliberate exception**: `buildAdjacency` (`dependencyAdjacency.ts`) merges per neighbouring card and joins verbs with `" / "`, because a tree renders one child per *card* — that is structural, not a style choice, so do not "fix" the two into agreement.
  - **The inventory grid has one column per relation-type *side*, headed "<verb> <Card type>"** (discussion #1373, 2.198.0). It used to keep one column per *related card type* whose cell was the union of every relation type to that type, so *uses* and *consumes* IT Component, or both directions of a self-pair, read as one list. `relationColumnSides` (`features/inventory/relationColumns.ts`) is the one list the grid, `defaultColumns` and the sidebar's Columns tab consume — `orderRelationTypesByOtherEnd` then `expandSides`, so same-target columns are adjacent and a self-pair is an `__out` and an `__in` column; the column id is **always direction-qualified**, `rel_<key>__out` from the source type and `rel_<key>__in` from the target type, cross-type relations included (`relationColumnId`) — the column selection, order, freeze and layout are one set shared by every card type's inventory, so a bare `rel_<key>` would be the same id at both ends and unticking *uses Application* on Organization would hide *is used by Organization* on Application. The cell reads its own `relationsMap` entry by `sideKey` (`relatedRefsOnSide`), the header and the Columns-tab row are `relationSideLabel` (also the query path strip's hop menu), and the edit click hands `RelationCellPopover` that one relation type **and its `isSource`**, so the dialog shows that side alone. Persisted `rel_<CardType>` ids (prefs, saved views' `columns` / `column_state` / `column_filter_model`, sort) are translated on load by one effect in `InventoryPage` (`migrateLegacyRelation*`). The old id meant "the <CardType> column" on **every** card type related to it, so the shared slices — selection, order, freeze, widths — are translated **metamodel-wide** from all relation types (`legacyRelationColumnMap`: per relation type with that card type at one end, the id seen from the other end — target → `__out`, source → `__in`, a self-pair both), in place, as soon as the relation types load and whatever type is selected; translating under the selected type alone lost the column on every other type. The sort and the column filters describe the grid on screen and resolve against the selected type's own sides: a sort (also a layout entry's `sort`) moves to the first side, a column filter is renamed when its card type has one side and dropped when it has several (a text filter over a merged cell cannot be split without changing which rows match). A new id always ends in `__out` / `__in`, so it never collides with a legacy one; an id that resolves to nothing is left alone. The relation **filter** vocabulary is separate and unchanged: `rel_<CardType>=` deep links, `relTypeGroupMap` / `relatedRefsOf` and `normalizeRelationFilterKeys` still think in card types, and the sidebar builds **facets per relation type** (and side) from the non-deduped list, disambiguating same-target rows by verb.
  - **Card detail keeps one section per relation type, ordered so same-target sections are contiguous.** The per-type group is load-bearing (mandatory warning, cardinality chip, descendant roll-up, subtype toggle, its own Add button), so `RelationsSection` does not merge — it sorts. `orderRelationTypesByOtherEnd` (`lib/relationSort.ts`) is a stable group-by anchored on each other-type's **first** appearance, applied once to `relevantRTs` so the displayed groups, the hidden-but-populated block and the Add menu all inherit it; `sort_order` alone is flat and knows nothing about pairs, so `owns Application` and `uses Application` could otherwise land at opposite ends. Adjacency is only half of it: a card reached through several types still renders one row per group, so `multiLinked` marks each of those rows with the other verbs (`relations.alsoLinked`). Read the direction **per row** (`r.source_id === fsId`), never off the type's static side flag — that is what `otherEnd` exists for. **A self-referencing type is two sides, everywhere.** "Am I the source" derived from the *type* (`rt.source_type_key === cardTypeKey`) is true at both ends of such a type, which is how *has site* / *is site of* rendered as one group under the forward verb on both cards, the target-side visibility/mandatory flags became unreachable, and the Add dialog could only ever create the outgoing row (reported by a user against 2.117.0, fixed in 2.117.1). The side helpers in `lib/relationSort.ts` are the one vocabulary: `expandSides(rts, cardTypeKey)` (one side for a cross-type rt, two adjacent sides for a self-pair), `onSide(r, key, myId, isSource)` (the per-row predicate), `sideKey(rt, isSource)` / `parseSideKey` (a cross-type rt keeps its bare key so persisted filters and deep links keep resolving; a self-pair takes `<key>__out` / `<key>__in`, the suffix the inventory's mass edit already used). Every surface consumes them the same way — card detail (`RelationsSection` groups per side, `sideFlags` and `AddRelationsDialog` take `isSource` as a **required** input and never derive it), the inventory (`buildRelationIndex` indexes every end whose card is the selected type; the sidebar facets, the cell popover's sections and `relationsMap` entries are per side), the reports (`app_relations[*].direction` and the heatmap's `related_by_rel_type` side keys; `relationOnSide` is the matcher), and the descendant roll-up (`(type, direction)` buckets, `direction` on `DescendantRelationSummaryEntry`, the `already_linked` suppression keyed per side so a direct outgoing link cannot hide an incoming roll-up). Where a surface unions both directions on purpose (a portal's relation filter), it says so by carrying both verbs.
  - **Where "first match wins" is unavoidable, make the order explicit** — `build_group_map` (`ppm_portfolio_service.py`) sorts candidate relation types by `(sort_order, key)` rather than relying on row order.
  
  Still true after the lift: relation type **keys** are unique, the workspace-transfer applier and the platform-migration importer both accept duplicate pairs (they agree by deletion of the old check), and `deriveRelationKey` (`features/admin/metamodel/helpers.ts`) keeps a pair's keys as one family — the first relation on a free pair is `<Source>To<Target>`, a second anchors on the pair's existing key plus the verb (`relOrgToApp` + "owns" → `relOrgToAppOwns`), with a numeric suffix only as the fallback. The key can never be changed: it is absent from `update_relation_type`'s `updatable` list, and the edit dialog shows it read-only (with where Excel uses it, #1406) but has no editable field for it, so creation is the *only* chance to choose what becomes an Excel column, a calculation variable and a survey field key. - **Creating a relation is idempotent on `(type, source_id, target_id)`.** `POST /relations` reuses an existing row and merges any supplied `attributes` / `description` onto it rather than inserting a second identical relation — matching what `POST /relations/bulk` has always done. The single-relation path lacked this, so drawing an edge on a diagram between two cards that were *already* related silently forked the inventory into duplicates (#905). There is deliberately **no** DB unique constraint: the invariant is owned at the application layer on every write path, and a hard constraint would turn a future edge case into a 500 rather than a merge. Migration `131_dedupe_relations.py` merged the duplicates existing installs already carried (oldest row wins, attributes/description folded in).

- **Every relation is stored in its relation type's direction.** A relation type runs one way (`relAppToInterface`: Application → Interface) and every surface reads a row that way round: card detail and the inventory list it under the side the card sits on (`onSide`, `relationIndex`), and its attributes mean something on that axis — `flowDirection` `forward` is offered as the Application being *Provider*. The UI always sends the ends right, but the API accepted card ids without checking them against the type, so rows stored the other way round (an Interface as the source) reached installs through `/relations/bulk` id refs, the MCP server, the extension bridge, workspace import, the Excel Relations sheet and the pre-2.39.1 diagram editor. Such a row was listed on neither card — users re-added the link, forking a duplicate — and its arrow drew a provider as a consumer ([#1140](https://github.com/vincentmakes/turbo-ea/discussions/1140), fixed in 2.149.3). `app/services/relation_orientation.py` is the one rule: `runs_against_type` (pure, the mirror of the frontend `runsAgainstType`; never true for a self-referencing type, false when anything is unknown), `oriented` for a caller that already knows both card types, `orient_endpoints` (one query) for one that does not, and `direction_for` for a caller that looks rows up **per side** before writing — the survey apply path takes the side from the relation type, not the field, so its lookup and its insert agree. **Every write path turns a swapped pair before any lookup**, silently and with the attributes kept exactly as sent: `card_write_service.upsert_relation` (so `POST /relations` and the extension bridge merge a swapped request into the existing row — the idempotency above), `apply_relation_operations` (the upsert, the **delete** and the cardinality guards all key on the oriented pair), survey apply, the TurboLens commit, the workspace applier and the platform-migration apply (which reuses a row the turn lands on instead of inserting). Correcting rather than rejecting is deliberate: an import or an integration that got the order wrong still lands what it meant. Migration `153_orient_relations_to_their_type.py` repaired existing rows with migration 131's merge rule, keeping `flowDirection` unchanged. `test_relation_orientation.py::test_every_relation_writer_orients` scans `backend/app` for `Relation(` and fails on any module that neither imports `relation_orientation` nor sits in its allowlist with the reason its direction is fixed — add a new writer there or it will not build. Guard tests: `tests/services/test_relation_orientation.py`, `test_alembic_153_orient_relations.py`, `tests/api/test_relations.py::TestCreateRelationOrientation`, `test_relations_bulk.py`, `test_workspace_io_roundtrip.py::test_import_stores_a_backwards_relation_in_its_type_direction`.

- **A relation may carry its own lifecycle, and a relation that is not in effect today does not COUNT — while every row stays listed for the person managing it.** `relations.lifecycle` (JSONB, migration 179, the five card phases; `{}` = always in effect) is validated on every write by `normalize_relation_lifecycle`. "In effect on a day" has one definition in `backend/app/services/lifecycle.py`, the frontend's `isAliveAtDate` unchanged: started (`active` arrived; with no `active`, a `plan` / `phaseIn` date means not yet) and not retired (`endOfLife` arrived, inclusive). It has three twins: `lifecycle_in_effect` (Python), `lifecycle_in_effect_sql(entity, today=)` (SQL over `Relation` or an alias — text comparison behind the date regexp, two-valued so it is safe to negate) and `live_relations_in_fiscal_year` (the cost reports' `is_live_in_fiscal_year` applied to the relations they sum or group through, at fiscal-year granularity like their cards). Every reader of the `Relation` model is one of two kinds. **Current-state** — counts, flags, aggregates, formulas, scores, anything published or shown as "the landscape now" — applies the definition: the orphaned flag (`card_flags.connected_card_ids` / `orphaned_condition`, shared with the Data Quality KPI), the dashboards' relation flags, dimensions and `@relations` measure and the card query's hops (`dashboard_query.relation_exists` / `relation_join`, `today=` threaded), the formula context (`relations[...]`, `relation_count`), mandatory-relation completeness (`card_completeness.load_link_facts`), `/reports/landscape`, `/matrix`, `/data-quality`, `/eol`, `/cost-treemap`, a card's `relation-summary` and descendant roll-up, the bulk path's cardinality guard (an ended or planned relation takes no room), portals (`portal_card_filters._related`, `web_portals`), survey targeting by related card, the BPM reports and process map, PPM grouping, the TurboLens loaders and graphs, and the extension data bridge (unless `include_inactive`). **All-time** — row lists a person manages (`GET /relations`, which returns `lifecycle`), writers that look a row up before writing (the idempotent create, survey apply — whose field must show every row or a submit would delete the hidden ones —, BPM element sync, catalogue, migration), rollback, archive impact, metamodel instance counts, workspace and platform exports (both carry `lifecycle`; a workspace or content-pack import validates it through `normalize_relation_lifecycle`, dropping an invalid value to `{}` with a note in the section's errors), and the three time-travel payloads (`/reports/dependencies`, `portfolio_payload`, `/reports/capability-heatmap`), which the client filters at the travelled date — returns every row. `tests/services/test_relation_lifecycle_guard.py` scans every function under `app/` that names the model (through any import alias) and fails one that neither applies a twin nor sits in `ALL_TIME` / `APPLIED_BY` with its reason; a stale entry fails too. **Time passing is not a write**: calculated fields and data-quality scores are stored, so `services/relation_lifecycle_sweep.py` (started by `_relation_lifecycle_sweep_loop` in `main.py`, a minute after boot and then at 00:05 UTC) finds the relations whose `active` or `endOfLife` date fell in `(last swept day, today]` — only those two dates flip "in effect" — and recalculates both ACTIVE end cards through `card_write_service.recalculate_and_rescore` (the write paths' function, so PPM-owned `costBudget` / `costActual` are never overwritten) inside `derived_maintenance` (no card event, no `updated_at` move) — ONE short transaction per card, the card loaded `with_for_update()` and fresh (`populate_existing`) and re-checked ACTIVE, so an edit committed meanwhile is read rather than overwritten; a failing card is logged and counted and never stops the rest, and the marker advances only when every card succeeded (otherwise the next run repeats the window). The last swept day is `general_settings.relationLifecycleSweptThrough`, written by key in SQL, the first run sweeps today only and catch-up is capped at 366 days; it is instance-local state — `workspace_io/secrets.py` `INSTANCE_LOCAL_GENERAL_KEYS` keeps it out of an export and out of an import, so a bundle cannot make a target skip its pending days. A dashboard query threads its own day (`run_query(today=)`, `Window.today`) into every relation reader — flags, the orphaned flag, `related:` pairs, the `@relations` measure and the sankey. `relation_types.lifecycle_enabled` governs **only** whether the UI offers the date editor: dates written by an import, the API, MCP or an extension are stored and counted regardless. A pair still has one row (the idempotency rule above), so a relation has one interval — re-adoption after a gap is not expressible. Guard tests: `tests/services/test_relation_lifecycle_guard.py`, `test_relation_lifecycle_readers.py`, `test_relation_lifecycle_sweep.py`, `tests/api/test_relation_lifecycle_readers.py`, `test_reports_cost_fiscal_year.py::TestCostTreemapRelationLifecycle`, `tests/services/test_lifecycle.py`. **The client side has the same one definition**: `frontend/src/lib/relationLifecycle.ts` (`relationLifecycleState` / `isRelationInEffect` over `isAliveAtDate`, `lib/lifecycleAtDate.ts`). Surfaces that show the landscape now read it at `todayLifecycleMs()` — UTC midnight of the **UTC** day, never the viewer's local day, because the server cannot follow a per-user day and every count it computes uses the UTC day (`_utc_today`) — card detail's rows and counts, the diagram's expand, the card's Dependencies section (`LayeredDependencySection` keeps only edges in effect today), the inventory's relation index (`buildRelationIndex` indexes in-effect relations only, so cells, facets and counts agree with the server; `RelationCellPopover` still lists every row from `GET /relations` with a `RelationPhaseChip`, so an ended relation is never re-added) and the PPM board's and the Lifecycle report's filters (`portfolio_payload.relations_in_effect_now`, shared by `ppm_portfolio_service.card_filter_payload` and `roadmap_from_portfolio`, drops what is not in effect and strips the dates server-side). The time-travel surfaces read it at the travelled date: the Dependencies report (`edgesAtDate`, `features/reports/dependencyEdgesAtDate.ts` — planned follows "preview planned", ended "keep retired", through `relationAtDate` in `timelineRange.ts`; an edge drawn despite not being in effect carries `relationState`, which the LDV draws in its own slot beside `severed` in `ldvEdgeStroke` / `edgeColors`, and the view itself stamps it from `lifecycle` at `asOfMs` via `withRelationStates`), the Portfolio report (`relationsAtDate` in `portfolioHelpers.ts` projects every card to its relations in effect at the date before grouping, filtering and colouring) and the Capability Map (`capabilityLinkInEffect` / `capabilityIdsAtDate`, `capabilityLinks.ts`, in `buildTree` and the split cost share; its relation filters match through `appRelationsAtDate` over each application's `related_link_lifecycles`). The three payloads that carry the dates: each `GET /reports/dependencies` edge (`lifecycle`, plus `in_effect_only=true` for "now" — the MCP `analyze_impact` sends it), each `portfolio_payload` `app_relations` entry (`lifecycle`, per side — `_relation_entry`) each capability-heatmap item's `app_link_lifecycles` (`{app_id: [lifecycle, …]}` for a pair whose every linking relation is dated) and each of its applications' `related_link_lifecycles` (`{relation-type key per side: {related id: [lifecycle, …]}}`, same rule, beside `related_by_type` / `related_by_rel_type`); an undated relation carries no key, which reads as always in effect. The heatmap's own `app_count` / `total_cost` (split denominator included) / `risk_count` are current-state — pairs in effect today (`link_keys_in_effect`), what the MCP `get_capability_heatmap` returns — while its `apps` lists stay complete for the client. **A collapse of several rows into one dated item never understates the relation**: `/reports/dependencies` folds two rows of one type between one pair (either direction) into the row with the largest `lifecycle_breadth` — undated if any row is, else one in effect today, else the one ending latest (no end is latest), ties to the smaller id — so the result never depends on row order. Relation dates also feed the slider: `computeTimelineRange` / `computeTimelineMilestones` take optional relation lifecycles (milestones count them as `linking` / `unlinking`, never as cards, so the pills keep naming cards) and `computeConnectionChanges` reads an edge's `lifecycle`. A published portal never sees any of it: its routes query relations themselves, in effect today only, and send no dates. - **A relation type is named by its VERB wherever it sits among other relation types; the Predecessors / Successors nouns belong to ONE section.** The verb comes from `useRelationLabel()` / `relationLabel(rt, locale, reverse)`, read from the side under view (`reverse=true` when the card is at the target end) — in the inventory's filter facets and mass-edit picker, `RelationCellPopover`, card detail's Relations groups, the Survey Builder's relation list and the survey forms downstream of it, portals, the calculation token catalogue, the Portfolio / Capability Map / Matrix facets and legends, the diagram relation picker, and the Layered Dependency View's edges. The reason is **parallel structure**: those lists are heterogeneous and a verb is the only part of speech every relation type has, so one noun among them reads as a different kind of thing — and you cannot turn `uses` into a noun to match it. This is Jira's inward/outward link model, which `label` / `reverse_label` mirrors exactly. The **one exception** is card detail's dedicated Lineage section (`SuccessorsSection.tsx`, `cards:successors.*`), which heads its two sub-lists **Predecessors** / **Successors**: it holds a single relation type, so there is nothing to be non-parallel with, its headings name two collections of cards rather than enumerate types, and the nouns are the vocabulary EA practitioners bring from LeanIX. **Lineage is UI-isolated in only six lists** — card-detail Relations, `AddRelationsDialog`, `DescendantRelationsDrawer`, the Metamodel admin Relations tab, `MetamodelGraph`, `TypeDetailDrawer` (all via `successorRelationKeys`, `frontend/src/lib/successorRelation.ts`) — and nowhere else, which is exactly why its verb has to work in a mixed list. Relabelling the Survey Builder's lineage rows to the nouns was #1091's second-guess fix and was reverted for this reason. If a verb reads badly, fix it in the metamodel — it is admin-editable and there is one definition. Full rule: `frontend/UI_GUIDELINES.md` §3.13.

- **Every relation edge on a diagram is built by `relationEdgeStyle` — there is exactly one renderer.** `frontend/src/features/diagrams/drawio-shapes.ts` owns the style of a relation edge and every path that draws one goes through it: the relation picker (`stampEdgeAsRelation`), the pending→synced switch (`markEdgeSynced`), expansion from the inventory (`expandCardGroupAt` / `insertChildVertex`), the delete-undo path (`restoreRemovedEdge`) and the LDV "Create diagram" serialiser (`buildLdvDiagramXml`). They each used to hand-roll a near-identical style string and they drifted, so the *same* relation rendered two ways depending on how it reached the canvas — grey with a verb when drawn by hand, card-coloured with no label at all when retrieved with `+` (#905, fixed in 2.39.1). Three invariants the builder encodes: an edge is drawn in the one neutral `RELATION_EDGE_COLOR`, **never** the related card's colour (an edge *is* a relation; tinting it by card type restates the node and hurts a dense landscape); direction is shown by moving the **arrowhead** (`startArrow` vs `endArrow`), never by flipping the mxGraph endpoints — expansion always inserts parent→child and expand/collapse plus the sync side-table key off that; and the verb is **always the forward label** — `relationLabel(rt, locale)`, never the reverse form. An edge on a canvas has no "card you started from": a reader sees a line with an arrowhead and reads it in the arrow's direction, and since the arrowhead always marks the relation's *target*, the sentence along the arrow is always source-verb-target. Resolving it from the expanded card instead made one relation read two ways depending on which end you expanded from — "uses" from the Organization, "is used by" from the Application — which is the #905 complaint one level deeper. `layeredDependencyLayout.ts` is forward-only for the same reason (both of its label branches collapse to `e.label`), so this is what keeps the diagram and the LDV agreeing; `humanRelationLabel` (the delete-confirm dialog and the side-table) was always forward-only too. When the relation type declares a `flowDirection` attribute *and* the relation has a value, `flow` decides the arrowhead instead of `incoming` (`forward` → target end, `reverse` → source end, `bidirectional` → both), matching what `layeredDependencyLayout.ts` already draws — this is what distinguishes an Application that *provides* an Interface from one that *consumes* it, since `relAppToInterface`'s label carries both verbs. `flow` means something on the **relation type's** source→target axis while the edge may be drawn the other way, so `relationArrowParts` XORs it with `incoming` rather than reading either alone. **The type's axis, not the stored row's.** Card detail offers `forward` as the Application being *Provider*, but several write paths accept ids without checking them against the type (the Excel Relations sheet, `/relations/bulk` id refs, the MCP server, the extension bridge, workspace import, the pre-2.39.1 diagram editor), so a `relAppToInterface` row can be stored Interface → Application — and read on the row, its provider drew as a consumer in the LDV, its "Create diagram" export and expansion ([#1140](https://github.com/vincentmakes/turbo-ea/discussions/1140), fixed in 2.149.3). `runsAgainstType(rt, sourceType, targetType)` (`lib/relationSort.ts`) is the one test for such a row (never true for a self-referencing type), and every arrow renderer reads it as if stored the type's way: the LDV turns its edges once on entry (`orientEdgesToRelationTypes`, `ldvLayoutShared.ts`, applied in `LayeredDependencyView` so both layouts and the export inherit it), expansion derives `incoming` through `edgeIncoming` (`expandChildren.ts`), and the stale check's flow restyle XORs `runsAgainst`. Since the same release no such row can be written or survive (see *Every relation is stored in its relation type's direction* under Backend Conventions), so on current data these are no-ops — they stay as the safety net for a row that arrives by a path nobody has thought of yet, and for a diagram edge synced to one before the repair. Guard tests: `features/reports/ldvOrientation.test.ts`, `lib/relationSort.test.ts`, `features/diagrams/expandChildren.test.ts`, `staleCheck.test.ts`. Gate on `flowDirectionBadge(rt, attrs)` (the same helper Card Detail buckets Provider/Consumer with) so the canvas and the card can't disagree, and stamp the value onto the edge user-object — `markEdgeSynced` reads it back rather than taking it as an argument, so the pending→synced restyle cannot drop it. A reversed pick is stamped `reversed="1"` on the edge user-object and `scanDiagramItems` surfaces it, because sync must swap `source_id`/`target_id` before POSTing — without it the relation is created backwards.
