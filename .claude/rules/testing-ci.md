# CI test gates, mutation testing, the browser suite and backend test fixtures

> Loaded when you touch `.github/workflows/**`, `scripts/mutation/**`, `frontend/e2e/**`, `frontend/scripts/**`, … (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

- **CI enforces the rule above three times, and every gate ratchets upward only.** (1) **Diff coverage**: on every pull request, `Backend Integration Tests`, `Frontend Tests` and `MCP Server Tests` run `diff-cover` against the base branch and fail when the lines the PR adds or changes are less than 80% covered — a change without a test fails CI, whatever the suite-wide total. (2) **Suite floors**: `fail_under` in `backend/pyproject.toml` and `mcp-server/pyproject.toml` and `coverage.thresholds` in `frontend/vitest.config.ts` sit just under the measured totals. Raise a floor in any PR that lifts the number; never lower one, and never exclude a file from measurement to get past one. Each job writes its per-file table to the run's job summary, so the number is visible without opening the log. **The two big suites run as shards, and only their aggregate is a required check.** `Backend Integration Tests` and `Frontend Tests` are aggregate jobs in `ci.yml` over matrix shard jobs (`backend-test-shards`, four runners, `--shard K/N` from `backend/tests/shard_plugin.py`, which deals every test file largest-first into the lightest shard; `frontend-test-shards`, three runners, Vitest's own `--shard` with `--reporter=blob`): a shard measures coverage but never reports or gates on it (`--cov-report= --cov-fail-under=0`, the four Vitest thresholds zeroed), and the aggregate combines the data (`coverage combine`, `vitest run --merge-reports`), enforces the floor and the diff gate and writes the summary table. **The frontend figure also counts the browser suite.** `Frontend Tests` lists `frontend-e2e` in its `needs` — for its coverage, not its verdict. `Frontend E2E` runs Playwright with `E2E_COVERAGE=1` (the `page` fixture in `frontend/e2e/fixtures.ts` records Chromium's V8 coverage of the SPA's `/assets/*.js` chunks, one file per test), `frontend/scripts/e2e-coverage.mjs` remaps those through the build's source maps with `ast-v8-to-istanbul` — the converter Vitest itself uses, AST-based so a minified one-line chunk is not read as one statement — into `coverage-e2e/lcov.info` under the same include/exclude as `vitest.config.ts` (`isMeasured` mirrors it; change both together — `scripts/e2e-coverage.test.ts` pins the two lists), and the aggregate's `frontend/scripts/merge-lcov.mjs` merges the unit and browser LCOVs line by line into `coverage-merged/`: the report the diff gate reads and the README badge shows. Lines only, by construction: statement, branch and function ids are not position-stable across the two pipelines (vite's dev transform vs the minified production map) and stay in Vitest's unit report. **The merge is anchored on the unit report**: Vitest lists every file `coverage.include` matches, tested or not, so its LCOV is the complete universe of measured lines; the browser suite can mark one of those lines covered but never add a line or a file (`mergeAnchored` drops and counts them). A plain union let the two pipelines' disagreements in as uncovered lines — a `v8 ignore` hint the minifier strips, a statement boundary the production map places elsewhere, an `isMeasured` drift — which the diff gate then charged to a PR; anchoring means the merge can only undercount, never inflate. The merged figure has its own floor, `config.coverageFloorMergedLines` in `frontend/package.json` (the one JSON the script already has at hand; raise it like the Vitest thresholds, never lower it), checked only when `Frontend E2E` passed — unit-only data would fail it for the wrong reason, and a red browser suite is its own required check — and `--fail-under-from-package` refuses a *missing* key rather than reading it as "no floor", so a typo cannot switch the gate off. For the same reason `Frontend E2E`'s `e2e` path filter is `frontend/**` plus the suite's own inputs, so it runs on every pull request and push that can move the figure (but not on the wider `frontend` filter's audit-ci config, which cannot), and the badge total is written only from a push to `main` on which it passed: the published figure is always unit+browser or unchanged, never unit-only. The three scripts are in Stryker's `mutate` list beside `src/**` (and `Frontend Tests` measures them, named file by file so the generator scripts beside them stay out of the diff gate). Two rules the layout owes: the aggregate runs on `if: always() && <changes gate>` and its first step fails unless `needs.<shards>.result == 'success'`, because branch protection treats a *skipped* required check as passing; and the matrix is the only place a shard count is set — `strategy.job-total` carries it into the job name, the command and the aggregate's count check, which refuses to combine fewer data files than legs (a missing artifact is silent at download). Guard tests: `backend/tests/core/test_shard_option.py` (the shards partition the suite exactly), `tests/services/test_ci_workflow_sharding.py` (the workflow shape).
- **(3) Mutation score on changed lines — coverage proves a line ran, a mutation score proves a test would notice it being wrong.** `Backend Mutation Tests`, `MCP Mutation Tests` (mutmut 3, pinned exactly in both `pyproject.toml`s) and `Frontend Mutation Tests` (StrykerJS + its Vitest runner, `frontend/stryker.config.json`) run on every pull request that touches their suite, and on one that touches the gate itself: `scripts/mutation/**` has its own `mutation` path filter in `ci.yml`, which runs those three jobs and `Backend Unit Tests` (where the scripts' and the floors' tests live) and nothing else — it sat in the backend, frontend and mcp filters until a one-line floor bump booted every suite (`test_nothing_else_runs_on_a_change_to_the_scripts`). Each mutates what the PR changed — the mutants on a changed line of every top-level function or method it touches for Python (`scripts/mutation/mutmut_scope.py` generates first and names them one by one, rendering each mutant's diff in-process from mutmut's `.spans` index rather than one `mutmut show` process per mutant: #1195 tested some 840 mutants to score 111, then spent 24 minutes placing them), the exact changed line ranges for Stryker (`stryker_scope.py`, whose `--mutate` takes `file:first-last`) — keeps the mutants on a line the PR added or modified (`changed_lines.py`, merge base vs. working tree, so CI and a laptop agree), and fails when fewer than the `[diff]` floor in `scripts/mutation/floors.toml` of them are killed. Score = killed / (killed + survived); a mutant **no test reaches counts as survived**, never as exempt; under `min_mutants` in scope the job warns instead of failing and the Test Plan answers for each survivor by hand — except on a file listed under `[modules]`, whose changed lines answer to that module's own floor however few they are (`changed_module_rows`): the diff floor's 60% let #1247 add 540 mutants to `workspace_io/applier.py` and take a 97% module under its floor, and only the nightly said so. One scorer, `gate.py`, judges all three suites from one record format. **Existing code is measured too**: `mutation-nightly.yml` shards every mutable file across runners and is *resumable* — mutmut keeps each verdict in its `mutants/` cache, and since Stryker writes its report only when a whole run completes (stopped, it saves just a partial incremental file the next run resumes, so the nightly warns "raise CHUNKS" only for a chunk that measured nothing new in a whole budget), `stryker_scope.py nightly` splits each frontend shard into stable chunks with their own incremental file and report — all kept per shard as a tarball artifact of the run (`nightly_state.py`; it was an Actions cache until the repository's 10 GB limit evicted 13 of the 15 shards' caches on 2026-10-15 and restarted the frontend's complete baseline), so a time-boxed night (`--budget`) picks up where the last stopped and, once the baseline is complete, re-tests only changed functions and the survivors a changed test runs. The nightly enforces the `[suite]` floor per suite and a `[modules]` floor per critical module (permissions, read scope, public access, OAuth, relation direction, the cost/EOL rules, the formula engine …) with `gate.py --allow-pending` (a floor applies once everything it covers is measured), names files whose score fell since the previous night, and keeps ONE open issue, **Mutation nightly: survivors by module**, as the ranked backlog (it opens with each suite's status against its floors; it is a report, not a bug list). The PR jobs restore the cache backend shard 1 and the MCP shard still save beside their artifact, which is what spares them mutmut's serial stats pass over the whole suite. Three outcomes for a survivor, in this order: add the assertion it exposes; delete the code it proves dead; or, only when it is genuinely equivalent, suppress it **with a reason** — `# pragma: no mutate, <reason>` (the separator is a **comma**: mutmut splits its pragma on one, so `no mutate block: why` silently degrades to a single-line pragma) or `// Stryker disable next-line <Mutator>: <reason>` — and name each in the Test Plan. A test-hardening PR that kills survivors in existing code is complete on its own (no product change, no version bump) and raises the touched module's floor in the same diff. Never widen `do_not_mutate` or the `mutate` exclusions to pass, never scope a mutmut run with `only_mutate` (it is outside mutmut's config fingerprint, so the stale test↔function stats make newly scoped functions read "no tests"), and never run mutmut outside `mutmut_scope.py`: it copies the suite into `mutants/`, and `shadow_root.py` is what places that copy one level down in a symlinked mirror of the repo so every test that finds a file via `Path(__file__).parents[N]` still finds it. **mutmut never mutates a decorated function** (only a bare `@staticmethod` / `@classmethod`), so every FastAPI route handler body is invisible to it and the PR job lists such changed functions under *Changed functions mutmut does not mutate*: logic that should carry a mutation score belongs in a plain function the handler calls — the same extraction the repo already does for shared write paths (`card_write_service`, `adr_service`, `risk_service`, `survey_service`). A guard test that reads `app/` **as text** (an AST or regex scan) sees mutmut's rewritten copy there, so it takes `pytestmark = pytest.mark.source_scan` (or the per-test marker) and is deselected under mutmut (`tests/mutation_plugin.py`) — it could not kill a runtime mutant anyway; one that is missed stops the nightly's stats pass and names itself in the log. `TEST_DB_REQUIRED=1` turns conftest's "skip when Postgres is unreachable" into a failure for the mutation jobs, because a skipped database suite kills nothing and still exits 0. **Stryker's initial test run aborts the whole frontend job on one failing test**, and it differs from `vitest run` in three ways `vitest.stryker.config.ts` absorbs so no test author has to: its worker thread ignores `vi.stubEnv("TZ")` (those suites are found by scan and left out), a test reading `src/` as text reads the instrumented copy (wrap it in `describeSourceScan` / `itSourceScan`), and it renders several times slower, so `src/test/mutationSandbox.ts` gives Testing Library's `findBy*` / `waitFor` 5 s there instead of the suite's 1 s (the normal suite keeps 1 s, so a slow render still fails a PR). A test that fails only there, with that budget, has a race: read the assertion message before deciding the cause (`Unable to find …` is a wait that ran out; `element could not be found in the document` is an element removed after it was found, i.e. something remounted it), reproduce with `make mutation-frontend FILE=<the mutated file>`, and fix the race itself, never by raising a timeout further or excluding the test. The nightly names every such test — and every test mutmut's clean test failed on — as a `::error::` annotation and in the section at the top of its summary and of the **Mutation survivors (nightly)** issue (`scripts/mutation/harness.py`); the shard stays red, since a chunk that measured nothing is not a pass. Local loop: `make mutation-diff` (the PR gate against `origin/main`), `make mutation-backend FILE=app/…`, `make mutation-frontend FILE=src/…`, then `cd backend && mutmut browse` or `frontend/reports/mutation/index.html`. Guard tests: `backend/tests/core/test_mutation_scripts.py`, `tests/core/test_conftest_mutation.py` (schemas, `TEST_DB_REQUIRED`, the `source_scan` deselection), `tests/services/test_ci_workflow_mutation.py`, `tests/services/test_mutation_pragmas.py`. Full guide: `scripts/mutation/README.md`.
- **The browser smoke suite (`frontend/e2e/`, Playwright) covers what jsdom cannot: the DrawIO diagram editor, the BPMN modeler, the PPM Gantt, the Layered Dependency View and the metamodel graph.** It runs as the `Frontend E2E` CI job on every pull request and push that touches `frontend/**` (its coverage joins the unit suite's in the frontend figure, previous bullet), `scripts/e2e/**` or the Dockerfile — the `e2e` filter in `ci.yml` — against a real backend booted with the demo seed and the built SPA served by `vite preview`; the editor is the DrawIO build the image ships, fetched by `scripts/e2e/install-drawio.sh` from the tag pinned in the Dockerfile. Locally: `SEED_DEMO=true make dev-backend` in one terminal, `make e2e` in another (`make e2e-coverage` runs it with coverage and writes `frontend/coverage-e2e/lcov.info`; `node scripts/merge-lcov.mjs --out coverage-merged coverage/lcov.info coverage-e2e/lcov.info` after `vitest run --coverage` gives the merged figure). A change to one of those widgets that the unit tests cannot exercise needs a spec there. The suite's rules: every wait is an `expect` / `expect.poll` (never a sleep), `retries: 0`, one API login per run (`auth.setup.ts` — `/auth/login` is rate-limited and locks an account after five failures, so only `login.spec.ts` touches the form), every spec — `login.spec.ts` included — imports `test` from `./fixtures` so the coverage-recording `page` fixture reaches it, `goto` with `domcontentloaded` because the SSE stream never lets the network go idle, demo data is looked up by name through the API and anything a spec creates is deleted in `afterAll`. A spec that fails without a product cause is fixed or deleted the same day, never retried into green.

- Backend integration tests use the savepoint-rollback pattern — each test runs in a transaction that rolls back automatically, so tests never pollute each other.
- The test database engine (`test_engine` in `conftest.py`) is a **sync** session-scoped fixture using `NullPool`. This avoids pytest-asyncio event loop mismatches — each test gets a fresh asyncpg connection on its own loop. Do not convert it to an async fixture.
- **Rate limiting is auto-disabled** in tests via an autouse fixture (`_disable_rate_limiter`). Tests should assert actual business logic status codes, not 429.
- **Coverage traces greenlets — keep `concurrency = ["greenlet", "thread"]` in `[tool.coverage.run]`.** Async SQLAlchemy runs every query on a greenlet, and without that setting coverage.py stops tracing a handler at its first `await db.execute()` and reports everything after it as never run. The backend measured 62% that way and 81% with the identical suite once greenlets were traced (`comments.py`: 52% → 94%). A file that looks untested past its first query is almost always this, not a missing test — check the setting before writing one.
- **`func.now()` is transaction-constant, and every test runs in one transaction.** PostgreSQL's `now()` is `transaction_timestamp()`, and the `db` fixture wraps the whole test in a single outer transaction with savepoints — so `updated_at` is byte-identical before and after however many UPDATEs were emitted. A test that checks "the timestamp did not move" by comparing timestamps passes vacuously. Assert on the emitted SQL instead, via the `card_update_sql` fixture in `conftest.py` (`updated_at=now()` in the SET clause means the `onupdate` default fired). Pair every such assertion with one proving the work was not a no-op, or it proves nothing either way.

- **Seed demo data must stay compatible with the metamodel.** `test_seed_demo.py` validates that every card type, subtype, attribute key, select option, and relation type used in `seed_demo.py` and `seed_demo_bpm.py` matches the definitions in `seed.py`. When changing the metamodel, update the demo data or these tests will fail. `test_seed_demo_security.py` does the equivalent for `seed_demo_security.py` — it asserts that every card name referenced by the demo Compliance findings exists in `seed_demo.py`'s Application + IT Component list, and that every regulation key / lifecycle state used by the seed is valid. Rename a NexaTech demo card and these tests will catch the dangling reference.
