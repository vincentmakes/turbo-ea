# UI plugins and the `window.TurboEA.sdk` reuse boundary

> Loaded when you touch `frontend/src/lib/extensionHost*`, `frontend/src/lib/ExtensionRoutesOutlet*`, `frontend/src/lib/extensionSavedReport*`, `frontend/src/features/admin/Extensions*`, … (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

- **UI plugins**: assets served same-origin by `GET /ext-assets/...` (unauthenticated by design — entitlement gating is the authenticated `/extensions/ui-manifest` + the `/ext/{key}/` APIs; CSP stays `'self'`). **Named UI SDK extension points** (nav routes, card tabs, admin panels; since UI SDK 1.16 **integration panels** — `integrationPanels` on `TurboExtensionUI`, `{id, label, icon?, permission?, component}`, rendered as sub-tabs of Admin → Settings → Integrations next to the built-in ServiceNow integration (`IntegrationsHub.tsx`) so an extension that connects Turbo EA to an external system is configured in the same place as built-in integrations — a typed named point rather than a slot because the hub needs label/icon metadata to build the sub-tab list; `adminPanels` is unchanged and still renders on Admin → Extensions; since UI SDK 1.1 **custom field types** — `fieldTypes` on `TurboExtensionUI`, a display/editor pair for a namespaced `ext.{key}.*` field type used inside card attribute sections; since UI SDK 1.2 **survey templates** — `surveyTemplates`, a "New from template" shortcut on the Surveys admin page whose `build()` payload is POSTed to `/surveys` (always a draft) and opened in the builder, surfaced by `getExtensionSurveyTemplates` / `useExtensionSurveyTemplates`, additive and ungated; since UI SDK 1.3 two **ADR** points — `adrPanels`, a component rendered on the ADR editor + preview (`ADREditor`/`ADRPreview`, consumed via `useExtensionAdrPanels`, props `{adrId, status, signed, readOnly}`; ADRs are not cards so `cardTabs`/`metamodel` field contributions do not apply to them), and `adrExportSections`, a plain-data builder (`getExtensionAdrExportSections`) whose returned `{heading, paragraphs?, table?}` sections core renders into the ADR DOCX export in `adrExport.ts`; both additive/ungated; and since UI SDK 1.10 **ADR grid columns** — `adrGridColumns`, a plain-data column (`{id, label, align?, width?, minWidth?, value(adr), sortValue?(adr)}`) appended to the shared decisions grid (`AdrGrid`, used by EA Delivery → Decisions AND GRC → Governance → Decisions; optional `width`/`minWidth` px hints default to 150/120). Core builds a native AG Grid `ColDef` from it (`useExtensionAdrGridColumns`), so the column shares theme/sorting/quick-filter with built-in columns; `value()`/`sortValue()` run guarded — a throw yields an empty cell, never a broken grid. Deliberately plain data, NOT a `cellRenderer` — extensions contribute data, core owns the rendering, same philosophy as `adrExportSections`). **Since UI SDK 1.12 the *preferred* way to add a plug point is the generic slot registry, not a new named point.** An extension declares `slots: [{ slot, id, component | build, permission?, appliesTo?, order? }]` on `TurboExtensionUI`; core exposes a location by dropping `<ExtensionSlot name="..." context={...} />` (component slots, rendered inside `ExtensionBoundary` with `context` as props) or calling `getExtensionSlots(name)` and rendering the returned `build(ctx)` data itself (data slots — the `adrGridColumns`/`adrExportSections` philosophy). A contribution must supply exactly one of `component`/`build`; `permission` hides the slot silently (never an access-denied page), `appliesTo` filters on `context.cardType`/`type`, `order` sorts within a slot. The payoff: a **new** plug location no longer needs an SDK type/hook/version change — only a one-line `<ExtensionSlot>` in core with a fresh `slot` string (seeded locations: `card.detail.header` in `CardDetailContent`, `risk.detail.panel` in `RiskDetailPage`, and `adr.header` (the ADR action-button row, alongside Duplicate / New revision) + `adr.signature.footer` in `ADREditor`/`ADRPreview` — the latter the sanctioned home for post-decision, below-signature ADR content, both passing `{adrId, status, signed, attributes}`; plus the two SDK 1.6 notification-preferences locations — `notification.preferences.channels`, a **data** slot returning `{label, order?}` per extension-delivered channel, and `notification.preferences.footer`, a component slot under the preferences table passing `{userId}` where a channel shows its per-user link state); and `notification.detail` (SDK 1.11), a component slot inside the bell's notification-details dialog passing `{id, type, title, message, link, data, cardId, createdAt}`, rendered with `ownerExtKey` so only the sending extension contributes). The named points above are retained for compatibility; add new locations as slots. Every extension component renders inside `ExtensionBoundary`. `UI_SDK_VERSION` bumps major on breaks, minor on additive points; the host checks the major only. A nav route may carry an optional `navGroup` placement hint (whitelisted by `EXTENSION_NAV_GROUPS`, currently `"reports"`, `"grc"` and — since UI SDK 1.28 — `"admin"`) so its menu entry renders inside a core nav group instead of adding another top-level icon — this is a hint on the existing routes point, **not** a fourth-plus extension point; the path stays `/ext/{key}/...`, `AppLayout` loops the whitelist and injects each group's routes into that nav item's `children` via `getExtensionRoutesForGroup`, and an unrecognised `navGroup` surfaces nowhere in the nav (still reachable by URL). **`admin` is not a top-bar dropdown**: its routes are appended to `adminItems` — the Admin section of the user menu and of the mobile drawer, after Metamodel / Users & Roles / Surveys / Extensions / Settings — so an extension page that *configures* something sits where an admin looks for configuration rather than claiming a bar icon every user sees. The only gate is the route's own `permission` (an `/ext/*` path is ungated in `ROUTE_PERMISSIONS`); a user without it sees no entry and the group **never falls back to the bar**, unlike the two dropdown groups below — an admin page has nowhere else to be. **Since UI SDK 1.26 a top-level route may also carry `navPlacement`** — `start` / `end` / `before:<anchor>` / `after:<anchor>`, anchors being the core nav keys exported as `NAV_ANCHORS` (`layouts/navItems.ts`) — so an extension page can sit beside the work it relates to instead of always at the tail of the bar. It is deliberately the SAME grammar as a manifest field section's `placement`, resolved by `resolveNavPlacement`, the frontend mirror of `resolve_placement` (`field_contributions.py`): one grammar learned once, including its leniency (any prefix that is not `after` reads as `before`). Two rules carry over and are what the tests pin: it defaults to `end`, which is the position every extension had before the field existed, so omitting it is a no-op; and an anchor **not currently in the bar** — `bpm`, `ppm` and `grc` come and go with their module flags — degrades to that default rather than dropping the entry. `AppLayout` recomputes the index per route against the list as it then stands, which is what keeps two routes sharing one placement in registration order instead of reversing them. `navPlacement` is ignored when `navGroup` is set: the entry is a child of that group, and where the group sits is core's. Three rules the injection owes, each of which shipped as a bug the first time a *second* group existed: **(1)** a group whose nav item is a **page** (GRC has `path: "/grc"`; Reports has none) becomes a dropdown the moment it gains children, so its own link is seeded as the first child or the page falls out of the nav; **(2)** when the group's nav item is absent for this user — module toggled off, or the permission missing — the routes fall back to **top-level** entries rather than being swallowed, so a licensed page stays reachable whatever a core module toggle says (which is why the host lookup checks `hasPerm`, not just presence); **(3)** the dropdown anchor and the mobile drawer's expanded flag are keyed **by group** — one shared anchor rendered `navItems.find(n => n.children)`, i.e. the *first* group's children under whichever button you clicked, and one shared boolean expanded every group at once. The nav container is also `minWidth: 0` + `overflowX: auto`: everything else in the toolbar is `flexShrink: 0`, so without it enough nav entries push the notification bell and user menu off screen.
- **The SDK is the reuse boundary — expose core UI on `window.TurboEA.sdk`, never make an extension rebuild it.** When an extension needs UI that core already has (a dialog, a picker, a report frame, a drawer), expose the existing core component on `window.TurboEA.sdk`: add the import + sdk entry + a `UI_SDK_VERSION` minor bump + a surface-test assertion, same as `SaveReportDialog` / `CardDetailSidePanel` / `ReportShell` / `FilterSelect`, and — since UI SDK 1.8 — `useCurrency`, `MetricCard`, `ReportLegend`, `UserMultiSelect` (the shared multi-user picker in `frontend/src/components/UserMultiSelect.tsx`), and — since UI SDK 1.32 — `loadECharts` (an async loader resolving, from the code-split chunk core's dashboards and reports already ship, the shared chart layer in `frontend/src/components/charts/`: the `EChart` wrapper with `EXPORT_DPR` / `ECHART_CLASS`, `useEChartsTheme` / `buildEChartsChrome` — the MUI-derived chrome that handles light, dark and right-to-left once — and the `chrome` namespace of pure option helpers (`tooltip`, `axisLabel`, `grid`, `legend`, `valueLabel`, `treemapLabel`, `niceMax`, `escapeHtml`, …); it is the ONLY chart stack — extensions must NOT bundle their own charting library — and since UI SDK 1.33 it also registers `ScatterChart` and `MarkAreaComponent`, so an extension draws scatter plots over shaded reference areas (`markArea`); the host never imports `components/charts` statically (a source-scan test in `extensionHost.test.tsx` pins it). The older chart entries — `loadRecharts` (1.8) and `useChartTheme` (1.9) — were deprecated at 1.32 and removed at UI SDK 1.33 (core 2.186.0), and `recharts` is no longer a dependency in `package.json`), and — since UI SDK 1.17 — `loadAgGrid` (an async loader resolving core's code-split AG Grid chunk together with the Theming API themes from `frontend/src/lib/agGridSetup.ts`, so an extension grid shares core's grid look without bundling AG Grid; **since 1.18 it also resolves the grid-template hooks `useColumnFreeze` / `useColumnOrder`** from the same chunk, so an extension grid can wire the documented column-freeze + reorder template — UI_GUIDELINES §3.6 — instead of shipping a grid without them, **and since 1.22 the shared cell context-menu hook `useCellContextMenu`** (`frontend/src/components/grid/useCellContextMenu.tsx`), so an extension grid offers the same right-click / long-press cell menu core grids have — filter by cell value, copy, and page-specific row actions via `extraItems` (the AdrGrid pattern) — instead of an anchorEl menu inside a virtualized cell, which breaks the moment the grid remounts the cell. The inventory renders `ext.*`-typed attribute columns through the `fieldTypes` registry (`ExtFieldCell`), read-only and inside `ExtensionBoundary`, so a custom field type looks the same in the grid as on card detail and degrades to plain text when the extension is absent) and `CreateCardDialog` (a lazy wrapper over core's create-card modal, which also accepts `initialSubtype` / `initialAttributes` presets so a caller can open it pre-configured), and — since UI SDK 1.13 — the saved-report **localStorage-persistence** passthroughs on `useSavedReport` (`consumeConfig` / `persistConfig` / `resetAll`, re-exported from `useSavedReport.ts`) so an extension report keeps its filters + selection across a refresh exactly like a core report (URL saved report > localStorage > defaults; `useExtensionSavedReport` returns them alongside `config` / `savedReportId` / `name`), and — since UI SDK 1.20 — `useDateFormat` (the workspace date format from Admin → Settings, returning the same bound `formatDate` / `formatDateTime` core renders every date through, so an extension never hand-rolls a `toLocaleDateString` that ignores the setting) and `useNavigate` (react-router's, re-exported — an extension page is mounted **inside** core's router, so it can route to a core deep link without the document reload an `<a href>` costs, and without bundling react-router itself), and — since UI SDK 1.23 — `DateField` (`frontend/src/components/DateField.tsx`, the shared commit-on-blur, focus-protected date input — the ONLY sanctioned date field — so an extension form cannot reintroduce the mid-edit value-clobber bug #865; MUI-only leaf, static import; it renders a native `type="date"` on Blink/Gecko only, and on Safari (`lib/browserEngine.ts`) the themed `SafariDateField` + `DateCalendarPopover` instead, because WebKit's OS-drawn picker can be neither styled nor suppressed and filled empty fields with today's date — #1142; display, placeholder and parsing take their day/month/year order from `Intl`, never from code), and — since UI SDK 1.24 — `CardMultiPicker` (`frontend/src/components/CardMultiPicker.tsx`, the shared multi-select card browser: type rail with live `/cards/counts`, hierarchy when a single hierarchical type is faceted, optional subtree-root semantics via `roots`, and a `Map<id, card>` selection seeded once per opening — **never** derived from `useCardSearch`'s `items`, which it replaces on every facet *and* search change; resolving a bare id `Set` against that array is exactly how the diagram's Insert-Cards dialog silently dropped picks before it was rebuilt on this. `CardScopeDialog` stays the compact single-type control a report toolbar opens; reach for `CardMultiPicker` when the user picks across types or chooses the type themselves, and note the two share their hierarchy logic via the pure `frontend/src/lib/cardTree.ts` so neither can drift on what a subtree root means), and — since UI SDK 1.29 — `LinkifiedText` / `sanitizeRichHtml` (the free-text linkifier and the one stored-HTML sanitiser, see the Free-text bullet above; an extension rendering a description or a rich-text field must not rebuild either), and — since UI SDK 1.30 — two grid-page entries: `loadAgGrid` also resolves `useDragFill`, so an extension grid with editable cells offers the Inventory's Excel-style fill-down under the same five invariants (write-then-reload through the page's own per-cell primitive, the one wrapper ref borrowed from `useColumnFreeze`, never a bulk endpoint), and `loadSpreadsheet` resolves the Inventory's own WYSIWYG `exportCurrentViewToExcel` / `buildCurrentViewWorkbook`, the workbook readers `parseWorkbook` / `readWorkbookSheets` and the vendored `xlsx` namespace itself (the async-loader posture for a bare heavy dependency — a caller appends its own machine-readable sheet to the workbook core built). The readers live in the leaf `frontend/src/lib/spreadsheet.ts`, lifted out of `excelImport.ts` (which re-exports `parseWorkbook`) so the loader hands over "read this file into rows" without the card importer's 2,000 lines of validators riding along; an extension must never bundle a spreadsheet library of its own. and — since UI SDK 1.27 — `CardPicker` itself (`frontend/src/components/CardPicker.tsx`, the single-select picker the *Picking an existing card* rule below mandates, so an extension dialog that links ONE card gets browse-on-open, ranked filtering and infinite scroll from the same `useCardSearch` engine; a MUI-only leaf — `useMetamodel`, `useCardSearch`, `searchRank`, `cardTree` — so a static entry beside `CardMultiPicker`), and — since UI SDK 1.21 — `loadTimeline` (an async loader resolving the time-travel `TimelineSlider` plus the `timelineRange` helpers — `computeTimelineRange` / `classifyTimelineChange` / `isPresentAtDate` / `isVisibleAtDate` / `computeTimelineMilestones` / `cardsChangingBetween` — and `useTimeline`, so an extension timeline shares the exact range/classification semantics and the persisted `timelineDate` convention the core reports have), `loadDependencyView` (a lazy loader resolving `LayeredDependencyView` + the `layeredDependencyLayout` module namespace from core's code-split chunk, React Flow riding along — §3.10's "never substitute another graph library" applies to extensions too), and the §3.11 filter-sidebar primitives `FilterSectionHeader` / `FilterCheckboxList` / `ColumnFreezeToggle` as static entries (MUI-only leaf modules, `frontend/src/components/FilterSidebarSection.tsx` + `components/grid/ColumnFreezeToggle.tsx`), so an extension grid page's sidebar is built from the Inventory anatomy instead of a lookalike, and `loadReportExport` (an async loader resolving core's own `exportReportToPptx` / `exportReportToXlsx` / `extractSheetsFromDOM` — an extension that wants a deck must never bundle a presentation library: the engine that renders a core report to PowerPoint renders an extension's too, so the decks match and pptxgenjs stays in the one code-split chunk that already carries it; pass a `chartNode` plus `paginateRowSelector` to cut one slide per marked block), and — since UI SDK 1.19 — the **select-option pill** `OptionChip` + `SELECT_CHIP_BASE` / `chipWidthForField` / `readableTextColor` and the metamodel label resolvers `useOptionLabel` / `useFieldLabel` / `optionLabel` / `fieldLabel`, so a `single_select` value on an extension page renders identically to the same value on card detail and in the Inventory grid (colour, contrast foreground, uniform per-field width, translated label, and the outlined warning chip for a stored key that matches no option). The pill lives in its own leaf module `frontend/src/components/OptionChip.tsx` and `cardDetailUtils.tsx` consumes it: that file imports `extensionHost`, so `extensionHost` cannot statically import it back — a lift-to-leaf is the standard fix when the component you want to expose sits in a module that already depends on the host. and — since UI SDK 1.25 — `LifecycleSection` (`frontend/src/features/cards/sections/LifecycleSection.tsx`, the card-detail lifecycle line: the five-phase track, the progress fill and the edit row, all props-driven and committing through an `onSave` callback rather than an API call of its own, so an extension can render a card's phases exactly as core does and wire the save to its own writer) together with the phase vocabulary `PHASES` / `getPhaseLabels`, and `buildGanttArrowPath` (`frontend/src/features/ppm/ganttArrowPath.ts`, the finish-to-start dependency-arrow routing lifted out of the project gantt — forward H–V–H with 6px arcs, a left-hand loop-back for overlapping bars, a straight segment for a shared row, plus the `clickSafe` variant that insets the hit stroke clear of each endpoint's relation handle; the shape of an FS arrow is a convention, and a second implementation is a second convention). `LifecycleSection` carries an optional `phaseAnnotation(phase)` prop returning `{note?, highlighted?}` — a caller that knows something the component cannot, such as a date differing from a baseline it tracks, marks the phase and hangs its own control under it; the component renders what it is given and knows nothing about why. Both are static entries only because `PHASES` / `getPhaseLabels` were lifted OUT of `cardDetailUtils.tsx` into the leaf `frontend/src/lib/lifecyclePhases.ts` first — the same lift-to-leaf `OptionChip` needed, for the same cycle. A weaker extension re-implementation is a bug, not a workaround. One caveat when adding an entry: if the component pulls a heavy code-split graph or would create a module cycle back into `extensionHost` (e.g. `CardDetailSidePanel` → `CardDetailContent`, `ReportShell` → the xlsx/pptx export engine), expose it as a `React.lazy` wrapper with Suspense handled internally (or an async loader like `loadSpreadsheet` for a bare library) — never a static import that drags the graph into the eager main bundle. One advanced metamodel field-authoring capability lives entirely in core but is only *authorable* when an installed, enabled, licensed extension declares the matching grant in its manifest (`"grants": ["metamodel.custom_field_types"]`, surfaced by `registry.grants_for` / `granted_capabilities` and the `/extensions/status` `grants` field): **custom field types** (`FieldDef.type = "ext.*"` + `config`, rendered via the `fieldTypes` registry). The free core ships the *engine* (schema, storage, rendering, the empty registry) but no UI to author one; `_enforce_field_gating` in `backend/app/api/v1/metamodel.py` downgrades a new or changed `ext.*` type on `create_type`/`update_type` unless the grant is active (`granted_capabilities()`). **Field help text** (`FieldDef.help` + `helpTranslations`, rendered as collapsible guidance by `FieldHelp` in `cardDetailUtils.tsx`) was the second gated capability until 2.174.0 ([#1297](https://github.com/vincentmakes/turbo-ea/issues/1297)): it is now a core feature, authored by any metamodel admin in `FieldEditorDialog` and written exactly as sent; `metamodel.field_help` stays in `VALID_GRANTS` (and its `teax.py` mirror) as a documented no-op so existing manifests still lint, and a field an extension contributes keeps its help read-only in the editor. **Two invariants:** (1) **rendering is never gated** — `FieldValue`/`FieldEditor` always render an `ext.*` value, degrading to a read-only text view when the extension is missing/disabled/unlicensed, so a lapse never blanks a card or deletes data; (2) **existing values are grandfathered** — the gating strip preserves an already-stored custom type verbatim so a lapse can't block an unrelated metamodel edit. Content packs bypass the strip (they write `fields_schema` through `workspace_io`, an extension-delivered path) so a pack can ship custom-typed fields directly. When adding a new gated core capability, follow this shape: inert plumbing + `grants` gate on the *write/authoring* path only + a guard test (`tests/api/test_metamodel_field_gating.py`).
