# The backend extension SDK (`app.services.extensions.sdk`) and its bridge history, 1.1 to 1.16

> Loaded when you touch `backend/app/services/extensions/**`, `backend/app/services/card_write_service.py`, `backend/app/services/adr_service.py`, `backend/app/services/risk_service.py`, … (full list in the frontmatter). Moved verbatim from `CLAUDE.md`; edit it here.

- **SDK surface only.** Backend extensions may import exclusively from `app.services.extensions.sdk` (SDK 1.16, major-version checked at load; guard test `tests/services/test_extension_sdk.py`). 1.1 added the route dependencies `get_db` / `get_current_user` / `require_permission` re-exports so extension routes authenticate and authorize without touching core internals. 1.2 added the connector seam (built for [#921](https://github.com/vincentmakes/turbo-ea/discussions/921)): `ctx.todos` — a typed bridge to core todos, gated per call by the manifest grants `core.todos.read` / `core.todos.write` (`todos_bridge.py`; writes audited as `ext:{key}` mutation batches with origin `ext`, scoped to rows whose `external_source` is NULL or the extension's own key); the optional `get_event_handlers()` hook returning `EventSubscription(prefix, handler)` rows (grant-gated via `EVENT_SCOPE_GRANTS` in `extensions/events.py`, currently `core.events.todo` → `todo.*`; own-write events filtered by default so sync loops cannot form; per-extension bounded drop-oldest queues, 30s handler timeout); and `ctx.get_secret` / `ctx.set_secret` — Fernet-encrypted credential storage under `ext.{key}.secret.*`, scrubbed from workspace transfer. 1.3 added `ctx.users` — a read-only user-directory bridge (grant `core.users.read`, `users_bridge.py`) returning the `_user_response_lite` least-privilege shape (id/email/display_name/is_active, pinned by test) for assignee mapping in connectors — and the system-todo mirror carve-out: the todos bridge accepts exactly one write shape on `is_system` rows, an `update` touching only `external_ref` / `external_url` (a sign-off can be *referenced* externally, never *performed* externally; everything else on system todos stays refused). 1.4 added batch settings — `ctx.get_settings(names)` / `ctx.set_settings(values)` move N namespaced settings in ONE database transaction (the per-key `get_setting`/`set_setting` are a full read-modify-write transaction each, which turns an N-key config save into N sequential round-trips on the `app_settings` row — seconds on a high-latency database); `set_settings` refuses `secret.` names so credentials still go through the encrypted `set_secret` path (tests: `test_extension_settings.py`). 1.5 added the **inventory data bridge** — `ctx.data` (`data_service.py`), typed grant-gated access to cards, relations, and the metamodel: reads (`get_card`, `search_cards`, `get_relations`, `get_card_types`, `get_relation_types`; grants `core.cards.read` / `core.cards.write`, write implies read; wire-shaped `ExtCard`/`ExtRelation` payloads, archived + hidden-type cards excluded by default, per-call short sessions) and guarded writes (`create_card`, `update_card`, `archive_card`, `upsert_relation`; grant `core.cards.write`) that delegate to the shared `app/services/card_write_service.py` — the B0 extraction of the card routes' write logic, so validation, hierarchy guards, calculated fields, data-quality scoring, approval-breaking and event emission are identical for humans and extensions. Write guardrails: every write lands in an `ext:{key}` mutation batch (grouped under `ctx.data.batch(label)`, revertible via the audit log), `EXTENSION_WRITES_ENABLED` kill switch (reads unaffected, no restart), `EXTENSION_MAX_WRITES_PER_BATCH` (500) + `EXTENSION_MAX_BATCHES_PER_MINUTE` (60) caps, `dry_run=True` previews (validate then roll back, no events), **attribute-MERGE update semantics** (a patch never wipes keys it does not carry; `None` deletes a key; unlike REST's full replace), refused fields (`reference`/`external_id`/`status`/`approval_status`), and **no hard delete / no relation delete** (`core.cards.delete` is the canonical rejected grant). 1.5 also added the `core.events.card` scope (`card.*` + `relation.*` delivery; own bridge writes stamped `data["ext"]` and self-filtered) and **cron scheduling** on `ExtensionJob` (`cron="0 3 * * *"`, 5-field UTC, XOR with `interval_seconds`; parser in `extensions/cron.py`). Tests: `test_extension_data_service.py`, `test_extension_card_write_bridge.py`, `test_extension_cron.py`, `test_card_write_service.py`. 1.6 added **notification channels** — an extension can deliver core notifications on a third channel beside the in-app bell and email, registered through the optional `get_notification_channels()` hook (duck-typed like `get_event_handlers`, so pre-1.6 extensions load untouched) returning `NotificationChannel(key, deliver)` rows, unlocked by the grant `core.notifications.channel` (`extensions/notification_channels.py`). **Core owns the preference matrix; the extension owns only the transport** — which types exist, who opted in, and which types may never leave the bell are all decided against `NOTIFICATION_TYPE_SPECS` (`models/user.py`, the canonical registry the preferences dialog also renders from), so a channel cannot invent a type, cannot deliver something the recipient did not switch on, and **cannot start delivering merely by being installed** — extension channels are opt-in-off for every type, with no per-type default able to raise that. Opt-ins live under `notification_preferences["channels"][<channel key>]`, namespaced so a channel key can never collide with a core one; the channel key is enforced to be the extension's own key or `{key}.`-prefixed for exactly that reason. Topology is `events.py`'s (bounded drop-oldest queue + worker, 30s timeout, crash logged never fatal) but deliberately **not** the event bus: `notification.created` only fires when a bell row exists, and the SSE fan-out (`_event_visible_to`) forwards every bus message to every `admin.events` holder, so a second event would broadcast the content of notifications belonging to users who muted their bell — and the bus drops whole *subscribers* on backpressure, not messages. `dispatch` is therefore a plain `def`: `create_notification` calls it with the request's transaction still open, so it enqueues and returns, doing no I/O and no `await` (pinned in `test_db_session_holding.py`). **Durability past that queue is the extension's** — the documented contract is "persist to your own `ext_{key}_*` outbox, drain it from an `ExtensionJob`" rather than a core outbox table that would exist solely to serve a commercial extension. `NotificationDelivery` carries no email address (least-privilege, matching the pinned `users_bridge` lite shape): a channel that needs one declares `core.users.read`. Frontend side: the dialog renders a channel column only when the **backend** reports the channel live *and* a `notification.preferences.channels` data slot supplies the localized label — backend-only degrades to the raw key, slot-only renders nothing, which is what stops a UI-only bundle (installs live) conjuring a column whose PATCH a not-yet-restarted backend would ignore. `PATCH /users/me/notification-preferences` **ignores** unknown channel keys rather than rejecting them and preserves their stored values: the dialog sends the whole object, so a 400 for a channel that de-registered between GET and PATCH would block the user saving their in-app settings, and grandfathering matches `_enforce_field_gating`'s posture. Tests: `test_notification_channels.py`, `test_notification_service_extended.py`, `test_notification_preferences.py`, `NotificationPreferencesDialog.test.tsx`. 1.7 added **`link` on the todos bridge** — `create`/`update` accept the relative in-app path the todo's Open button navigates to, validated by the same `validated_link` as the REST routes (never an absolute or protocol-relative URL); system todos still refuse it — their mirror carve-out stays `external_ref`/`external_url` only (tests: `test_extension_todos_bridge.py`). 1.8 added three surfaces: **batch inventory reads** `ctx.data.get_cards(ids, include_archived=False)` / `get_relations_for(card_ids)` / `get_stakeholders_for(card_ids)` (one query each, a 500-id cap matching `MAX_CARD_IDS_PER_QUERY`, the single-id reads' hidden-type + archived exclusions; malformed ids and over-long lists are *refused* with `ExtensionDataError`, not skipped — on a batch call a dropped id is indistinguishable from "not found"; no `ids=` on `search_cards`, a lookup is not a search; `ExtStakeholder` is `(card_id, user_id, role)` only — names go through `ctx.users`, so the inventory grant alone never exposes the directory); the **decisions bridge** `ctx.decisions` (`adr_bridge.py`, grants `core.adr.read` / `core.adr.write`, write implies read): `create_draft` + `get` only — an extension files a *draft* decision record and can never sign or transition it (the system-todo posture), attribute keys must be `ext.{own key}.*` (stricter than REST's `ext.*`), linked cards must exist and be ACTIVE, `created_by` is NULL with the `ext:{key}` mutation batch (origin `ext`, summary carrying the reference number) as provenance, the `EXTENSION_WRITES_ENABLED` kill switch honoured, no event on create (parity with `POST /adr`); it rides on the B0-style extraction `app/services/adr_service.py` (`next_reference_number`, `resolve_card_ids`, `create_decision` — flush, never commit) which `POST /adr`, `duplicate`/`revise`, the analysis commit flow and the bridge all share, so there is exactly one reference-number generator; and `ctx.data.batch(label)` now **yields `ExtBatch(id, label)`** (the committed `mutation_batches.id`). Tests: `test_extension_adr_bridge.py`, `test_adr_service.py`. 1.9 added the **action surfaces an automation needs**, each grant-gated and audited like the rest: the **risks bridge** `ctx.risks` (`risks_bridge.py`, grants `core.risks.read` / `core.risks.write`, write implies read): `create`, `get`, `list_for_card`, `find_by_source_ref` and an `update` limited to title / description / owner / target date / added cards — **never a status transition**, the same human-only posture as ADR signing; every risk it files carries `source_type="extension"` (a third value on `SourceLiteral`, filter and label) and `source_ref="{key}:{ref}"`, the prefix being what scopes `find_by_source_ref` so two extensions cannot collide and what `update` checks so an extension edits only rows it filed; it rides on the B0-style extraction `risk_service.create_risk` / `sync_owner_todo` / `publish_risk_event` (nullable actor) that `POST /risks` now calls too, so the reference sequence, the owner's system Todo and the `risk_assigned` notification are identical whichever path raised the risk. The **notification bridge** `ctx.notify.send(user_ids, title, message, link?, card_id?)` (`notify_bridge.py`, grant `core.notifications.send`): delivers through `deliver_notification_batch` (never `create_notification` inline — no session across SMTP) under ONE generic type `extension_notice` added to `NOTIFICATION_TYPE_SPECS` (in-app default on, email off), so the recipient's own matrix decides bell / email / extension channel and can mute it; core owns the type, the extension can address people but never invent a type or pick a channel; `link` passes the todo link validator (in-app paths only), 50 recipients per call, `data.ext` stamped, no actor. And two writes on the data bridge: `ctx.data.set_card_tags(card_id, tag_ids, mode=replace|add|remove)` plus the reads `get_tag_groups` / `get_card_tags` (`core.cards.write`; the shared `tag_service.set_card_tags` enforces single-choice groups and `restrict_to_types`, rescores and publishes `tag.added` / `tag.removed` with `db=`, and `POST /cards/{id}/tags` now uses the same event helper), and `assign_stakeholder` / `remove_stakeholder` under their **own** grant `core.stakeholders.write` — a role confers card permissions on the user, so enriching attributes must not imply handing out `card.edit` — validated against `stakeholder_service.roles_for_type` (extracted from the route) and idempotent on `(card, user, role)`; `get_card_types()` now carries each type's `stakeholder_roles` (`[{key, label}]`) so an extension offers the same picker, and the in-process event message carries `user_id` (the actor, or `None`) beside `card_id` so a handler can address the person behind a change. **Every write bridge joins an open `ctx.data.batch(label)` scope** (`data_service.active_batch_id()` / `count_write_in_active_batch()`): inside the scope the todos, decisions and risks bridges run their write in the batch already set on the contextvars instead of opening one of their own, so one extension operation — a card update, a risk, a todo — is ONE Audit Log row with one Rollback; outside a scope each write still opens its single-op batch as before. Tests: `test_extension_risks_bridge.py`, `test_extension_notify_bridge.py`, `test_extension_card_context_bridge.py`. 1.10 added **`ctx.data.get_eol_status(card_ids)`** (`core.cards.read`): the resolved end-of-life status of up to 500 cards as `{card_id: ExtEolStatus(status, source, eol_product, eol_cycle, eol_date, support_date, latest)}`, computed by the very `resolve_eol_statuses` the EOL report and `GET /eol/card-status` use (`eol_service.py`, 30-minute per-product cache), so an extension never re-implements the classification; a card with neither a link nor a manual date is **absent**, never present with a null status. It is outbound HTTP, so the id lookup runs in one short session that is closed before the fetch — `_EolCardSnapshot` copies the three columns out, and `test_extension_eol_bridge.py::test_fetches_outside_the_session` pins that no session is open during the call. 1.11 added **extension-declared notification types and in-app notification details**. An extension holding `core.notifications.send` may declare up to five types of its own under `notifications.types` in its manifest (`{key: "ext.<key>.<name>", label, translations?, in_app_default?, email_default?}`; validated by `notification_types_error` in `bundle.py`, mirrored verbatim in `teax.py` and pinned by `test_teax_grants_lint.py`; key ≤ 50 chars because `notifications.type` is `String(50)`). `extensions/notification_types.py` is the runtime registry, shaped like the channel registry: manifest-driven at startup (`start_notification_types`), `_live` re-checked per call via `grants_for`, never `in_app_only` / `email_locked`. It is consulted in exactly three places — `_user_wants_notification` falls back to `notification_types.type_spec()` after core's own registry (a lapsed extension's type then resolves like any unknown type: bell on, nothing else, stored opt-ins untouched), `GET /users/me/notification-preferences` appends `type_descriptors(locale)` rows carrying a server-resolved `label` (core has no i18n key for a type it did not define; the dialog renders `nt.label ?? t(...)`) and `extension_key`, and PATCH's channel filter unions `registered_type_keys()`. `ctx.notify.send(..., type=)` must name one of the caller's own live types (`types_for_extension`), else `ExtensionDataError`; `detail=True` stamps `data.open = "detail"` — the marker `NotificationBell.opensDetailDialog` reads to open `NotificationDetailDialog` (full message pre-wrap, sender via `getExtensionDisplayName` from the ui-manifest's new `name`, **Open card** gated by `canAccessPath`, **Open** gated by `canOpenExtensionPath` for `/ext/` links — fail-closed: no registered route ⇒ hidden — and the `notification.detail` component slot rendered with `ownerExtKey = data.ext` so only the sending extension contributes) instead of following `link`. `data` is capped at 16 KiB and `ext` / `open` are reserved keys core stamps. The `notification.created` SSE payload now carries the notification's JSONB **nested** as `data.data` plus `card_id` — never spread, because `_event_visible_to` routes on the top-level `user_id`. Tests: `test_notification_types.py`, `test_extension_notify_bridge.py::TestDeclaredTypes`, `test_notification_preferences.py::TestExtensionDeclaredTypes`, `NotificationDetailDialog.test.tsx`. 1.12 added the **per-card permission check** — `check_card_permission(db, user, app_permission, card_id, card_permission)` and `require_card_permission(...)` (the same question, raising 403 instead of returning False), thin wrappers over the very `PermissionService` core gates its own card routes with: true when the app-level permission grants it landscape-wide, **or** when a stakeholder role the caller holds *on that card* carries the card-level key. The canonical pair is `("inventory.view", "card.view")`, the literal core repeats at every card-scoped read of its own (`cards.py`). `require_permission` structurally cannot express it — it is a dependency **factory**, and the card id is per-request path or body data that does not exist when the dependency is declared — and there is no ambient current-user seam to fall back on (the contextvars carry origin, batch, endpoint and impersonation, never identity), so both take `db` and `user` explicitly, the shape `PermissionService` already uses. They are **ungated**, like the 1.1 route dependencies and unlike every `ctx.*` bridge: a grant opens a *data* domain and all 16 in `VALID_GRANTS` name one, whereas these return no data at all — only a verdict about authority the caller already holds, which core's own `GET /cards/{id}/my-permissions` hands any authenticated user in fuller form. Wrappers rather than a re-export of `PermissionService`, whose role cache, impersonation resolution and stakeholder internals are not a supported surface; an unknown card id answers False, not 404; since core 2.151.0 the verdict also honours a per-card-type **View** deny, with no SDK change (see *A card read has one scope* under Backend Conventions). Tests: `test_extension_card_permission.py` (including that no grant is required). 1.13 added **`ctx.batch(label)`** — the audited batch scope without the inventory grant. Every write bridge already *joined* an open `ctx.data.batch`, but `ctx.data` exists only with `core.cards.*`, so a connector whose writes all go through the todos bridge could not open one and left one Audit Log row per todo per poll. `open_context_batch` (`data_service.py`) is the same scope gated on any write grant (`CONTEXT_BATCH_GRANTS`); `ExtensionData.batch` delegates to the shared `open_batch`. Two rules travel with it: **a scope that recorded no write leaves no row** — `open_batch` deletes its `mutation_batches` row on exit when `writes == 0`, on the exception path too, because "sync ran, nothing changed" is not an audit event and an empty batch offered a Rollback that reversed nothing (so an extension must record the handle's `id` only once something was written); and **rollback deletes todos an extension created** — `rollback_service._plan_todo_created` reverses a `todo.created` event carrying `data["ext"]` while the todo is still open and not `is_system`, leaving a person's own todo, a completed one and a `rolled_forward` occurrence under the standing `todo.` decline. Tests: `test_extension_card_write_bridge.py::TestBatching`, `test_extension_todos_bridge.py::TestContextBatch`, `test_rollback_service.py::TestExtensionTodoRollback`. 1.14 added the **surveys bridge** `ctx.surveys` (`surveys_bridge.py`, grants `core.surveys.read` / `core.surveys.write`, write implies read): `send`, `preview`, `get` — **send only**. An extension creates a survey and activates it in one audited step; closing it and applying its answers stay human acts in Admin → Surveys (the ADR-signing / risk-status posture), so there is no `close` / `update` / `delete`. The cards are named explicitly (≤ 500, all existing, ACTIVE and of `target_type`; malformed ⇒ refused, not skipped) and stored as the survey's `card_ids` filter; `fields` are `[{key, action}]` expanded by `survey_service.expand_fields` from the type's `fields_schema` into the rows the survey builder writes, so a program never hand-writes labels; roles are checked against `stakeholder_service.roles_for_type`. It rides on the B0-style extraction `app/services/survey_service.py` (`resolve_targets`, `activate_survey`, `expand_fields` — flush, never commit) that `POST /surveys/{id}/send` now calls too, so response rows, the one-notification-per-person payloads and the events are identical whichever path sent it. `activate_survey` publishes **one `survey.sent` event per matched card** with `db=` (a card's History tab shows it was surveyed; the bridge stamps `ext`), and `rollback_service._plan_survey_sent` reverses them as ONE `close_survey` op (`_DEDUPE_KEYS` on `survey_id`): the survey is closed and the still-`pending` responses deleted, answered ones kept. `created_by` is NULL, the `ext:{key}` batch is the provenance, and the bridge joins an open `ctx.batch` like every write bridge (`CONTEXT_BATCH_GRANTS` includes the write grant). Delivery goes through `deliver_notification_batch` **after** `_write` returned and its session closed — `test_db_session_holding.py` pins the order. Tests: `test_survey_service.py`, `test_extension_surveys_bridge.py`, `test_rollback_service.py::TestSurveyRollback`. 1.16 added the **survey reads** an automation needs to follow up: `ctx.surveys.list_surveys(status="active", target_type=None, limit=200)` lists surveys whoever sent them (newest send first, counts from one grouped query), and `ctx.surveys.pending_responses(survey_id, card_ids=None, limit=5000)` returns the still-unanswered `(card, person)` requests as `ExtSurveyResponse(survey_id, card_id, user_id, status, requested_at)` rows, oldest first — ids only (names go through `ctx.users`, as with `ExtStakeholder`), archived cards left out, an unknown survey `()`. Both sit under the existing `core.surveys.read` grant; nothing new can be written. Valid manifest grants live in `VALID_GRANTS` (`bundle.py`, mirrored in `scripts/extension-tools/teax.py`, pinned together by `test_teax_grants_lint.py`). Extension tables are `ext_{key}_*` (tracked in `extension_schema_versions`, never in core Alembic), permission keys `ext.{key}.*` (namespace enforced by the loader), API routes mounted under `/api/v1/ext/{key}/` at import time in `app.main` (**backend**-code install/uninstall ⇒ `needs_restart`; UI-only/content/metamodel bundles install live — `RUNTIME_CAPABILITIES` in `installer.py` is `{"backend"}` only, since `/ext-assets` serves from disk per request and `/extensions/ui-manifest` refreshes from the DB per call).
