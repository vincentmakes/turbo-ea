# Релизы и канал предварительных версий

Как Turbo EA управляет версиями, тегами и публикацией образов контейнеров. Эта страница служит справочником для операторов, которым нужно закрепить версии в рабочей среде, и участников проекта, готовящих релизы.

---

## Версионирование

Turbo EA следует [Semantic Versioning](https://semver.org/). Единственный источник текущей версии — файл `/VERSION` в корне репозитория.

- **Patch** (например, `1.0.0` → `1.0.1`): только исправления ошибок. Обновление всегда безопасно.
- **Minor** (например, `1.0.0` → `1.1.0`): новые функции. Обратная совместимость обеспечивается согласно [политике совместимости](compatibility.md).
- **Major** (например, `1.x` → `2.0.0`): несовместимые изменения. Вместе с релизом публикуются инструкции по миграции.

Версия повышается один раз на PR, а не на каждый коммит. В записи CHANGELOG для PR новая версия используется как заголовок; CI завершится ошибкой в [`version-check.yml`](https://github.com/TommasoChi/turbo-ea/blob/main/.github/workflows/version-check.yml), если `/VERSION` повышена без соответствующего заголовка `## [<version>]` в `CHANGELOG.md`.

## Теги образов контейнеров

Каждый push в `main` и каждый тег `v*.*.*` запускает `.github/workflows/docker-publish.yml`, который собирает и публикует в GHCR мультиархитектурные образы (`amd64` + `arm64`).

Для тега релиза, например `v1.2.3`, публикуются следующие теги каждого образа:

| Тег               | Указывает на                   | Стабильный?                          |
|-------------------|--------------------------------|--------------------------------------|
| `1.2.3`           | именно этот релиз              | да — закрепите для рабочей среды     |
| `1.2`             | последний patch в `1.2.x`      | продвигается с выходом patch         |
| `1`               | последнюю minor-версию в `1.x` | продвигается с выходом minor         |
| `latest`          | последнюю не предварительную версию | продвигается с каждым релизом    |
| `sha-<short>`     | точный коммит                   | да — отладка / предварительная версия |

При push в `main` без тега создаются только теги `main` и `sha-<short>` — тег `latest` и semver-теги не создаются.

Все манифесты опубликованных образов подписываются Cosign с помощью бесключевого OIDC. Сведения о проверке подписи и SBOM см. в разделе [Supply Chain](../admin/supply-chain.md).

## Канал предварительных версий

Для minor-версий, меняющих компоновку контейнеров, базовые образы, UID по умолчанию, имена томов, порты по умолчанию или схему так, что операторам нужно выполнить действия, перед финальным тегом выпускается **release candidate**.

Соглашения:

- Теги RC имеют формат `vX.Y.0-rc.N` — они не выпускаются для patch-релизов, только для minor-версий с изменениями, заметными операторам.
- В workflow публикации `docker/metadata-action` настроен с `flavor: latest=auto`. Это автоматически исключает semver-теги предварительных версий из `:latest`, `:X.Y` и `:X` — RC публикуются только как `:X.Y.0-rc.N`. Операторы, закрепившие `:latest`, случайно не получат RC.
- GitHub автоматически помечает релиз с тегом `vX.Y.0-rc.N` как предварительный. Стабильный тег создаёт обычный релиз.

Период проверки:

- RC остаётся доступным не менее **48–72 часов** или до тех пор, пока хотя бы один оператор вне команды сопровождающих не подтвердит успешное обновление, в зависимости от того, что дольше.
- Если ошибку в RC стоит исправить, исправление выпускается как `vX.Y.0-rc.N+1`. Предыдущая RC остаётся в GHCR для воспроизводимости.

Перевод в финальный релиз:

- Финальный тег `vX.Y.0` указывает на merge PR о выпуске, который обновляет версию и журнал изменений после последней RC. Workflow публикации заново собирает мультиархитектурные образы и назначает им новые теги; digest будет отличаться от RC, поскольку меняются версия и входные данные сборки.
- С этого момента теги `:X.Y`, `:X` и `:latest` указывают на финальный релиз.

## Выпуск релиза (чек-лист сопровождающего)

Для обычного patch- или minor-релиза канал RC не нужен:

1. В feature-ветке повысьте `VERSION` и добавьте соответствующий заголовок `## [<version>] - YYYY-MM-DD` в `CHANGELOG.md`.
2. Выполните `python scripts/dump_openapi.py`, если изменился маршрут backend или схема; включите результат в коммит, если он изменился.
3. Откройте PR. CI запускает lint, тесты, проверку расхождений OpenAPI и `version-check.yml`.
4. Выполните squash merge в `main`. До создания тега для этого коммита запустите `security-audit` и `ponytail-audit` для всего репозитория. Прочитайте оба отчёта, устраните блокирующие выводы аудита безопасности и все замечания Must и Should, а также убедитесь, что обе проверки охватывают финальный коммит. В чате Codex или Claude зафиксируйте оба завершённых отчёта согласно `SETUP.md`. Это относится к стабильным тегам и тегам release candidate.
5. В `main` выполните `git tag -s v<version> -m "v<version>"` (или `git tag v<version>`, если ключ подписи не настроен), затем `git push origin v<version>`.
6. Workflow `Publish GitHub Release` извлекает раздел `## [<version>]` из `CHANGELOG.md` и создаёт GitHub Release.
7. Workflow `Publish Docker images to GHCR` собирает, подписывает и публикует мультиархитектурные образы.
8. Проверьте подпись с помощью Cosign:
   ```bash
   cosign verify \
     --certificate-identity-regexp '^https://github\.com/TommasoChi/turbo-ea/\.github/workflows/docker-publish\.yml@refs/(heads/main|tags/v[^/]+)$' \
     --certificate-oidc-issuer 'https://token.actions.githubusercontent.com' \
     ghcr.io/tommasochi/turbo-ea/backend:<version>
   ```
   Требуется Cosign версии 2.6 или новее (либо 3.x) — подпись является пакетом Sigstore; см. [Supply Chain](../admin/supply-chain.md).

Для minor-версии, которой нужна RC:

1. Выполните тот же процесс PR и слияния, что и выше, но повысьте версию до `1.Y.0-rc.1`.
2. После merge создайте тег `v1.Y.0-rc.1` и отправьте его. Workflow публикации соберёт и опубликует образы RC (только `:1.Y.0-rc.1`, без `:latest` и коротких тегов — за это отвечает `flavor: latest=auto`). GitHub автоматически пометит релиз как предварительный.
3. Дождитесь окончания периода проверки. При необходимости исправьте сообщения об ошибках в `-rc.2`, `-rc.3` и последующих версиях.
4. Для выпуска финальной версии повысьте `VERSION` до `1.Y.0` в итоговом PR (запись CHANGELOG объединяет все исправления RC), выполните merge, запустите обе проверки релиза и зафиксируйте их результаты для финального коммита, затем создайте тег `v1.Y.0` и отправьте его. Теперь теги `:latest` и короткие теги указывают на выпущенную версию.

---

## Конец жизненного цикла

Исправления безопасности получает только последняя minor-линейка. Полная политика приведена в [`SECURITY.md`](https://github.com/vincentmakes/turbo-ea/blob/main/SECURITY.md). Срок поддержки более старых minor-линеек истёк; backport-исправления для них выпускаться не будут. Операторам старых версий следует планировать обновление согласно политике совместимости.
