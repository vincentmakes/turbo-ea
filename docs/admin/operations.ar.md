# العمليات والترقيات

هذه الصفحة هي دليل المشغّل لتشغيل Turbo EA في بيئة الإنتاج: كيف تعمل الترقيات وترحيلات قاعدة البيانات، وكيفية النسخ الاحتياطي والتراجع، وما البيئات الموصى بها، والمزالق التي تقع فيها الفرق عند التشغيل على نطاق واسع.

## صور الإنتاج وتثبيت الإصدار

الصور المنشورة على `ghcr.io/vincentmakes/turbo-ea/*` هي الطريقة الموصى بها لتشغيل الإنتاج — فملف `docker-compose.yml` القياسي يسحبها افتراضيًا، أما البناء من الشيفرة المصدرية فهو سير عمل تطويري. وإلى جانب السهولة، توفر الصور المنشورة ضمانات لسلسلة التوريد لا يوفرها البناء المحلي: كل إصدار منشور متعدد المعماريات (amd64 + arm64)، وموقَّع بأداة cosign (عبر OIDC بلا مفاتيح، ويمكن التحقق منه مقابل هوية سير عمل GitHub Actions)، ومشفوع بإثبات منشأ SLSA وقائمة مكونات برمجية (SBOM). تُحجب الصور عند النشر إذا وُجدت ثغرات CVE حرجة، ويعاد فحصها يوميًا بعد النشر، ويعاد بناؤها أسبوعيًا على مستودعات Alpine محدثة بحيث تصل تصحيحات الصور الأساسية تلقائيًا. وإذا كانت مؤسستك تفرض التحقق من توقيعات الصور عند القبول، فإن توقيعات cosign تتكامل مباشرة — راجع [سلسلة التوريد](supply-chain.md) للاطلاع على أوامر التحقق.

العادة الأهم: **ثبّت إصدارك**. فالوسم `:latest` يُعاد توجيهه عند الإصدارات وعند إعادة البناء الأسبوعية — وليس عند كل إيداع — لذا قد يتغير وفق جدول لا تتحكم فيه. عيّن وسمًا صريحًا في ملف `.env`:

```bash
TURBO_EA_TAG=2.23.1
```

راجع [تثبيت إصدار](../getting-started/setup.md) للأساسيات و[الإصدارات](../reference/releases.md) لشجرة الوسوم الكاملة وسياسة قنوات ما قبل الإصدار.

## قاعدة PostgreSQL المُدارة

في البيئات المؤسسية التي تتوفر فيها خدمة PostgreSQL مُدارة — مثل Azure Database for PostgreSQL أو Amazon RDS / Aurora أو Google Cloud SQL أو ما يماثلها — يُعد تشغيل Turbo EA على تلك الخدمة هو الإعداد الموصى به. فحاوية `db` المرفقة مجرد خيار افتراضي بلا تبعيات وليست شرطًا: وجّه الخادم الخلفي إلى مثيلك عبر متغيرات `POSTGRES_*` وتجاوز الخدمة المرفقة (انظر [استخدام PostgreSQL موجودة](../getting-started/setup.md)).

ما الذي تتكفل به الخدمة المُدارة نيابةً عنك:

- **النسخ الاحتياطي والاستعادة إلى نقطة زمنية (PITR)** — آلية، بإدارة مدد الاحتفاظ، وقابلة للاستعادة إلى أي لحظة؛ وهو بالضبط ما تحتاجه استراتيجية التراجع أدناه.
- **التوافر العالي وتجاوز الأعطال** — تكرار على مستوى المناطق أو الأقاليم دون تشغيل نسخ متماثل بنفسك.
- **تصحيحات المحرك، والتشفير أثناء السكون، والعزل الشبكي** — تُدار وفق خط الامتثال الأساسي لمؤسستك (نقاط نهاية خاصة، وتكامل مع IAM).

ثلاثة أمور **لا** تتغير: الخادم الخلفي يظل ينفّذ ترحيلات Alembic بنفسه عند بدء التشغيل (نموذج الترقية في هذه الصفحة مطابق تمامًا)، ووحدة التخزين `backend_data` تظل بحاجة إلى نسخة احتياطية خاصة بها (مرفقات الملفات والملحقات لا تُخزَّن في PostgreSQL)، ومسؤولية حفظ `SECRET_KEY` تبقى عليك. الصورة المرفقة تأتي بـ PostgreSQL 18 — وأي إصدار رئيسي حديث يقدمه مزوّدك مناسب.

### تحقّق من حدّ الاتصالات

الإعداد الوحيد الجدير بالتأكّد منه قبل التبديل هو حدّ الاتصالات. تعمل الواجهة الخلفية كعملية واحدة وتفتح **ما يصل إلى `DB_POOL_SIZE + DB_MAX_OVERFLOW` اتصالاً — 30 افتراضيًا**. تسمح حاوية `db` المضمّنة بـ 100 اتصال، لذا لا تظهر هذه المشكلة أبدًا في التثبيت الافتراضي؛ أمّا الخطط المُدارة من الفئة الأساسية فكثيرًا ما تحدّ قاعدة البيانات بأقل من ذلك، فيردّ PostgreSQL عندئذٍ بـ `too many connections for database "turboea"`.

```sql
SELECT datname, datconnlimit FROM pg_database WHERE datname = 'turboea';
SELECT rolname, rolconnlimit FROM pg_roles    WHERE rolname = 'turboea';
SHOW max_connections;
```

تعني `-1` «لا يوجد حدّ محدّد». وإذا كان الحدّ الفعلي أقل من 30، فإمّا أن ترفعه أو أن تصغّر تجميعة الاتصالات في ملف `.env`، مع ترك بضعة اتصالات متاحة للنسخ الاحتياطي وجلسات الإدارة:

```dotenv
DB_POOL_SIZE=8
DB_MAX_OVERFLOW=2
DB_POOL_TIMEOUT=30
```

ولمعرفة ما هو متصل فعليًا في أي لحظة:

```sql
SELECT state, count(*) FROM pg_stat_activity WHERE datname = 'turboea' GROUP BY state;
```

## كيف تعمل الترقيات: ترحيلات Alembic

يُدار توافق مخطط قاعدة البيانات تلقائيًا عبر [Alembic](https://alembic.sqlalchemy.org/). فعند بدء التشغيل ينفّذ الخادم الخلفي الأمر `alembic upgrade head`، بحيث تُطبَّق كل الترحيلات المعلّقة بين مخططك الحالي والإصدار الجديد — بالترتيب — قبل أن يبدأ التطبيق في خدمة الطلبات.

الترحيلات مرقّمة تسلسليًا وتراكمية، ما يجعل القفز بين الإصدارات آمنًا: فإذا رقّيت مثلًا من 2.10 إلى 2.23، تُنفَّذ كل الترحيلات الوسيطة بالتسلسل. لست بحاجة إلى المرور بكل إصدار فرعي على حدة.

بعض السلوكيات الجديرة بالمعرفة:

| الحالة | ما يحدث عند بدء التشغيل |
|---|---|
| قاعدة بيانات جديدة | تُنشأ الجداول مباشرة وتُختم القاعدة عند head — دون إعادة تشغيل الترحيلات. |
| قاعدة بيانات موجودة | تُنفَّذ الترحيلات المعلّقة تلقائيًا قبل أن تصبح واجهة API متاحة. |
| `RESET_DB=true` | تُحذف كل الجداول ويعاد إنشاؤها وتعبئتها من جديد. لا تفعّله في الإنتاج أبدًا. |

ضمن خط الإصدار الرئيسي الواحد تبقى الترحيلات إضافية ومتوافقة مع الإصدارات السابقة عند الترقية — راجع [سياسة التوافق](../reference/compatibility.md) للاطلاع على العقد الكامل.

!!! warning "لا تشغّل أبدًا خادمًا خلفيًا أقدم على مخطط أحدث"
    لا يرحّل Alembic عند بدء التشغيل إلا إلى الأمام. تشغيل شيفرة قديمة على مخطط أحدث سلوك غير معرَّف — وهذا هو القيد الأساسي للتراجع (انظر أدناه).

## إجراء الترقية

1. **اقرأ سجل التغييرات.** راجع مدخلات `CHANGELOG.md` بين إصدارك الحالي والإصدار المستهدف. التغييرات الكاسرة ترفع الإصدار الرئيسي.
2. **خذ نسخة احتياطية** من قاعدة البيانات ووحدة تخزين البيانات (انظر أدناه).
3. **ارفع الوسم واسحب الصور:**

    ```bash
    TURBO_EA_TAG=2.24.0 docker compose pull
    docker compose up -d
    ```

4. **راقب سجلات بدء التشغيل** وتأكد من اكتمال الترحيلات بنجاح قبل أن تبدأ واجهة API في خدمة الطلبات:

    ```bash
    docker compose logs -f backend
    ```

!!! note "نوافذ الصيانة"
    الترحيلات سريعة عادة، لكن مع المخزونات الكبيرة قد تستغرق بعض ترحيلات البيانات عدة دقائق لا يستجيب خلالها الخادم الخلفي. جدوِل الترقيات ضمن نافذة صيانة.

### معرفة توفّر ترقية جديدة

بدلًا من مراقبة المستودع، دع النسخة تخبرك: يتحقق Turbo EA يوميًا من وجود إصدار أحدث ويُشعر المسؤولين عبر جرس الإشعارات، مع رقم الإصدار وملاحظات الإصدار. وهو لا ينزّل ولا يثبّت أي شيء إطلاقًا — فالخطوة 1 أعلاه ما زالت تبدأ بقراءة سجل التغييرات. التحقق مُفعّل افتراضيًا ويمكن إيقافه من [الإدارة ← الإعدادات ← عام](settings.md#update-notifications)، وهو ما يوقف أيضًا الطلب الصادر في التثبيتات المعزولة. وبمجرد اكتمال الترقية، يُبلَّغ كل مستخدم عبر جرس الإشعارات بأن التطبيق قد تم تحديثه، ويمكنه قراءة سجل التغييرات للإصدارات التي عبرتها. ويظل كل إشعار يعرض الإصدار الذي أعلن عنه — إذ تأتي الملاحظات من سجل التغييرات المُضمَّن داخل الصورة — فلا يُجاب إشعار قديم أبدًا بملاحظات أحدث إصدار.

## النسخ الاحتياطي

خذ نسخة احتياطية **قبل كل ترقية**، وأتمت نسخة ليلية في كل الأحوال:

```bash
docker compose exec db pg_dump -U turboea turboea > backup-$(date +%F).sql
```

عدّل اسم المستخدم واسم قاعدة البيانات إذا كنت قد غيّرت `POSTGRES_USER` / `POSTGRES_DB`. ويُعد أخذ لقطة لوحدة التخزين `postgres_data` بديلًا مكافئًا. وعلى خدمة PostgreSQL مُدارة (انظر قسم «قاعدة PostgreSQL المُدارة» أعلاه)، فضّل النسخ الاحتياطية الآلية والاستعادة إلى نقطة زمنية التي يقدمها المزوّد على التفريغات اليدوية — مع بقاء `pg_dump` دوري مفيدًا كنسخة محمولة مستقلة عن المزوّد.

خذ نسخة احتياطية أيضًا من وحدة التخزين **`backend_data`** — فهي تحتوي على مرفقات الملفات والملحقات المثبّتة وحزم نقل مساحة العمل التي لا تُخزَّن في PostgreSQL.

نقطتان إضافيتان حول جاهزية الاستعادة:

- **اختبر عمليات الاستعادة دوريًا.** النسخة الاحتياطية التي لم تُستعد قط هي أمل لا خطة.
- **البطاقات المؤرشفة تُحذف حذفًا مرنًا** مع نافذة 30 يومًا قبل الحذف النهائي — وهذه شبكة أمانك ضد أخطاء البيانات، وهي منفصلة عن استعادة البنية التحتية.

## التراجع والاستعادة

ترحيلات المخطط في الإنتاج **أحادية الاتجاه فعليًا**: فمع أن Alembic يدعم تقنيًا الرجوع إلى إصدارات أدنى، فإن الترحيلات الحاملة للبيانات لا يمكن دائمًا عكسها دون فقد، والتطبيق لا ينفّذ الرجوع تلقائيًا أبدًا. استراتيجية التراجع الموثوقة هي:

1. أوقف المكدّس.
2. استعد النسخة الاحتياطية لقاعدة البيانات المأخوذة قبل الترقية (في PostgreSQL المُدارة: استعادة إلى النقطة الزمنية السابقة مباشرة للترقية).
3. أعد `TURBO_EA_TAG` إلى الإصدار السابق.
4. `docker compose up -d` — قاعدة البيانات المستعادة تطابق مخطط الشيفرة القديمة، فيبقى كل شيء متسقًا.

!!! warning "لا تتراجع أبدًا عن الصورة وحدها"
    التراجع عن الصورة مع الإبقاء على قاعدة البيانات المرحّلة هو التركيبة الوحيدة التي لا يستطيع نظام الترحيل التلقائي حمايتك منها. النسخة الاحتياطية لقاعدة البيانات ووسم الصورة يتحركان معًا.

## استعادة وصول المسؤول { #recovering-administrator-access }

يرفض Turbo EA التغييرين الأكثر تسبّبًا في حجب المسؤول عن نظامه: لا يمكنك تغيير دورك الخاص إلى دور غير مسؤول، ولا يمكنك إلغاء تنشيط حسابك الخاص (انظر [المستخدمون والأدوار](users.md)). يبقى بعد ذلك الحالة المعتادة — كلمة مرور منسيّة، أو نسخة غادر مسؤولها الوحيد الشركة. اتبع هذه القائمة بالترتيب؛ الخطوة الأخيرة وحدها هي التي تمسّ قاعدة البيانات.

1. **اطلب ذلك من مسؤول آخر.** من **Admin ← المستخدمون ← أيقونة التحرير ← كلمة المرور** يمكن تعيين كلمة مرور جديدة لأي حساب محلي. هذا هو المسار المعتاد ولا يتطلّب أي وصول إلى الخادم.
2. **استخدم إعادة التعيين الذاتية.** يرسل رابط **نسيت كلمة المرور** في صفحة تسجيل الدخول رابط إعادة تعيين عبر البريد الإلكتروني. وهو يعمل للحسابات المحلية فقط، وفقط عندما يكون [SMTP مُهيّأً](settings.md) — فالنسخة التي لا خادم بريد لها لا تملك إعادة تعيين ذاتية. أمّا حسابات SSO فلا كلمة مرور لها لإعادة تعيينها؛ عالِجها لدى مزوّد الهوية.
3. **أعد التعيين في قاعدة البيانات.** فقط حين لا يعود بإمكان أي شخص تسجيل الدخول بصفة مسؤول.

### إعادة تعيين كلمة المرور مباشرةً في قاعدة البيانات

أنشئ التجزئة بدالة التجزئة الخاصة بالتطبيق نفسه، كي تكون القيمة المخزَّنة مطابقة تمامًا لما يتوقّعه فحص تسجيل الدخول. لا تصنعها يدويًا باستخدام `htpasswd` أو `openssl`:

```bash
docker compose exec -it backend python -c \
  "from app.core.security import hash_password; print(hash_password(input('New password: ')))"
```

كتابة كلمة المرور عند الموجّه تُبقيها خارج سجلّ أوامر الصدفة. انسخ السطر `$2b$…` الذي يُطبع، ثم:

```bash
docker compose exec -T db psql -v ON_ERROR_STOP=1 -U turboea -d turboea -c \
  "UPDATE users
      SET password_hash = '<الصق التجزئة هنا>',
          auth_provider = 'local',
          is_active = true,
          password_setup_token = NULL
    WHERE lower(email) = lower('admin@example.com');"
```

لكل بند سببه، لأن تسجيل الدخول يفحصها جميعًا:

| البند | سبب وجوده |
|---|---|
| `password_hash` | بيانات الاعتماد الجديدة. أبقِها بين علامتَي اقتباس مفردتين — فتجزئات bcrypt تحتوي على `$` التي كانت الصدفة ستوسّعها لولا ذلك. |
| `auth_provider = 'local'` | كلمة المرور لا تصادق أبدًا على حساب مُعلَّم بأنه SSO. |
| `is_active = true` | الحساب غير النشط يُرفض *بعد* فحص كلمة المرور، وهو ما يبدو تمامًا كأنّ كلمة المرور خاطئة. |
| `password_setup_token = NULL` | يُبطل أي رابط دعوة ما يزال قائمًا، فلا يستطيع لاحقًا الكتابة فوق كلمة المرور التي عيّنتها للتو. |

إن كان الحساب قد خُفِّض دوره أيضًا، فاستعِد الدور في العبارة نفسها بإضافة `role = 'admin'`.

النتيجة المتوقَّعة هي `UPDATE 1`. أمّا `UPDATE 0` فتعني أنه لم يطابق أي صف — إذ تُخزَّن عناوين البريد كما أُدخلت، و`lower()` على الطرفين هو ما يجعل المقارنة غير حسّاسة لحالة الأحرف. للعثور على الصف الصحيح أولًا:

```bash
docker compose exec -T db psql -U turboea -d turboea -c \
  "SELECT email, role, is_active, auth_provider FROM users ORDER BY email;"
```

نقطتان إضافيتان جديرتان بالمعرفة:

- **عدّل بيانات الاتصال.** استخدم قيَمك أنت لـ `POSTGRES_USER` / `POSTGRES_DB` إن كنت قد غيّرتها. وفي خدمة PostgreSQL المُدارة لا وجود لحاوية `db` — اتّصل مباشرةً باستخدام `psql` بدلًا من ذلك.
- **تبقى الجلسات الأخرى مسجَّلة الدخول.** الجلسات هي رموز JWT بلا إبطال من جهة الخادم، لذا تظل الرموز الصادرة قبل إعادة التعيين صالحة حتى انتهاء صلاحيتها (`ACCESS_TOKEN_EXPIRE_MINUTES`، 24 ساعة افتراضيًا). تغيير كلمة المرور لا يُخرج أحدًا من جلسته.

!!! note "الاستثناء المسموح به من قاعدة «لا تحرّر قاعدة البيانات»"
    تحرير قاعدة البيانات مباشرةً مزلق في ما عدا ذلك، ولسبب وجيه. هذا الإجراء آمن لأنه يحدّث بضعة أعمدة في صف واحد من `users`: فهو لا يغيّر أي مخطّط، ومن ثمّ لا يمكن أن يتعارض مع ترحيل مستقبلي، وهو الحالة الوحيدة التي يعجز عن إصلاحها كلٌّ من الواجهة وواجهة البرمجة بحكم التعريف — إذ تحتاج إلى وصول كي تستعيد الوصول.

## البيئات وحوكمة الإصدارات

تكفي **بيئتان** (تجهيز + إنتاج) لمعظم المؤسسات، لأن الترقيات صور يصدرها المورّد وليست بناءات مخصصة — فأنت تتحقق ولا تطوّر. أما سلسلة Dev/SIT/UAT/Prod الكاملة فتضيف قيمة أساسًا إذا كنت تبني ملحقات مخصصة أو تكاملات ثقيلة.

| البيئة | الغرض | ملاحظات |
|---|---|---|
| تطوير / بيئة تجريبية (اختياري) | تجربة تغييرات النموذج الفوقي والعروض التوضيحية | `SEED_DEMO=true` لمجموعة البيانات التجريبية؛ و`RESET_DB=true` يمنح بداية نظيفة. |
| التجهيز (Staging) | التحقق من الإصدارات الجديدة أولًا | بيانات مشابهة للإنتاج؛ تستقبل الوسوم الجديدة أولًا. |
| الإنتاج | وسم مثبّت، نسخ احتياطية، ترقيات ضمن نافذة صيانة | لا `latest` أبدًا، ولا `RESET_DB` أبدًا. |

طريقتان جيدتان لإدخال بيانات واقعية إلى بيئة التجهيز:

- **[نقل مساحة العمل](workspace-transfer.md)**: صدّر مساحة عمل الإنتاج كحزمة `.zip` واستوردها في بيئة التجهيز. تُحذف الأسرار (بيانات اعتماد SMTP وSSO والذكاء الاصطناعي وServiceNow) بحكم التصميم ولا تغادر المثيل أبدًا.
- **استعادة قاعدة البيانات**: استعد `pg_dump` من الإنتاج في قاعدة بيانات التجهيز (وعلى خدمة مُدارة، يفي بالغرض أيضًا استنساخ مثيل الإنتاج أو استعادته إلى نقطة زمنية). الأسرار المشفّرة في قاعدة البيانات مشتقة من `SECRET_KEY`، لذا تحتاج بيئة التجهيز إما إلى نفس `SECRET_KEY` أو إلى إعادة إدخال بيانات اعتماد التكاملات هناك.

على صعيد الحوكمة:

- تعامل مع ملف `.env` والوسم المثبّت `TURBO_EA_TAG` بوصفهما تهيئة كشيفرة — احفظهما في Git الداخلي لديك، واجعل الترقيات تغييرًا خاضعًا للمراجعة (طلب سحب يرفع الوسم).
- ولأن بيئتي التجهيز والإنتاج تسحبان نفس وسم GHCR المثبّت، فأنت تتحقق من نفس القطعة المطابقة بايتًا ببايت التي ستُرقّى.
- رقِّ بيئة التجهيز ← اتركها تعمل بضعة أيام ← ثم رقِّ الوسم نفسه إلى الإنتاج.

## المزالق الشائعة

1. **تشغيل `latest` دون تثبيت** — يتحول `docker compose pull` الروتيني إلى ترقية غير مخطط لها بترحيلات غير مخطط لها، وفق جدول الإصدارات لا جدولك.
2. **الترقية دون نسخة احتياطية** — الترحيلات أحادية الاتجاه؛ والنسخة الاحتياطية *هي* وسيلة تراجعك.
3. **فقدان `SECRET_KEY` أو تغييره** — فهو يوقّع رموز JWT *ويشتق* مفتاح تشفير الأسرار المخزّنة (بيانات اعتماد SMTP وSSO وServiceNow). تغييره يجعل الأسرار المخزّنة غير قابلة لفك التشفير. تعامل معه كبيانات اعتماد قاعدة بيانات: في خزنة، ثابت، ومنسوخ احتياطيًا.
4. **نسيان `RESET_DB=true` في ملف بيئة** — فهو يفعل ما يقوله حرفيًا عند كل بدء تشغيل.
5. **تحرير قاعدة البيانات مباشرة** — حالة المخطط ملك لـ Alembic، وأي DDL يدوي سيتصادم مع الترحيلات المستقبلية. وينطبق الأمر نفسه على البيانات: استخدم واجهة API أو الواجهة الرسومية لتبقى الصلاحيات وأحداث التدقيق وإعادة حساب جودة البيانات صحيحة. والاستثناء المسموح به الوحيد هو [استعادة وصول المسؤول](#recovering-administrator-access)، في الحالة التي لم يعد فيها بإمكان أحد تسجيل الدخول لاستخدام واجهة البرمجة أو الواجهة أصلًا.
6. **عدم إدامة وحدات التخزين** — يجب أن تنجو `postgres_data` و`backend_data` من إعادة إنشاء الحاويات؛ تأكد من أن أدوات اللقطات والنسخ الاحتياطي لديك تغطي كلتيهما.
7. **التراجع عن الصورة دون استعادة قاعدة البيانات** — انظر قسم «التراجع والاستعادة» أعلاه.
8. **توجيه التطبيق إلى PostgreSQL مُدار دون التحقّق من حدّ الاتصالات فيه** — تحتاج الواجهة الخلفية إلى ما يصل إلى 30 اتصالاً افتراضيًا. ويظهر الحدّ الأدنى من ذلك على شكل `too many connections for database "turboea"` أثناء الاستخدام العادي؛ راجع قسم «تحقّق من حدّ الاتصالات» أعلاه.
