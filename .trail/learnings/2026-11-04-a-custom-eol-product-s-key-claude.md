## Decided
- Nobody types or sees a custom EOL product's key. `POST /eol/custom-products` derives it from the title (`product_key_from_title`), suffixing `-2`, `-3` when the key exists, so two products may share a title; an explicit key (API, workspace import) is still accepted. The dialog has no Key field and the grid's product cell shows the title only; the key remains in URLs and as the endoflife.date proposal's file name.
- A custom product's `title` travels on every cycle dict (`product_cycles`, `load_custom_cycles`), so the resolver, `GET /eol/card-status`, the EOL report items (`eol_product_title`) and mass-search (`current_title`) can name the product; the card section, report, inventory tooltip and bulk-link line use `eolProductLabel(product, title)`.
- The card's End of Life chip uses the shared `cycleStatus` (backend `eol_status`): Supported / Approaching EOL / End of life / Unknown, 182 days. The card's own "Security fixes only" status is gone. Note the shared rule treats `support: false` with a far EOL date as *supported* (only a past support date is "approaching").
- The card section takes `canEdit` from the page (`perms.can_edit`): without it, no Link / Change / Unlink.

## Tried and ruled out
- Showing the generated key read-only in the dialog "for reference": the user's call was that nobody cares about it.
- Keeping the card's richer "Security fixes only" label: the same cycle then read differently on the card and in the report.
